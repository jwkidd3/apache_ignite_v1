Traditional Database Limitations

The Problem with Disk-Based Databases

This section motivates the entire course. Ask students if they have experienced slow database queries in production. Most will relate to this pain point, which makes the case for in-memory computing more compelling.

Performance Bottleneck

Disk I/O:        ~100-200 IOPS (HDD)
                 ~10,000-100,000 IOPS (SSD)
RAM Access:      ~1,000,000+ IOPS

Speed Comparison

  • RAM: 100 nanoseconds
  • SSD: 50-150 microseconds (500-1500x slower)
  • HDD: 1-10 milliseconds (10,000-100,000x slower)
Emphasize the orders-of-magnitude difference between RAM and disk. The IOPS numbers are key: RAM can do millions of operations per second versus tens of thousands for SSDs. Ask students to think about what this means for a system doing thousands of queries per second.

Challenges

  • Slow query response times
  • Limited scalability
  • High latency for real-time applications
  • Expensive hardware upgrades
These challenges are what drive organizations to adopt in-memory computing. Highlight that vertical scaling (bigger hardware) has limits, while horizontal scaling with in-memory grids can grow linearly. Common student question: "Can't we just add more indexes?" Yes, but that only helps so much with disk-based I/O.

What is In-Memory Computing?

In-Memory Computing (IMC) uses RAM as the primary storage medium for data and computation.

Stress the word "primary" -- this is not just a cache sitting in front of a database. In-memory computing treats RAM as the main storage layer. This is a paradigm shift from traditional architectures where disk is primary and RAM is just a buffer.

Key Characteristics

  • Data stored in RAM, not disk
  • Distributed across cluster nodes
  • Massively parallel processing
  • Sub-millisecond response times
  • Horizontal scalability
Walk through each characteristic. Distributed across cluster nodes is key -- this is not a single-server solution. Massively parallel processing means computation moves to where the data lives, not the other way around. Sub-millisecond response times are achievable for key-value lookups.

Architecture Comparison

Traditional Architecture: [Application] --> [Database on Disk] --> Slow In-Memory Computing: [Application] --> [Distributed RAM Grid] --> Fast
This simple diagram illustrates the fundamental architectural difference. In the traditional model, every query hits disk. In the in-memory model, data is spread across a grid of RAM on multiple machines. Point out that the "distributed" aspect is what makes this scalable beyond a single machine's RAM capacity.

In-Memory Computing vs Caching

Traditional Caching

  • Sits in front of database
  • Cache-aside pattern
  • Limited functionality

In-Memory Platform

  • Full-featured data platform
  • ACID + SQL + Compute
  • Can be primary data store
This distinction is crucial. Many students initially think of Ignite as "just another Redis." Emphasize that a traditional cache like Memcached only stores key-value pairs and sits passively in front of a database. An in-memory platform like Ignite can run SQL queries, execute distributed computations, and even serve as the primary data store with ACID guarantees.

Apache Ignite Overview

Apache Ignite is a distributed database for high-performance computing with in-memory speed.

Now we transition from general in-memory computing concepts to Apache Ignite specifically. Emphasize that Ignite is not just a cache -- it is a full distributed database platform. The key differentiator from other solutions is the combination of in-memory speed with database-grade features like SQL and ACID transactions.

Key Features

  • Distributed in-memory cache
  • SQL queries (ANSI-99)
  • ACID transactions
  • Distributed computing
  • Machine learning
  • Streaming & CEP
Walk through each feature briefly. SQL queries using ANSI-99 syntax are a major selling point for teams familiar with relational databases. ACID transactions provide data consistency guarantees. Distributed computing allows moving code to data. ML capabilities are built-in for predictive analytics. We will cover most of these in depth during the 3-day course.

Origins

  • Open source (Apache 2.0 license)
  • Apache Top-Level Project
  • Active community
  • Production-proven (GridGain roots since 2007)
The Apache Software Foundation governance provides credibility and long-term viability. GridGain originally developed the technology starting in 2007, then donated it to the Apache Foundation. This means nearly two decades of production hardening. The active community means bugs get fixed quickly and features are continuously added.

The Mental Model

"Redis with SQL"

Think of Ignite as Redis that speaks SQL and scales horizontally

This mental model resonates with most developers because almost everyone has used Redis. The "Redis with SQL" analogy is a simplification but gives students an immediate anchor point. It captures the essence: in-memory speed plus relational query capabilities. Caveat: Ignite is architecturally very different from Redis under the hood.

What This Means

Redis Ignite
Key-value only Key-value + SQL
Single-threaded Multi-threaded, distributed
Primary-replica True horizontal scaling
Limited transactions Full ACID transactions
No joins Distributed joins
Walk through each row of the comparison table. The SQL support is the biggest differentiator -- Redis has no query language for complex lookups. Multi-threaded vs single-threaded is important for CPU-intensive operations. True horizontal scaling means adding nodes increases both capacity and throughput, unlike Redis's primary-replica model. Distributed joins are something Redis simply cannot do.

  • Complex queries

This is the slide to spend extra time on. The combination of Redis-like speed with SQL power is the core value proposition. Students will build on both of these capabilities throughout the labs. Mention that distributed computing allows running code on the nodes where data lives, avoiding costly data transfers.

When to Choose Ignite

Decision Framework

This section is about being honest with students. Ignite is powerful but not the right tool for every job. A good architect knows when NOT to use a technology. Walk through the decision framework methodically.

✓ Choose Ignite When

  • You need SQL on cached data
    JOINs, aggregations, complex queries
  • You need ACID transactions across records
    Financial systems, inventory management
  • You need to scale reads horizontally
    Add nodes to increase throughput
  • You have a read-heavy workload
    80%+ reads is ideal
Focus on the SQL on cached data point -- this is where Ignite shines versus Redis. ACID transactions across records is important for financial and inventory systems. The 80% read-heavy workload guideline is a good rule of thumb. Students should think about their own workload patterns.

✗ Consider Alternatives When

  • Simple key-value, no SQL needed
    → Redis may be simpler
  • Write-heavy with no read requirements
    → Traditional database or Kafka
  • Small dataset, single server sufficient
    → PostgreSQL, MySQL may suffice
  • Need complex stored procedures
    → Traditional RDBMS
Being candid about alternatives builds credibility. If someone just needs simple key-value caching, Redis is simpler to set up and operate. If the dataset fits on a single server, PostgreSQL or MySQL may be perfectly adequate. The overhead of distributed systems only pays off when you actually need distribution.

The Sweet Spot

Ignite excels when you need:

  1. Fast reads (in-memory speed)
  2. SQL query capability
  3. Horizontal scalability
  4. Data consistency (ACID)

Common: Read-optimized layer in front of OLTP database

The sweet spot summary is what students should remember. The most common deployment pattern is Ignite as a read-optimized layer in front of an existing OLTP database. This gives you in-memory speed for reads while keeping your existing database for writes and persistence. This pattern is low-risk and high-reward.

Ignite vs Other Solutions

Comparison Matrix

Students always want to see head-to-head comparisons. Be balanced and fair -- each technology has its strengths. The next few slides go into detail on Ignite vs Redis and Ignite vs Hazelcast, which are the two most common comparisons.
Feature Ignite Redis Hazelcast
SQL Full No Limited
ACID Yes Limited Yes
Compute Yes No Yes
Persistence Native RDB/AOF No
Focus on the SQL row -- this is where Ignite clearly differentiates. Redis has no SQL at all, Hazelcast has limited SQL support. For ACID transactions, both Ignite and Hazelcast support them but Redis only has limited transaction support. Native persistence in Ignite is a unique advantage -- data survives full cluster restarts without an external database.

Ignite vs Redis

Apache Ignite

  • Distributed SQL with joins
  • ACID transactions
  • Distributed computing
  • Multi-language clients
  • Horizontal scalability

Use case: Distributed database + compute

Redis

  • Extremely fast for simple ops
  • Rich data structures
  • Pub/sub messaging
  • Limited query capabilities
  • Single-threaded

Be fair to Redis -- it is excellent at what it does. For simple key-value operations, Redis is often faster because of its single-threaded design that avoids locking overhead. Redis also has rich data structures like sorted sets, HyperLogLog, and streams that Ignite does not have. The key differentiator is when you need SQL queries, ACID transactions, or distributed computing on your cached data.

Ignite vs Hazelcast

Apache Ignite

  • Full SQL support (ANSI-99)
  • Native persistence
  • Better for analytics
  • Apache open source
  • ML built-in

Hazelcast

  • Easier to get started
  • Strong JCache compliance
  • Limited SQL
  • No native persistence (enterprise)

Both are distributed IMDGs with ACID transactions and horizontal scaling

Hazelcast is the closest competitor to Ignite architecturally. Both are Java-based distributed IMDGs. Ignite's advantages are full SQL support, native persistence, and built-in ML. Hazelcast's advantage is ease of getting started -- the API is simpler and documentation is more beginner-friendly. Note that both are excellent products and the choice often depends on specific requirements.

Ignite Deployment Models

Flexible Deployment Options

Deployment flexibility is important because organizations have different infrastructure requirements. Some want tight integration, others want separation of concerns. We will cover these in much more depth in Module 4 on Configuration and Deployment.

1. Embedded Mode

[Application + Ignite Node]
  • Ignite runs in same JVM as application
  • Zero-latency data access
  • Simpler deployment
Embedded mode is what we use in most of the labs. The Ignite node runs inside your application's JVM, giving zero-latency data access. This is the simplest way to get started and is great for development. The trade-off is that your application lifecycle is tied to the data node lifecycle.

2. Client-Server Mode

[Application] --> [Ignite Cluster]
  • Application is lightweight client
  • Cluster is separate tier
  • Better resource isolation
Client-server mode is the recommended production pattern. The Ignite cluster runs as a separate tier, and your applications connect to it as clients. This gives you independent scaling -- you can scale your application servers without affecting data distribution, and vice versa. We will explore both thick and thin clients in Module 2.

3. Kubernetes/Cloud

  • Container-based deployment
  • Auto-scaling
  • Cloud-native architecture
Kubernetes deployment is increasingly common. Ignite has first-class Kubernetes support with a dedicated IP finder for discovery. Auto-scaling with Ignite on Kubernetes requires careful consideration of data rebalancing. We will touch on Docker and Kubernetes deployment in Module 4.

Architecture Patterns

Common Usage Patterns

These three patterns represent the most common ways organizations deploy Ignite. Understanding these patterns helps students choose the right architecture for their use case. Most organizations start with the caching layer pattern and evolve toward system of record or hybrid as they gain confidence.

1. System of Record

[Application] --> [Ignite (Primary Store)]
  • Ignite as main database
  • Native persistence enabled
  • Full ACID compliance
System of Record means Ignite IS your database. This requires native persistence to be enabled so data survives restarts. This pattern is bold but increasingly common for new greenfield applications that need high performance from day one. ACID compliance means you get the same guarantees as a traditional database.

2. Caching Layer

[Application] --> [Ignite Cache] --> [Database]
  • Cache-aside or write-through
  • Faster read access
  • Reduced DB load
The caching layer pattern is the most common starting point. It is low risk because your existing database remains the source of truth. Cache-aside means the application checks the cache first, then falls back to the database. Write-through means writes go to both cache and database simultaneously. This pattern can dramatically reduce database load and improve response times.

3. Hybrid

[Application] --> [Ignite (Hot Data)] --> [Database (Cold Data)]
  • Frequently accessed data in Ignite
  • Historical data in database
  • Best of both worlds
The hybrid pattern is the most sophisticated and often the end-state architecture. Hot data (frequently accessed) lives in Ignite for fast access, while cold data (historical, rarely accessed) stays in a traditional database. This optimizes both cost and performance. The challenge is defining the boundary between hot and cold data and managing data movement between tiers.

Performance Expectations

Setting realistic performance expectations is important. Students often expect magic -- Ignite is fast but not infinitely fast. The numbers on the next slides are typical but depend heavily on hardware, network, data model, and configuration.

Read Operations

  • Single key lookup: < 1ms
  • Batch operations: 100K+ ops/sec per node
  • SQL queries: Sub-millisecond to seconds

Write Operations

  • Single put: 1-2ms
  • Batch puts: 50K+ ops/sec per node
  • Transactional: 10K+ tx/sec per node
Highlight the "per node" aspect -- these numbers scale linearly as you add nodes. A 10-node cluster can do 1M+ reads per second. Single key lookups under 1ms is the headline number. SQL queries vary widely depending on complexity -- a simple indexed lookup is sub-millisecond, while a complex join across partitions could take seconds. Write operations are slightly slower due to replication to backup nodes.

Scalability

  • Linear scale-out (add nodes = add capacity)
  • 100+ node clusters in production
  • Petabyte-scale deployments

Note: Actual performance depends on hardware, data model, access patterns, and configuration.

Linear scalability is the key message here. Adding a node should roughly double your capacity if you go from 1 to 2 nodes. 100+ node clusters exist in production at organizations like Sberbank. The disclaimer at the bottom is important -- always benchmark with your own data and workload patterns rather than relying on published numbers.
