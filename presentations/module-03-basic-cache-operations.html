Cache API Overview

Core Interface

IgniteCache<K, V> cache = ignite.cache("myCache");

// Or create if not exists
IgniteCache<K, V> cache = ignite.getOrCreateCache("myCache");

// With configuration
CacheConfiguration<K, V> cfg = new CacheConfiguration<>("myCache");
IgniteCache<K, V> cache = ignite.getOrCreateCache(cfg);
Key Points:
  • Type-safe generic interface
  • Similar to java.util.Map
  • JCache (JSR 107) compliant
  • Thread-safe operations
The IgniteCache interface is the primary API students will use. Show the three ways to get a cache reference: by name, getOrCreate, and with configuration. Emphasize that it is similar to java.util.Map which most Java developers already know. JCache compliance means code written for Ignite can work with other JCache implementations. Thread safety means no external synchronization is needed.

Basic CRUD Operations

Create/Update - PUT

// Put single entry
cache.put(key, value);

// Put if absent
boolean added = cache.putIfAbsent(key, value);

// Get and put (returns old value)
V oldValue = cache.getAndPut(key, newValue);

Read - GET

// Get single entry
V value = cache.get(key);

// Check existence
boolean exists = cache.containsKey(key);

(Press down arrow for DELETE operations)

Walk through each operation. The put method is straightforward -- if the key exists, the value is overwritten. putIfAbsent is atomic and returns false if the key already exists. getAndPut returns the previous value, which is useful for logging or audit trails. The get method returns null if the key does not exist. These are the bread-and-butter operations students will use most.

Basic CRUD Operations

Delete - REMOVE

// Remove entry
boolean removed = cache.remove(key);

// Conditional remove
boolean removed = cache.remove(key, value);

// Get and remove
V value = cache.getAndRemove(key);
The remove operations mirror the put operations. Simple remove returns a boolean indicating whether the key existed. Conditional remove only removes if the current value matches -- this is a compare-and-swap pattern useful for optimistic concurrency. getAndRemove returns the value before deletion, useful when you need to process data before removing it.

Replace Operations

Atomic Replace

// Replace (key must exist)
boolean replaced = cache.replace(key, newValue);

// Conditional replace (compare-and-swap)
boolean replaced = cache.replace(key, oldValue, newValue);

// Get and replace
V oldValue = cache.getAndReplace(key, newValue);

Use Cases:

  • Optimistic locking
  • Version control
  • Atomic updates
  • Race condition prevention
Replace operations are essential for concurrent programming. The conditional replace with oldValue and newValue is the compare-and-swap (CAS) pattern -- it only succeeds if the current value matches what you expect. This prevents lost updates in multi-threaded or multi-node scenarios. Optimistic locking with replace is more efficient than pessimistic locking with transactions for simple updates.

Replace Operations

Example: Safe Counter Increment

// Increment counter safely
while (true) {
    Integer current = cache.get("counter");
    if (cache.replace("counter", current, current + 1)) {
        break; // Success
    }
    // Retry if another thread modified it
}
This counter example is a classic CAS loop pattern. Read the current value, attempt to replace it with current+1, and retry if another thread modified it concurrently. This is lock-free and scales well. The while(true) loop is safe because contention is typically low and the loop resolves quickly. Students will implement a similar pattern in the lab.

Cache Modes - Overview

Three Cache Modes

PARTITIONED (Default)

  • Data distributed across nodes
  • Best for scalability
  • Configurable backups

REPLICATED

  • Full copy on every node
  • Best for small, read-heavy datasets
  • Slower writes

LOCAL

  • Data only on local node
  • No distribution
  • Good for node-specific data
These three cache modes are fundamental. PARTITIONED is the default and most commonly used -- data is split across nodes for scalability. REPLICATED copies all data to every node, giving fast local reads but at the cost of memory and slower writes. LOCAL is rarely used but appropriate for node-specific temporary data. The choice of cache mode is one of the most important design decisions.

PARTITIONED Cache Mode

Distributed Data

CacheConfiguration<K, V> cfg = new CacheConfiguration<>("partCache");
cfg.setCacheMode(CacheMode.PARTITIONED);
cfg.setBackups(1); // Number of backup copies
With 3 nodes, 1 backup:
Node 1: Primary [A, B, C]    Backup [G, H, I]
Node 2: Primary [D, E, F]    Backup [A, B, C]
Node 3: Primary [G, H, I]    Backup [D, E, F]

Total Memory Usage = Data Size x (1 + Backups) / Nodes

Benefits:

  • Scales horizontally
  • Efficient memory use
  • Parallel processing

Trade-offs:

  • Network hops for remote data
  • Rebalancing on topology changes
Walk through the memory formula: with 3 nodes and 1 backup, total memory usage is Data Size times 2 divided by 3 per node. Each node stores roughly one-third of the primary data plus one-third of backup data. The benefits of horizontal scaling and parallel processing are significant for large datasets. The trade-off is network hops when accessing data owned by another node.

REPLICATED Cache Mode

Full Copy Everywhere

CacheConfiguration<K, V> cfg = new CacheConfiguration<>("replCache");
cfg.setCacheMode(CacheMode.REPLICATED);
// No backup setting needed - all nodes have all data
With 3 nodes:
Node 1: [A, B, C, D, E, F, G, H, I]
Node 2: [A, B, C, D, E, F, G, H, I]
Node 3: [A, B, C, D, E, F, G, H, I]

Total Memory Usage = Data Size x Number of Nodes

Benefits:

  • No network hops (local reads)
  • Fast reads
  • High availability

Trade-offs:

  • High memory usage
  • Slower writes (update all nodes)
  • Doesn't scale with data size

Best For: Reference data, Configuration, Small datasets (< 10 GB), Read-heavy workloads

Emphasize the memory formula: total memory is Data Size times Number of Nodes. This is expensive. A 1GB dataset replicated across 10 nodes uses 10GB total. This is why REPLICATED mode is only appropriate for small datasets. The read speed advantage is significant -- every read is local with no network hop. Use it for lookup tables, configuration data, and reference data like country codes or product categories.

LOCAL Cache Mode

Node-Specific Data

CacheConfiguration<K, V> cfg = new CacheConfiguration<>("localCache");
cfg.setCacheMode(CacheMode.LOCAL);
With 3 nodes:
Node 1: [A, B, C]
Node 2: [D, E, F]
Node 3: [G, H, I]

No sharing, no backups

Benefits:

  • Simple
  • No network overhead
  • Fast operations

Trade-offs:

  • No distribution
  • No fault tolerance
  • Limited scalability

Best For: Session data, Thread-local caches, Node-specific computations, Temporary data

LOCAL mode is the simplest but most limited. Data is not shared between nodes at all -- each node has its own independent copy. There is no fault tolerance since data is not replicated. This is useful for node-specific scratch space, session data that is sticky to a server, or intermediate computation results. Students rarely use this mode in practice but should understand it exists.

Choosing Cache Mode

Decision Matrix

Criteria PARTITIONED REPLICATED LOCAL
Data Size Large Small Any
Read Pattern Any High Any
Write Pattern High Low Any
Memory Efficiency Best Worst Good
Read Speed Network Local Local
Scalability Scales Limited No
Fault Tolerance Yes Yes No
Rule of Thumb: User data, transactions → PARTITIONED | Reference data, lookups → REPLICATED | Temporary, node-specific → LOCAL
This decision matrix is a reference students should bookmark. Walk through each row. For data size: PARTITIONED handles large datasets efficiently, REPLICATED is only for small data. For memory efficiency, PARTITIONED is the clear winner. For read speed, REPLICATED gives local reads. The rule of thumb at the bottom is the quick answer for most decisions. In the lab, students will experiment with all three modes.

Synchronous Operations

Default Behavior

// Synchronous put (waits for completion)
cache.put(key, value); // Blocks until acknowledged

// Synchronous get
V value = cache.get(key); // Blocks until value retrieved

Characteristics:

  • Blocking calls
  • Simple programming model
  • Immediate error handling
  • Lower throughput
  • Can't do other work while waiting

When to Use: Single operations, Need immediate confirmation, Sequential logic, Error handling critical

Synchronous operations are the default and the simplest to understand. The thread blocks until the operation completes, which makes error handling straightforward -- exceptions are thrown immediately. For single operations or sequential logic, synchronous is fine. The performance limitation appears when you need to do many independent operations -- each one blocks, creating a sequential bottleneck.

Asynchronous Operations

Non-Blocking Pattern

IgniteCache<K, V> asyncCache = cache.withAsync();

// Async put
asyncCache.put(key, value);
IgniteFuture<Void> future = asyncCache.future();

// Do other work...
processOtherData();

// Wait for completion when needed
future.get();
The async API uses the withAsync() wrapper to create a non-blocking version of the cache. After calling an operation, you get an IgniteFuture that represents the pending result. You can continue doing other work while the operation completes in the background. Call future.get() when you actually need the result. This pattern enables parallelism within a single thread.

Asynchronous Operations

With Callbacks

asyncCache.get(key);
IgniteFuture<V> future = asyncCache.future();

future.listen(f -> {
    V value = f.get();
    System.out.println("Value retrieved: " + value);
});

Benefits:

  • Non-blocking
  • Higher throughput
  • Parallel operations
  • Better resource utilization

When to Use: Multiple independent operations, High-throughput scenarios, Can do useful work while waiting

Callbacks with listen() are useful when you want to process results as they arrive rather than waiting for all operations to complete. The lambda runs when the future completes, allowing event-driven processing. This is more complex than synchronous code but enables higher throughput. The when-to-use guidelines help students decide: if operations are independent, async wins.

Async Performance Comparison

Scenario: Update 1000 cache entries

Synchronous:

long start = System.currentTimeMillis();
for (int i = 0; i < 1000; i++) {
    cache.put(i, "Value-" + i);
}
long time = System.currentTimeMillis() - start;
// Time: ~500ms (sequential)

Asynchronous:

long start = System.currentTimeMillis();
IgniteCache<K, V> asyncCache = cache.withAsync();
List<IgniteFuture> futures = new ArrayList<>();

for (int i = 0; i < 1000; i++) {
    asyncCache.put(i, "Value-" + i);
    futures.add(asyncCache.future());
}
futures.forEach(f -> f.get());
long time = System.currentTimeMillis() - start;
// Time: ~100ms (parallel)
Speedup: 5x faster!
This side-by-side comparison makes the performance difference concrete. Synchronous: 1000 sequential puts, each waiting for acknowledgment before the next starts. Asynchronous: all 1000 puts fired off immediately, then wait for all to complete. The 5x speedup comes from overlapping network latency. In a multi-node cluster with network round trips, the speedup can be even larger. This is a key optimization students should apply in their own code.

Batch Operations

putAll / getAll

Batch Put:

Map<K, V> batch = new HashMap<>();
for (int i = 0; i < 1000; i++) {
    batch.put(i, "Value-" + i);
}
cache.putAll(batch); // Single network call

Batch Get:

Set<K> keys = new HashSet<>(Arrays.asList(1, 2, 3, 4, 5));
Map<K, V> values = cache.getAll(keys);

Batch Remove:

Set<K> keys = new HashSet<>(Arrays.asList(1, 2, 3));
cache.removeAll(keys);
Batch operations are the single most impactful performance optimization. putAll sends all entries in one network call, which is dramatically faster than individual puts. The entries are automatically routed to the correct nodes based on key affinity. getAll similarly retrieves multiple values in one round trip. Students should always prefer batch operations when working with multiple entries.

Batch Operations

Performance Gain

  • 10-100x faster than individual operations
  • Reduced network round trips
  • Lower protocol overhead
  • Efficient serialization
The 10-100x improvement is not an exaggeration. Each individual put requires a network round trip, serialization, and deserialization. With 1000 individual puts, that is 1000 round trips. With putAll, it is just one round trip per node in the cluster. The reduced protocol overhead and efficient serialization of batch entries add up to massive savings. This is the number one performance tip for new Ignite developers.

Batch Size Optimization

Finding the Sweet Spot

Batch Size Result
Too Small (10) Many network calls, not optimal
Optimal (500-1000) Good balance
Too Large (100,000) Memory pressure, timeout risk

Best Practices:

  • Batch size: 500-1000 entries
  • Monitor network utilization
  • Adjust based on entry size
  • Consider memory constraints
Finding the optimal batch size requires balancing. Too small and you do not get enough benefit from batching. Too large and you risk memory pressure from building the batch in memory, plus timeout risk if the operation takes too long. 500-1000 entries is a good starting point for typical entry sizes. Adjust based on your entry size: smaller entries can use larger batches, larger entries need smaller batches.

Batch Size Optimization

Example Pattern

List<Entry> allData = loadData();
int batchSize = 500;

for (int i = 0; i < allData.size(); i += batchSize) {
    Map<K, V> batch = new HashMap<>();
    for (int j = i; j < Math.min(i + batchSize, allData.size()); j++) {
        batch.put(allData.get(j).key, allData.get(j).value);
    }
    cache.putAll(batch);
}
This code pattern is one students should memorize. It iterates through a large dataset in chunks of the specified batch size, building a HashMap for each batch and calling putAll. The Math.min prevents an IndexOutOfBoundsException on the last batch. This pattern works for data loading, migration, and bulk updates. Students will implement this pattern in the lab.

Atomic Operations

Thread-Safe Operations

Built-in Atomicity:

// These are atomic (no race conditions)
cache.putIfAbsent(key, value);
cache.replace(key, oldValue, newValue);
cache.remove(key, value);
cache.getAndPut(key, value);
cache.getAndRemove(key);
cache.getAndReplace(key, value);

NON-ATOMIC (Bad):

if (!cache.containsKey(key)) {
    cache.put(key, value);
    // Race condition!
}

ATOMIC (Good):

cache.putIfAbsent(key, value);
// Thread-safe!

Use Cases: Counters, Flags, Resource allocation, Distributed locks

The side-by-side comparison of non-atomic vs atomic code is critical. The non-atomic version has a race condition: between containsKey and put, another thread could insert the same key. putIfAbsent eliminates this race in a single atomic operation. Emphasize that this is a distributed system -- race conditions can happen across nodes, not just threads. Always use the atomic variants when concurrent access is possible.

Cache Iteration

Scanning Cache Entries

forEach:

cache.forEach(entry -> {
    System.out.println(entry.getKey() + " = " + entry.getValue());
});

Iterator:

for (Cache.Entry<K, V> entry : cache) {
    K key = entry.getKey();
    V value = entry.getValue();
}

Scan Query:

ScanQuery<K, V> scan = new ScanQuery<>((k, v) -> v.startsWith("A"));

try (QueryCursor<Cache.Entry<K, V>> cursor = cache.query(scan)) {
    for (Cache.Entry<K, V> entry : cursor) {
        // Process entries
    }
}

Caution: Iteration can be expensive on large datasets. Consider SQL queries or scan queries for filtering.

Three iteration approaches with different trade-offs. forEach is the simplest but pulls all data to the client. The iterator approach using for-each loop is similar. ScanQuery is the most efficient because it can push filtering to the server side -- only matching entries are transferred over the network. Emphasize the caution: iterating a large distributed cache transfers all data across the network. SQL queries or ScanQueries with predicates are much more efficient for filtering.

Cache Size and Metrics

Monitoring Cache

Size Operations:

// Local size (on this node)
int localSize = cache.localSize();

// Total size (across cluster)
int totalSize = cache.size();

// Size with mode
int primarySize = cache.localSize(CachePeekMode.PRIMARY);
int backupSize = cache.localSize(CachePeekMode.BACKUP);

Cache Metrics:

CacheMetrics metrics = cache.metrics();

System.out.println("Gets: " + metrics.getCacheGets());
System.out.println("Puts: " + metrics.getCachePuts());
System.out.println("Hits: " + metrics.getCacheHits());
System.out.println("Misses: " + metrics.getCacheMisses());
System.out.println("Hit %: " + metrics.getCacheHitPercentage());
Monitoring cache metrics is essential for production. The localSize vs size distinction matters: localSize shows entries on this node, size aggregates across the cluster. CachePeekMode lets you see primary vs backup counts separately. CacheMetrics provides hit/miss ratios, operation counts, and timing. The hit percentage is the most important metric -- below 90% usually indicates a problem with your caching strategy.

Clear vs Destroy

Cache Management

Clear (Empty Cache):

cache.clear();
  • Cache still exists
  • Can add new entries
  • Configuration preserved

Remove All:

cache.removeAll();
  • Same as clear but with events

Destroy (Delete Cache):

ignite.destroyCache("myCache");
  • Cache no longer exists
  • Must recreate to use
  • Frees all resources
Use Cases: Clear = Reset data for new test | RemoveAll = Clear with event notifications | Destroy = Remove cache entirely
The distinction between clear, removeAll, and destroy is a common source of confusion. Clear removes all entries but keeps the cache structure -- useful for resetting between test runs. RemoveAll is similar but fires cache entry events, which matters if you have event listeners. Destroy completely removes the cache including its configuration -- the cache name becomes invalid. A common mistake is calling destroy when clear was intended.

Error Handling

Exception Management

Common Exceptions:

try {
    cache.put(key, value);
} catch (CacheException e) {
    // Generic cache operation error
} catch (TransactionException e) {
    // Transaction-specific error
} catch (ClusterTopologyException e) {
    // Cluster state changed during operation
}

Timeout Handling:

IgniteCache<K, V> cacheWithTimeout = cache.withExpiryPolicy(
    new CreatedExpiryPolicy(new Duration(TimeUnit.SECONDS, 10))
);
Error handling in a distributed system requires understanding the exception hierarchy. CacheException is the generic wrapper for most cache errors. TransactionException occurs during transactional operations. ClusterTopologyException means the cluster changed during the operation -- this is retriable. The expiry policy example shows how to set automatic TTL on cache entries, which helps prevent stale data.

Error Handling

Retry Pattern

int maxRetries = 3;
for (int i = 0; i < maxRetries; i++) {
    try {
        cache.put(key, value);
        break; // Success
    } catch (ClusterTopologyException e) {
        if (i == maxRetries - 1) throw e;
        Thread.sleep(100); // Wait and retry
    }
}
The retry pattern is essential for production code. ClusterTopologyException is transient -- it occurs when a node joins or leaves during an operation. Retrying after a short delay usually succeeds. The maximum retry count prevents infinite loops. In production, consider using exponential backoff instead of fixed 100ms delays. Students should add retry logic to all critical cache operations in their applications.

Performance Best Practices

Optimization Tips

1. Use Batch Operations

// Slow
for (Entry e : entries) cache.put(e.key, e.value);

// Fast
cache.putAll(entriesMap);

2. Use Async for Parallel Operations

// Sequential
for (K key : keys) cache.get(key);

// Parallel
IgniteCache async = cache.withAsync();
List<Future> futures = new ArrayList<>();
for (K key : keys) {
    async.get(key);
    futures.add(async.future());
}
These two best practices are the most impactful optimizations. The code examples show the slow way (individual operations) versus the fast way (batch and async). Encourage students to always think about whether they are doing one operation or many. If many, use putAll/getAll or async. These simple changes can make orders-of-magnitude performance differences in production.

Performance Best Practices

More Tips

3. Choose Right Cache Mode

  • Large data → PARTITIONED
  • Small, read-heavy → REPLICATED

4. Configure Backups Appropriately

  • 1 backup usually sufficient
  • More backups = more memory

5. Enable Statistics

cfg.setStatisticsEnabled(true); // Monitor performance
Tips 3-5 are configuration-level optimizations. Choosing the right cache mode (covered earlier) is a design decision that affects everything. One backup is sufficient for most workloads -- more backups use proportionally more memory. Enabling statistics adds a small overhead but is invaluable for monitoring and troubleshooting. Always enable statistics in production.

Cache Configuration Summary

CacheConfiguration<K, V> cfg = new CacheConfiguration<>();
cfg.setName("myCache");
cfg.setCacheMode(CacheMode.PARTITIONED);
cfg.setBackups(1);
cfg.setAtomicityMode(CacheAtomicityMode.ATOMIC);
cfg.setStatisticsEnabled(true);
This summary shows a complete cache configuration with all the important settings. Walk through each line: name, cache mode, backups, atomicity mode, and statistics. ATOMIC mode is faster than TRANSACTIONAL because it does not require two-phase commit. Use TRANSACTIONAL only when you need cross-key consistency. PRIMARY_SYNC write mode is a good balance of speed and safety -- not shown here but covered in Module 4.

Common Patterns

Cache-Aside

V val = cache.get(key);
if (val == null) { val = db.query(key); cache.put(key, val); }

Distributed Counter

cache.putIfAbsent("counter", 0);
cache.replace("counter", current, current + 1);
These two patterns appear in almost every Ignite application. Cache-aside is the most common caching pattern: check the cache first, fall back to the database on a miss, and populate the cache for next time. The distributed counter uses putIfAbsent for initialization and replace for atomic increments. Both patterns will be practiced in the lab exercises.

Troubleshooting

Issue Solution
Slow ops Check network, use batch/async
High memory Review backups, add eviction
Data not found Verify cache name and key type
These three troubleshooting scenarios are the most common issues students encounter. Slow operations usually mean network latency or too many individual operations -- switch to batch or async. High memory usage often means too many backups or no eviction policy. Data not found is frequently a cache name typo or key type mismatch -- Ignite uses exact type matching, so Integer 1 and Long 1 are different keys.

Key Takeaways

Remember These Points

  1. Cache modes matter
    • PARTITIONED: scalable, distributed
    • REPLICATED: fast reads, high memory
    • LOCAL: node-specific, simple
  2. Batch operations are faster
    • putAll/getAll reduce network calls
    • 10-100x performance improvement
  3. Use async for parallelism - Non-blocking, better throughput
  4. Atomic operations prevent races - putIfAbsent, replace, etc.
  5. Monitor with metrics - Hit ratios, operation times, cache sizes
These five takeaways are the core of this module. Cache modes determine your data distribution strategy and should match your access patterns. Batch operations are the single biggest performance win. Async operations enable parallelism. Atomic operations prevent race conditions in distributed systems. Metrics are essential for understanding and optimizing cache performance. Students should be able to apply all five in the upcoming lab.
