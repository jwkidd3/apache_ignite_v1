SECURITY

Authentication and SSL/TLS

Securing your Ignite cluster for production

Security is often overlooked in development but is absolutely mandatory for production. We will cover authentication, SSL/TLS encryption, and the security checklist that every production deployment must satisfy.

Security Overview

Authentication

  • User credentials required
  • Role-based access control
  • Permission management
  • Audit logging

Encryption

  • SSL/TLS communication
  • Node-to-node encryption
  • Client connections
  • Data at rest encryption
Ignite supports both authentication and encryption. Authentication prevents unauthorized access, while SSL/TLS protects data in transit. In many regulated industries, both are required for compliance. Data at rest encryption is available for persistent storage.

Authentication Configuration

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setIgniteInstanceName("secure-node");

// Configure discovery
TcpDiscoverySpi spi = new TcpDiscoverySpi();
TcpDiscoveryVmIpFinder ipFinder = new TcpDiscoveryVmIpFinder();
ipFinder.setAddresses(Arrays.asList("127.0.0.1:47500..47509"));
spi.setIpFinder(ipFinder);
cfg.setDiscoverySpi(spi);
Authentication configured via security plugin
Authentication in Ignite is configured through a security plugin. The basic configuration here shows standard discovery setup. In a secured cluster, clients must provide valid credentials before any cache operations are allowed.

SSL/TLS Configuration

<property name="sslContextFactory">
  <bean class="org.apache.ignite.ssl.SslContextFactory">
    <property name="keyStoreFilePath" value="keystore.jks"/>
    <property name="keyStorePassword" value="${KEYSTORE_PASS}"/>
    <property name="trustStoreFilePath" value="truststore.jks"/>
    <property name="protocol" value="TLSv1.2"/>
  </bean>
</property>
SSL/TLS configuration requires a keystore for the server certificate and a truststore containing trusted certificates. Always use TLSv1.2 or higher. Store passwords securely using environment variables or a secrets manager rather than hardcoding them in configuration files.

Generate SSL Certificates

#!/bin/bash

# Generate keystore with server certificate
keytool -genkeypair -alias ignite-server \
    -keyalg RSA -keysize 2048 \
    -validity 365 \
    -keystore keystore.jks \
    -storepass changeit \
    -keypass changeit \
    -dname "CN=ignite.example.com, OU=Ignite, O=MyOrg, L=City, ST=State, C=US"

# Export certificate
keytool -exportcert -alias ignite-server \
    -keystore keystore.jks \
    -storepass changeit \
    -file server.cer

# Create truststore with server certificate
keytool -importcert -alias ignite-server \
    -file server.cer \
    -keystore truststore.jks \
    -storepass changeit \
    -noprompt

echo "SSL certificates generated successfully!"
echo "  - Keystore: keystore.jks"
echo "  - Truststore: truststore.jks"
Walk through this script step by step. In production you would use a proper CA-signed certificate rather than a self-signed one. The truststore must contain the certificates of all nodes that are allowed to join the cluster, providing mutual TLS authentication.

Security Best Practices

  • Use strong passwords (rotate regularly)
  • Enable SSL/TLS for all communication
  • Implement role-based access control
  • Enable audit logging
  • Configure firewall rules (ports 47500-47509, 47100, 10800)
  • Use secure credential storage (HashiCorp Vault, etc.)
  • Keep Ignite and dependencies updated
These best practices are non-negotiable for production. Password rotation and secure credential storage are often missed. Emphasize that firewall rules should restrict discovery and communication ports to internal cluster traffic only, while thin client and REST ports can be exposed to authorized clients.

Production Security Checklist

Required for Production:
  • Authentication enabled
  • SSL/TLS configured and tested
  • Firewall rules in place
  • Audit logging enabled
  • Regular security updates scheduled
  • Encrypted node-to-node communication
  • Secure credential management
Use this checklist as a gate before any production deployment. Every item should be verified and signed off. If any item is missing, the deployment should be delayed until it is addressed. This is a good candidate for an automated compliance check in your CI/CD pipeline.

DOCKER

Container Deployment

Containerizing Apache Ignite for modern deployments

Docker is the standard for packaging and deploying Ignite in modern environments. We will cover building a custom Ignite image, composing a multi-node cluster, and the key considerations for running a stateful distributed system inside containers.

Dockerfile

FROM openjdk:11-jre-slim

# Install Ignite
ENV IGNITE_VERSION 2.16.0
ENV IGNITE_HOME /opt/ignite

RUN apt-get update && \
    apt-get install -y wget unzip && \
    wget https://archive.apache.org/dist/ignite/${IGNITE_VERSION}/apache-ignite-${IGNITE_VERSION}-bin.zip && \
    unzip apache-ignite-${IGNITE_VERSION}-bin.zip -d /opt && \
    mv /opt/apache-ignite-${IGNITE_VERSION}-bin ${IGNITE_HOME} && \
    rm apache-ignite-${IGNITE_VERSION}-bin.zip && \
    apt-get clean

# Copy configuration
COPY ignite-config.xml ${IGNITE_HOME}/config/

WORKDIR ${IGNITE_HOME}

# Expose ports: REST, Thin Client, Communication, Discovery
EXPOSE 8080 10800 47100 47500

# JVM options for containerized environment
ENV JVM_OPTS="-Xms1g -Xmx1g -XX:+UseG1GC -XX:+UseContainerSupport"

CMD ${IGNITE_HOME}/bin/ignite.sh ${IGNITE_HOME}/config/ignite-config.xml
Key points in this Dockerfile: we expose all four essential ports, use UseContainerSupport so the JVM respects container memory limits, and copy in our own configuration file. In production, consider using the official apacheignite/ignite image as a base instead of building from scratch.

      - IGNITE_INSTANCE_NAME=node2
      - JVM_OPTS=-Xms2g -Xmx2g -XX:+UseG1GC
    networks:
      - ignite-net
    volumes:
      - ignite-data-2:/persistence

  ignite-node3:
    build: .
    container_name: ignite-node3
    hostname: ignite-node3
    environment:
      - IGNITE_INSTANCE_NAME=node3
      - JVM_OPTS=-Xms2g -Xmx2g -XX:+UseG1GC

  ignite-data-2:

This Docker Compose file creates a 3-node cluster with named volumes for persistence. Each node gets its own volume so data survives container restarts. The bridge network allows nodes to discover each other by hostname. Note the JVM memory settings match across all nodes for consistent behavior.

Docker Discovery Configuration

<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
           http://www.springframework.org/schema/beans/spring-beans.xsd">

    <bean class="org.apache.ignite.configuration.IgniteConfiguration">
        <!-- Discovery for Docker network -->
        <property name="discoverySpi">
            <bean class="org.apache.ignite.spi.discovery.tcp.TcpDiscoverySpi">
                <property name="ipFinder">
                    <bean class="org.apache.ignite.spi.discovery.tcp.ipfinder.vm.TcpDiscoveryVmIpFinder">
                        <property name="addresses">
                            <list>
                                <value>ignite-node1:47500..47509</value>
                                <value>ignite-node2:47500..47509</value>
                                <value>ignite-node3:47500..47509</value>
                            </list>
                        </property>
                    </bean>
                </property>
            </bean>
        </property>
    </bean>
</beans>
In Docker, nodes discover each other using container hostnames. The VM IP finder lists all three hostnames explicitly. This is simpler than multicast discovery, which does not work across Docker networks. For larger dynamic clusters, consider using a ZooKeeper-based discovery instead.

Docker Commands

# Build and start cluster
docker-compose up -d

# Check cluster status
docker-compose ps

# View logs
docker-compose logs -f ignite-node1

# Scale to 5 nodes (if using replicas)
docker-compose up -d --scale ignite-node2=5

# Execute command in container
docker exec -it ignite-node1 /opt/ignite/bin/ignite.sh --baseline

# Stop cluster gracefully
docker-compose down

# Stop and remove volumes (WARNING: deletes data)
docker-compose down -v
Demonstrate these commands live if possible. The most important point is the difference between docker-compose down and docker-compose down -v. The -v flag removes volumes and permanently deletes all persisted data. Always warn team members about this distinction.

Docker Best Practices

Do

  • Use volume mounts for persistence
  • Configure resource limits
  • Use container-aware JVM flags
  • Use health checks
  • Plan network topology

Avoid

  • Running without resource limits
  • Storing data in container layer
  • Using host networking blindly
  • Ignoring container logs
The key takeaway is that Ignite is a stateful system. Always use volume mounts for persistence, set resource limits so the JVM does not consume more than allocated, and use UseContainerSupport so Java correctly detects container memory boundaries.

KUBERNETES

Cloud-Native Deployment

Production-grade Ignite on Kubernetes

Kubernetes is the most common deployment target for production Ignite clusters today. We will cover StatefulSets, headless services for discovery, persistent volume claims, health probes, and the Kubernetes-native IP finder that Ignite provides out of the box.

Kubernetes Architecture

+----------------------------------------------------------+ | Kubernetes Cluster | | +----------------------------------------------------+ | | | ignite namespace | | | | +------------+ +------------+ +------------+ | | | | | ignite-0 | | ignite-1 | | ignite-2 | | | | | | (Pod) | | (Pod) | | (Pod) | | | | | | PVC: 10Gi | | PVC: 10Gi | | PVC: 10Gi | | | | | +------------+ +------------+ +------------+ | | | | ^ ^ ^ | | | | | | | | | | | +--------------------------------------------+ | | | | | ignite-discovery (Headless Service) | | | | | +--------------------------------------------+ | | | | | | | | | +--------------------------------------------+ | | | | | ignite-service (LoadBalancer) | | | | | | Ports: 8080, 10800, 47100 | | | | | +--------------------------------------------+ | | | +----------------------------------------------------+ | +----------------------------------------------------------+
This architecture diagram shows the key components. The headless service provides DNS-based discovery so pods can find each other. The LoadBalancer service exposes client-facing ports. Each pod has its own persistent volume claim for data durability across pod restarts.

Namespace and Services

apiVersion: v1
kind: Namespace
metadata:
  name: ignite
---
apiVersion: v1
kind: Service
metadata:
  name: ignite-service
  namespace: ignite
spec:
  type: LoadBalancer
  ports:
    - name: rest
      port: 8080
      targetPort: 8080
    - name: thin-client
      port: 10800
      targetPort: 10800
    - name: thick-client
      port: 47100
      targetPort: 47100
  selector:
    app: ignite
---
apiVersion: v1
kind: Service
metadata:
  name: ignite-discovery
  namespace: ignite
spec:
  clusterIP: None    # Headless service for discovery
  ports:
    - name: discovery
      port: 47500
      targetPort: 47500
  selector:
    app: ignite
Two services are needed: a LoadBalancer for external client access and a headless service with clusterIP None for internal pod discovery. The headless service is critical because it creates DNS A records for each pod, which the Kubernetes IP finder uses to locate cluster members.

StatefulSet Configuration

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: ignite-cluster
  namespace: ignite
spec:
  serviceName: ignite-discovery
  replicas: 3
  selector:
    matchLabels:
      app: ignite
  template:
    metadata:
      labels:
        app: ignite
    spec:
      containers:
      - name: ignite
        image: apacheignite/ignite:2.16.0
        ports:
        - containerPort: 47100  # Communication
        - containerPort: 47500  # Discovery
        - containerPort: 10800  # Thin clients
        - containerPort: 8080   # REST API
        env:
        - name: IGNITE_INSTANCE_NAME
          valueFrom:
            fieldRef:
              fieldPath: metadata.name
        - name: JVM_OPTS
          value: "-Xms2g -Xmx2g -XX:+UseG1GC"
        - name: OPTION_LIBS
          value: "ignite-kubernetes,ignite-rest-http"
The StatefulSet ensures pods get stable network identities like ignite-cluster-0, ignite-cluster-1. The OPTION_LIBS environment variable loads the Kubernetes discovery module and REST API. Note how the instance name is derived from the pod metadata name for easy identification in logs.

StatefulSet - Resources and Storage

        # Resource limits
        resources:
          requests:
            memory: "2Gi"
            cpu: "1000m"
          limits:
            memory: "4Gi"
            cpu: "2000m"
        # Volume mount for persistence
        volumeMounts:
        - name: ignite-storage
          mountPath: /persistence
        # Health checks
        readinessProbe:
          httpGet:
            path: /ignite?cmd=version
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
        livenessProbe:
          tcpSocket:
            port: 47500
          initialDelaySeconds: 60
          periodSeconds: 20
  volumeClaimTemplates:
  - metadata:
      name: ignite-storage
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
Resource requests and limits prevent noisy neighbor problems. The readiness probe checks the REST API to confirm the node is ready to serve traffic. The liveness probe uses a TCP check on the discovery port. Volume claim templates create a unique PVC per pod, ensuring data persists across pod restarts.

Kubernetes Discovery ConfigMap

apiVersion: v1
kind: ConfigMap
metadata:
  name: ignite-config
  namespace: ignite
data:
  ignite-config.xml: |
    <?xml version="1.0" encoding="UTF-8"?>

The TcpDiscoveryKubernetesIpFinder queries the Kubernetes API to find pod IPs in the specified namespace and service. This eliminates the need to hardcode IP addresses. The ignite-kubernetes module must be included in OPTION_LIBS for this to work. RBAC permissions may be needed for the pod service account.

Kubernetes Deployment Commands

# Create namespace
kubectl apply -f ignite-namespace.yaml

# Deploy ConfigMap
kubectl apply -f ignite-configmap.yaml

# Deploy Services
kubectl apply -f ignite-service.yaml

kubectl apply -f ignite-statefulset.yaml

kubectl get pods -n ignite -w

# Port forward for local access
kubectl port-forward svc/ignite-service 10800:10800 -n ignite

kubectl exec -it ignite-cluster-0 -n ignite -- /opt/ignite/bin/ignite.sh --baseline
Walk through these commands in order. The -w flag on get pods provides a watch mode to see pods come up in real time. Port-forwarding is useful for local development access. Scaling the StatefulSet triggers automatic rebalancing as new nodes join the cluster topology.

StatefulSet vs Deployment

Feature StatefulSet Deployment
Pod Identity Stable, ordered Random
Storage Persistent, per-pod Shared or ephemeral
Network Predictable DNS Random
Scaling Ordered (0, 1, 2...) Parallel
Use Case Ignite, Databases Stateless apps
Recommendation: Always use StatefulSet for Ignite clusters to ensure stable network identity and persistent storage.
This comparison is important because teams sometimes try to use Deployments for Ignite, which causes problems. StatefulSets provide the stable pod identity and per-pod storage that Ignite requires. Deployments create pods with random names and shared storage, which leads to data corruption and discovery failures.

Kubernetes Best Practices

  • Use StatefulSets: Stable pod identity and persistent storage
  • Configure Resource Limits: Prevent noisy neighbor issues
  • Use PodDisruptionBudgets: Ensure quorum during updates
  • Enable Health Probes: Automatic pod recovery
  • Use Kubernetes Discovery: TcpDiscoveryKubernetesIpFinder
  • Plan Storage: Use appropriate StorageClass (SSD preferred)
  • Network Policies: Restrict cluster communication
PodDisruptionBudgets are critical for preventing Kubernetes from evicting too many Ignite pods simultaneously during node maintenance or upgrades. SSD-backed StorageClass provides the IOPS needed for WAL and checkpoint operations. Network policies add defense in depth by restricting which pods can communicate with the Ignite cluster.

BACKUP

Backup and Disaster Recovery

Protecting your data for business continuity

Backup and disaster recovery are essential for any production data store. Even though Ignite replicates data across nodes, you still need backups for protection against logical errors, accidental deletions, and full cluster failures. We will cover snapshots, WAL archiving, and cross-datacenter strategies.

Backup Strategies Overview

Strategy Type Use Case
Snapshots Full backup Point-in-time recovery
WAL Archiving Incremental Continuous protection
Persistence Backup File-based Offline backup
Cross-DC Replication Real-time Disaster recovery
Each strategy has different tradeoffs. Snapshots are the simplest for full recovery. WAL archiving provides continuous protection with lower RPO. File-based persistence backup works for offline scenarios. Cross-datacenter replication is the gold standard for disaster recovery but adds complexity and cost.

Snapshot Backups

# Create cluster snapshot
bin/ignite.sh --snapshot create my_snapshot_20240115

# List available snapshots
bin/ignite.sh --snapshot list

# Check snapshot status
bin/ignite.sh --snapshot status

# Restore from snapshot (cluster must be stopped)
bin/ignite.sh --snapshot restore my_snapshot_20240115

# Cancel snapshot operation
bin/ignite.sh --snapshot cancel
Snapshot Features:
  • Full cluster point-in-time backup
  • Consistent across all nodes
  • Includes all caches and metadata
Snapshots are cluster-wide consistent backups taken while the cluster is running. They capture all caches and metadata at a single point in time. Restoration requires the cluster to be stopped first. Schedule automated snapshots during low-traffic periods to minimize performance impact.

Write-Ahead Log (WAL)

+-------------------+ +-------------------+ +-------------------+ | Application | | WAL Segments | | Archive | | Write | --> | (Active) | --> | (Backup) | +-------------------+ +-------------------+ +-------------------+ | v +-------------------+ | Checkpoint | | (Persistence) | +-------------------+
  • WAL: Records all changes before applying to data regions
  • Archiving: Move WAL segments to backup storage
  • Recovery: Replay WAL to restore to specific point
The WAL is fundamental to how Ignite persistence works. Every write goes to the WAL first, then gets applied during checkpoints. Archiving WAL segments to external storage enables point-in-time recovery. This is analogous to database transaction logs and provides the lowest possible RPO.

WAL Configuration

// Configure WAL for incremental backup
DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// Enable WAL archiving
storageCfg.setWalMode(WALMode.FSYNC);
storageCfg.setWalArchivePath("/backup/wal-archive");
storageCfg.setWalPath("/data/wal");

// WAL segment size (default 64MB)
storageCfg.setWalSegmentSize(64 * 1024 * 1024);

// WAL history size for point-in-time recovery
storageCfg.setWalHistorySize(20);

// Enable checkpointing
storageCfg.setCheckpointFrequency(180_000); // 3 minutes

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setDataStorageConfiguration(storageCfg);
FSYNC mode provides the strongest durability guarantees by forcing writes to disk. The WAL archive path should point to a different physical disk or network storage from the main data path. Checkpoint frequency balances recovery speed against write amplification. More frequent checkpoints mean faster recovery but more I/O overhead.

Disaster Recovery Strategies

Active-Passive

  • Primary cluster handles traffic
  • Secondary on standby
  • Manual or automated failover
  • Lower cost

Active-Active

  • Both clusters handle traffic
  • Bi-directional replication
  • Automatic load distribution
  • Higher complexity
Active-passive is simpler and cheaper but requires failover time. Active-active provides zero downtime but introduces conflict resolution complexity. Most organizations start with active-passive and move to active-active only when RTO requirements demand it. The choice depends on your business SLAs.

Recovery Procedures

# 1. Recovery from Snapshot
# Stop cluster
# Restore snapshot
bin/ignite.sh --snapshot restore my_snapshot
# Start cluster
# Activate cluster
bin/ignite.sh --set-state ACTIVE

# 2. Recovery from Persistence Files
# Stop cluster
# Copy persistence files from backup to all nodes
rsync -av /backup/persistence/ /data/persistence/
# Start cluster
# Activate and verify

# 3. WAL-based Recovery (automatic on startup)
# Node automatically replays WAL on startup
# No manual intervention required
# Ensures data consistency after crash
Practice these recovery procedures regularly. Snapshot restore is the most common approach. File-based recovery using rsync is useful when snapshots are not available. WAL-based recovery happens automatically on node startup and requires no manual intervention, which is one of the benefits of Ignite native persistence.

Backup Best Practices

  • Schedule regular automated backups
  • Test recovery procedures quarterly
  • Store backups in geographically separate location
  • Monitor backup job success/failure
  • Document recovery runbooks
  • Keep multiple backup generations
  • Verify backup integrity with checksums
  • Define RTO/RPO based on business needs
Testing recovery is the most commonly skipped practice. Schedule quarterly DR drills to verify that backups are valid and the team knows the recovery procedures. Geo-separated backups protect against regional failures. Define RTO and RPO early so the backup strategy aligns with business expectations.

Rolling Updates

Zero-Downtime Upgrades

Maintaining availability during maintenance

Rolling updates allow you to upgrade Ignite versions or apply configuration changes without taking the entire cluster offline. The key principle is updating one node at a time and waiting for data rebalancing to complete before proceeding to the next node.

Rolling Update Process

Step 1: Cluster Running (v2.15) +--------+ +--------+ +--------+ | Node 1 | | Node 2 | | Node 3 | | v2.15 | | v2.15 | | v2.15 | +--------+ +--------+ +--------+ Step 2: Update Node 1 +--------+ +--------+ +--------+ | Node 1 | | Node 2 | | Node 3 | | v2.16 | | v2.15 | | v2.15 | | (new) | | | | | +--------+ +--------+ +--------+ Step 3: Continue for Each Node... Step 4: All Updated +--------+ +--------+ +--------+ | Node 1 | | Node 2 | | Node 3 | | v2.16 | | v2.16 | | v2.16 | +--------+ +--------+ +--------+
This diagram shows the rolling update progression. At each step, only one node is offline for the upgrade. With backup copies configured, the cluster remains fully available throughout the process. The mixed-version state in steps 2 and 3 is supported by Ignite version compatibility.

Rolling Update Procedure

#!/bin/bash
# Rolling Update Script for Apache Ignite

echo "=== Rolling Update Procedure ==="

# Prerequisites checklist
echo "Pre-update checklist:"
echo "  [x] Backup completed"
echo "  [x] New version tested in staging"
echo "  [x] Maintenance window scheduled"
echo "  [x] Rollback plan ready"

# For each node (one at a time):
for node in node1 node2 node3; do
    echo "Updating $node..."

    # 1. Stop node gracefully
    ssh $node "kill -SIGTERM \$(cat /var/run/ignite.pid)"
    sleep 30  # Wait for graceful shutdown

    # 2. Update binaries
    ssh $node "cp -r /opt/ignite-2.16.0/* /opt/ignite/"

    # 3. Start node
    ssh $node "/opt/ignite/bin/ignite.sh &"

    # 4. Wait for node to rejoin
    sleep 60

    # 5. Verify cluster health
    ./bin/ignite.sh --baseline

    # 6. Wait for rebalancing
    echo "Waiting for rebalancing to complete..."
    sleep 120
done

echo "Rolling update complete!"
This script automates the rolling update process. The sleep intervals are important to allow graceful shutdown and rebalancing. In practice, you would replace the fixed sleep with a health check loop that verifies rebalancing is complete before proceeding. Always have a rollback plan ready in case the new version introduces issues.

Kubernetes Rolling Update

# Update StatefulSet with rolling update strategy
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: ignite-cluster
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0  # Update all pods
  # ... rest of spec

---
# Pod Disruption Budget for safety
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: ignite-pdb
  namespace: ignite
spec:
  minAvailable: 2    # Keep at least 2 pods running
  selector:
    matchLabels:
      app: ignite
# Trigger rolling update
kubectl set image statefulset/ignite-cluster \
  ignite=apacheignite/ignite:2.16.0 -n ignite

# Monitor rollout
kubectl rollout status statefulset/ignite-cluster -n ignite
Kubernetes handles rolling updates natively for StatefulSets. The PodDisruptionBudget with minAvailable of 2 ensures at least two pods remain running during the update. Kubernetes updates pods in reverse ordinal order, so ignite-cluster-2 updates first, then 1, then 0. Monitor the rollout status to track progress.

Rolling Update Best Practices

Critical Points:
  • Update ONE node at a time
  • Wait for rebalancing to complete before proceeding
  • Monitor cluster health throughout
  • Have rollback plan ready
  • Version Compatibility: Check compatibility matrix
  • Configuration Changes: Apply config changes separately
  • Testing: Test upgrade path in staging first
  • Timing: Schedule during low-traffic periods
The most common mistake is rushing the update by not waiting for rebalancing between nodes. Always check the Ignite version compatibility matrix before upgrading. Some major version changes may require a full cluster restart rather than a rolling update. Test the exact upgrade path in a staging environment first.

Troubleshooting Guide

Common Issues and Solutions

This section covers the most common production issues we see in real deployments. Knowing these patterns and their solutions will save significant debugging time. Encourage students to bookmark these slides for reference during production incidents.

Issue: Node Cannot Join Cluster

Symptoms: Node starts but doesn't discover others, segmentation errors
Solutions:
  • Check network connectivity between nodes
  • Verify discovery configuration matches
  • Open firewall ports: 47500-47509, 47100
  • Ensure consistent cluster configuration
  • Check for IP address conflicts
Discovery failures are the number one issue in new deployments. The first thing to check is whether nodes can reach each other on ports 47500-47509. Firewall rules and network segmentation are the most common culprits. Also verify that all nodes use the same discovery configuration and consistent cluster settings.

Issue: Out of Memory Errors

Symptoms: OutOfMemoryError, node crashes, slow performance
Solutions:
  • Increase heap size: -Xms4g -Xmx4g
  • Review data region configuration
  • Enable eviction policies
  • Check for memory leaks (heap dump analysis)
  • Monitor GC logs: -Xlog:gc*
  • Consider off-heap memory allocation
OOM errors often occur when the data region is too small for the dataset or when heap memory is not properly sized. Remember that Ignite uses both heap and off-heap memory. GC logs are essential for diagnosing whether the issue is heap pressure or data region exhaustion. Enable GC logging from day one in production.

Issue: Slow Query Performance

Symptoms: Queries taking too long, high CPU usage
Solutions:
  • Add appropriate indexes
  • Use EXPLAIN to analyze query plan
  • Avoid distributed joins (use colocation)
  • Check data colocation with affinity keys
  • Enable lazy query execution for large results
  • Review cache configuration
Slow queries are almost always caused by missing indexes or distributed joins across non-colocated data. Use EXPLAIN to see the query plan and verify that indexes are being used. Data colocation with affinity keys eliminates cross-node data movement and can improve query performance by orders of magnitude.

Diagnostic Commands

# Check cluster state and baseline
./bin/ignite.sh --baseline

# View cluster topology via REST
curl "http://localhost:8080/ignite?cmd=top"

# View cache metrics
curl "http://localhost:8080/ignite?cmd=cache&cacheName=myCache"

# Thread dump for deadlock analysis
jstack $(pgrep -f ignite) > thread-dump.txt

# Heap dump for memory analysis
jmap -dump:format=b,file=heap-dump.hprof $(pgrep -f ignite)

# GC statistics
jstat -gcutil $(pgrep -f ignite) 1000

# Check logs for errors
tail -f work/log/ignite*.log | grep -E "(ERROR|WARN)"
These diagnostic commands should be part of every operations team toolkit. Thread dumps help identify deadlocks and contention. Heap dumps reveal memory leaks. jstat provides real-time GC statistics. Encourage teams to practice running these commands before an actual incident occurs.

Log Messages to Watch

Pattern Meaning
Topology snapshot Node joined/left cluster
Rebalancing started Data redistribution in progress
Possible split brain CRITICAL: Network partition
OutOfMemory Memory exhausted
Transaction timeout Long-running transaction
Checkpoint started Persistence checkpoint
Set up log alerts for these patterns in your monitoring system. The split brain message is the most critical and requires immediate attention. Topology snapshot messages help track cluster membership changes. Transaction timeout messages may indicate contention or deadlocks that need investigation.

Common Port Reference

Port Purpose Firewall
47500-47509 Discovery Internal only
47100 Communication Internal only
10800 Thin clients Client access
8080 REST API Admin/monitoring
11211 Memcached If enabled
Keep this port reference handy for firewall configuration. Discovery and communication ports should only be open within the cluster network. Thin client and REST ports can be exposed to application servers. The Memcached port is only needed if you are using the Memcached protocol compatibility layer.

Production Readiness Checklist

Are You Ready for Production?

This checklist consolidates everything we have covered in this module and the entire course. Walk through each category and have students assess their own readiness. Any unchecked item represents a risk that should be addressed before going to production.

Security Checklist

  • Authentication enabled and tested
  • SSL/TLS configured for all communication
  • Firewall rules configured
  • Audit logging enabled
  • Regular security updates scheduled
  • Credentials stored securely
  • Network policies defined (Kubernetes)
Security is the first gate. Do not proceed to production without every item checked. Authentication and SSL/TLS are the minimum baseline. Audit logging is required for compliance in most regulated industries. Credential rotation should be automated wherever possible.

High Availability Checklist

  • Minimum 3 nodes deployed
  • Backup copies configured (1-2 backups)
  • Cross-datacenter setup (if required)
  • PodDisruptionBudget configured (K8s)
  • Anti-affinity rules for pod placement
  • Health probes configured
  • Baseline topology documented
High availability requires planning. Three nodes is the minimum for fault tolerance with one backup copy. PodDisruptionBudgets and anti-affinity rules prevent Kubernetes from placing all Ignite pods on the same physical node, which would create a single point of failure.

Performance Checklist

  • JVM properly tuned
  • Memory regions sized appropriately
  • Indexes created for frequent queries
  • Affinity keys used for colocation
  • GC logs enabled
  • Baseline performance metrics captured
  • Load testing completed
Performance tuning should be validated with realistic load tests before production. Capture baseline metrics so you can detect regressions later. Indexes and affinity keys are the two highest-impact optimizations. GC logs should be enabled from the start since they add negligible overhead.

Monitoring Checklist

  • Metrics collection enabled (JMX/Prometheus)
  • Alerting configured for critical events
  • Log aggregation in place
  • Dashboards created
  • Disk space monitoring
  • Network latency monitoring
  • Query performance tracking
Monitoring without alerting is just watching. Configure alerts for disk space, memory usage, long GC pauses, and topology changes. Dashboards should be available to the operations team before go-live. Query performance tracking helps identify slow queries before they become user-facing issues.

Operations Checklist

  • Backup procedures tested
  • Recovery procedures documented and tested
  • Rolling update procedure defined
  • Troubleshooting guide available
  • Runbooks created for common scenarios
  • On-call rotation established
  • Escalation paths defined
Operations readiness is about people and processes, not just technology. Tested recovery procedures give confidence during incidents. Runbooks reduce mean time to recovery by providing step-by-step instructions. On-call rotations and escalation paths ensure someone is always available to respond.

Documentation Checklist

  • Architecture documented
  • Configuration files version controlled
  • Operations procedures documented
  • Contact information available
  • Change management process defined
  • Capacity planning documented
  • SLAs defined and agreed
Documentation is often the last thing teams think about but is critical for long-term maintainability. Configuration files must be version controlled so changes can be tracked and rolled back. Capacity planning documentation helps with future scaling decisions and budget requests.

Final Go-Live Checklist

Ready for Production When:
  • All security controls implemented
  • HA and DR tested successfully
  • Performance benchmarks met
  • Monitoring and alerting operational
  • Team trained on operations
  • Runbooks reviewed and approved
  • Stakeholder sign-off obtained
This is the final gate. All previous checklists feed into this one. Getting stakeholder sign-off ensures that business owners understand the deployment risks and accept the current state of readiness. If any checklist category has gaps, document them as accepted risks with a remediation timeline.
