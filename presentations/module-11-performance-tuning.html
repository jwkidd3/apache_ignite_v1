Section 1: JVM Tuning

Optimizing the Java Virtual Machine for Ignite Workloads

JVM tuning is the foundation of Ignite performance. Even perfectly written application code will perform poorly with bad JVM settings. The key areas are heap sizing, garbage collector selection, and off-heap memory configuration. Ask students about their current JVM configurations to gauge their familiarity.

JVM Tuning Overview

Proper JVM configuration is critical for Ignite performance
  • Heap Size - Memory for Java objects and metadata
  • Garbage Collection - Minimize pause times
  • Off-Heap Memory - Native memory for data storage
  • Thread Pools - Concurrent processing capacity
These four areas interact with each other. Heap size affects GC behavior. Off-heap reduces GC pressure but needs its own sizing. Thread pools determine how many operations can execute concurrently. Getting any one of these wrong can bottleneck the entire system. We will address each in detail.

Heap Size Configuration

Rules of Thumb

  • 60-70% of available RAM for Ignite
  • Set -Xms equal to -Xmx
  • Reserve memory for off-heap and OS
Example: 32GB RAM
Heap: 20GB | Off-Heap: 10GB | OS: 2GB 
# Heap Configuration
HEAP_SIZE="-Xms4g -Xmx4g"

# Why equal values?
# - Avoids heap resizing
# - Predictable memory usage
# - Reduces GC overhead
Setting Xms equal to Xmx is one of the most important JVM tuning tips. Without this, the JVM dynamically resizes the heap, which triggers full GC cycles. The 60-70% rule leaves room for off-heap data storage and the OS page cache. In the 32GB example, the split gives good balance. Adjust ratios based on your data volume and whether persistence is enabled.

G1GC: Recommended Garbage Collector

G1GC (Garbage First) is recommended for Apache Ignite due to its balance of throughput and latency 
# G1GC Configuration for Ignite
GC_SETTINGS="-XX:+UseG1GC \
  -XX:+ParallelRefProcEnabled \
  -XX:MaxGCPauseMillis=200 \
  -XX:InitiatingHeapOccupancyPercent=45 \
  -XX:G1HeapRegionSize=32m"
Parameter Purpose Recommended Value
MaxGCPauseMillis Target pause time 200-500ms
G1HeapRegionSize Region granularity 16-64MB
G1GC divides the heap into equal-sized regions and collects the regions with the most garbage first, hence the name. MaxGCPauseMillis is a target, not a guarantee, but G1 tries to meet it. InitiatingHeapOccupancyPercent controls when G1 starts concurrent marking. Setting it to 45% means GC starts early, preventing full GC pauses. ParallelRefProcEnabled speeds up reference processing.

G1GC vs Other Collectors

Collector Best For Ignite Use Case
G1GC Large heaps, balanced workloads Recommended default
ZGC Ultra-low latency (Java 15+) Real-time applications
Shenandoah Low pause times Alternative to ZGC
CMS Legacy applications Deprecated - Avoid
G1GC is the safe default for most Ignite deployments. ZGC is worth trying if you are on Java 15+ and need sub-millisecond GC pauses, for example in financial trading systems. Shenandoah provides similar benefits to ZGC and is available on some OpenJDK builds. CMS is deprecated since Java 9 and removed in Java 14 -- never use it for new deployments.

GC Logging Configuration

Java 8

# Java 8 GC Logging
GC_LOG="-Xloggc:gc.log \
  -XX:+PrintGCDetails \
  -XX:+PrintGCDateStamps \
  -XX:+PrintGCTimeStamps \
  -XX:+UseGCLogFileRotation \
  -XX:NumberOfGCLogFiles=10 \
  -XX:GCLogFileSize=100M"

Java 11+

# Java 11+ Unified Logging
GC_LOG="-Xlog:gc*:file=gc.log:\
time,uptime,level,tags:\
filecount=10,filesize=100M"
Always enable GC logging in production!
Essential for diagnosing performance issues
GC logging has virtually zero performance overhead and provides invaluable diagnostic data. The Java 8 and Java 11+ syntaxes are completely different, so make sure to use the right one. Log rotation prevents disk space issues. In production, analyze GC logs with tools like GCViewer or GCEasy to identify problematic GC patterns like frequent full GCs or long pause times.

Performance JVM Options

# Performance Settings
PERFORMANCE="-XX:+AlwaysPreTouch \
  -XX:+UseStringDeduplication \
  -XX:+DisableExplicitGC"

# Off-heap memory (for data regions)
OFF_HEAP="-XX:MaxDirectMemorySize=8g"

# Diagnostic options
DIAGNOSTIC="-XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=./heapdump.hprof"
Option Purpose
AlwaysPreTouch Pre-allocate memory at startup
UseStringDeduplication Reduce string memory usage
DisableExplicitGC Ignore System.gc() calls
AlwaysPreTouch forces the OS to commit all heap pages at startup. This avoids page faults during runtime but increases startup time. UseStringDeduplication is a G1GC feature that eliminates duplicate strings in the heap. DisableExplicitGC prevents third-party libraries from calling System.gc() and triggering unnecessary full GC pauses. HeapDumpOnOutOfMemoryError automatically creates a heap dump when the JVM runs out of memory, which is essential for post-mortem analysis.

Complete JVM Configuration

#!/bin/bash
# Heap (set equal -Xms and -Xmx)
HEAP="-Xms4g -Xmx4g"

# G1GC settings
GC="-XX:+UseG1GC -XX:MaxGCPauseMillis=200"

# Off-heap and diagnostics
OFF_HEAP="-XX:MaxDirectMemorySize=8g"

export JVM_OPTS="$HEAP $GC $OFF_HEAP"
This is the minimal production-ready JVM configuration. Copy this as a starting point and adjust the sizes based on your hardware. The 4GB heap with 8GB off-heap is suitable for a medium-sized deployment. For larger clusters, scale proportionally. Always test configuration changes with realistic load before deploying to production.

Section 2: Memory Management

Heap vs Off-Heap and Data Region Configuration

Ignite's memory architecture is different from most Java applications. It uses off-heap memory for data storage, which eliminates GC pressure from large datasets. Understanding the heap vs off-heap distinction is essential for proper configuration. This section covers how Ignite manages memory and how to configure it optimally.

Heap vs Off-Heap Memory

Heap Memory

  • Managed by JVM GC
  • Java objects and metadata
  • Ignite internals
  • Query results
Subject to GC pauses

Off-Heap Memory

  • Native memory (DirectByteBuffer)
  • Data storage (Data Regions)
  • No GC overhead
  • Controlled by Ignite
Recommended for data
The key insight is that Ignite stores your actual cache data in off-heap memory, not on the Java heap. This means even if you have 100GB of data, the GC only sees the heap objects (metadata, indexes, query results). Off-heap data is stored in Ignite's own binary format, which is more compact than Java objects. This separation is what allows Ignite to handle large data volumes without GC problems.

Why Off-Heap?

Off-heap storage eliminates GC pressure from large datasets
Aspect Heap Storage Off-Heap Storage
GC Impact High - scanned during GC None - invisible to GC
Memory Limit Limited by heap size Limited by physical RAM
Serialization Java objects Binary format (compact)
Access Speed Fast (direct reference) Slightly slower (deserialization)
This table is the core comparison. Off-heap wins on GC impact and memory limits but has a slight access speed disadvantage due to deserialization. In practice, the GC benefit far outweighs the deserialization cost, especially as data volumes grow. With 10 million entries on-heap, GC pauses can reach seconds. The same data off-heap has near-zero GC impact.

Data Region Configuration

DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// Default data region (off-heap)
DataRegionConfiguration defaultRegion = new DataRegionConfiguration();
defaultRegion.setName("Default_Region");
defaultRegion.setInitialSize(512L * 1024 * 1024);  // 512 MB
defaultRegion.setMaxSize(2L * 1024 * 1024 * 1024); // 2 GB
defaultRegion.setPageEvictionMode(DataPageEvictionMode.RANDOM_2_LRU);
defaultRegion.setEvictionThreshold(0.9);
defaultRegion.setMetricsEnabled(true);

storageCfg.setDefaultDataRegionConfiguration(defaultRegion);
cfg.setDataStorageConfiguration(storageCfg);
Data regions are Ignite's memory management units. Each region is a contiguous block of off-heap memory with its own size limits and eviction policies. The initial size is allocated at startup; the region grows to maxSize on demand. RANDOM_2_LRU eviction randomly samples two pages and evicts the less recently used one, which approximates true LRU with much lower overhead. Always enable metrics for production monitoring.

Data Region Parameters

Parameter Description Recommendation
initialSize Memory allocated at startup Start with expected baseline
maxSize Maximum memory allowed Leave room for growth
pageEvictionMode How to evict pages when full RANDOM_2_LRU for most cases
evictionThreshold When to start evicting (0-1) 0.9 (90% full)
metricsEnabled Collect region metrics true (essential for monitoring)
Walk through each parameter. Initial size determines startup memory allocation. If set too low, frequent region expansion causes overhead. If set too high, you waste memory at startup. The max size is a hard limit -- once reached, eviction kicks in or operations fail. The eviction threshold of 0.9 means eviction starts when the region is 90% full, giving a 10% buffer to avoid OOM situations.

Multiple Data Regions

DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// Hot data region (fast, smaller)
DataRegionConfiguration hotRegion = new DataRegionConfiguration();
hotRegion.setName("Hot_Region");
hotRegion.setInitialSize(256L * 1024 * 1024);   // 256 MB
hotRegion.setMaxSize(1L * 1024 * 1024 * 1024);  // 1 GB
hotRegion.setPersistenceEnabled(false);         // In-memory only

// Cold data region (larger, persistent)
DataRegionConfiguration coldRegion = new DataRegionConfiguration();
coldRegion.setName("Cold_Region");
coldRegion.setInitialSize(1L * 1024 * 1024 * 1024);  // 1 GB
coldRegion.setMaxSize(8L * 1024 * 1024 * 1024);      // 8 GB
coldRegion.setPersistenceEnabled(true);

storageCfg.setDataRegionConfigurations(hotRegion, coldRegion);
Use multiple regions to separate hot and cold data with different policies
Multiple data regions let you apply different policies to different data types. Hot data that changes frequently stays in a pure in-memory region for maximum speed. Cold or archival data goes to a persistent region that can survive restarts. You assign caches to regions in the CacheConfiguration using setDataRegionName(). This pattern is common in production for balancing performance and durability.

WAL Configuration

// WAL (Write-Ahead Log) configuration for better performance
storageCfg.setWalMode(WALMode.LOG_ONLY);
storageCfg.setWalSegmentSize(64 * 1024 * 1024);  // 64 MB

// Checkpointing
storageCfg.setCheckpointFrequency(180000);  // 3 minutes
WAL Mode Performance Durability
LOG_ONLY Best Good (async fsync)
FSYNC Moderate Best (sync fsync)
BACKGROUND Good Moderate
NONE Fastest No durability
WAL is only relevant when persistence is enabled. LOG_ONLY is the recommended mode for most production deployments. It writes to the WAL file but does not force an fsync on every write, relying on the OS to flush periodically. FSYNC forces a disk sync on every write for maximum durability but at significant performance cost. NONE disables WAL entirely -- use only for disposable data. Checkpoint frequency controls how often dirty pages are flushed to disk.

Thread Pool Configuration

// Configure thread pools based on workload
IgniteConfiguration cfg = new IgniteConfiguration();

// Public thread pool (user operations)
cfg.setPublicThreadPoolSize(Runtime.getRuntime().availableProcessors() * 2);

// System thread pool (internal operations)
cfg.setSystemThreadPoolSize(Runtime.getRuntime().availableProcessors());

// Query thread pool
cfg.setQueryThreadPoolSize(Runtime.getRuntime().availableProcessors());

// Data streamer pool
cfg.setDataStreamerThreadPoolSize(Runtime.getRuntime().availableProcessors());
Default pool sizes may cause thread starvation under high load
Thread pools control the parallelism of different operation types. The public pool handles user-submitted tasks like compute jobs and cache operations. The system pool handles internal operations like discovery and rebalancing. The query pool handles SQL query execution. Size each pool based on your workload profile. If you run heavy SQL queries alongside compute tasks, make sure both pools are adequately sized to avoid starvation.

Section 3: Performance Metrics

Monitoring Cache, Cluster, and Data Region Metrics

You cannot optimize what you do not measure. Ignite provides comprehensive metrics at the cache, cluster, and data region levels. This section covers how to enable metrics, what to monitor, and what the numbers mean. Metrics are disabled by default, so the first step is always enabling them.

Enabling Metrics

// Enable cache statistics
CacheConfiguration cfg =
    new CacheConfiguration<>("monitoredCache");
cfg.setStatisticsEnabled(true);  // Essential!

IgniteCache cache = ignite.getOrCreateCache(cfg);

// Enable data region metrics
DataRegionConfiguration regionCfg = new DataRegionConfiguration();
regionCfg.setMetricsEnabled(true);
Statistics are disabled by default. You must explicitly enable them!
This is the most common oversight in Ignite deployments. Statistics are off by default because they add a small overhead (typically less than 5%). In production, the monitoring benefit far outweighs this cost. Enable statistics on every cache and data region. You can also enable them at runtime via JMX without restarting the cluster.

Cache Metrics

CacheMetrics metrics = cache.metrics();

// Operation Counts
System.out.println("Gets: " + metrics.getCacheGets());
System.out.println("Puts: " + metrics.getCachePuts());
System.out.println("Hits: " + metrics.getCacheHits());
System.out.println("Misses: " + metrics.getCacheMisses());

// Hit Rate (crucial metric!)
System.out.println("Hit Rate: " +
    String.format("%.2f%%", metrics.getCacheHitPercentage()));

// Timing
System.out.println("Avg Get Time: " +
    String.format("%.3f ms", metrics.getAverageGetTime()));
System.out.println("Avg Put Time: " +
    String.format("%.3f ms", metrics.getAveragePutTime()));
Cache metrics give you direct visibility into cache behavior. The hit rate is the single most important metric: if it is below 90%, you are likely hitting the backing store too often, which means your cache is too small or your access pattern does not benefit from caching. Average get and put times should be sub-millisecond for local operations. If they are significantly higher, investigate network issues or GC pauses.

Key Cache Metrics

Hit Ratio

Percentage of cache hits vs total accesses

Target: > 90%

Average Latency

Time for get/put operations

Target: < 1ms for local

Throughput

Operations per second

Monitor: Trends over time

Entry Count

Heap vs Off-Heap entries

Check: Memory distribution

These four metrics should be on your primary monitoring dashboard. Hit ratio below 90% indicates the cache is not effective -- either it is too small, the data is not cacheable, or the access pattern is not reusing data. Latency above 1ms for local operations suggests GC pauses or resource contention. Throughput trends reveal capacity limits before they become critical. Entry count helps verify data distribution across heap and off-heap.

Cluster Metrics

ClusterMetrics clusterMetrics = ignite.cluster().metrics();

// Cluster Performance
System.out.println("Total Nodes: " + ignite.cluster().nodes().size());
System.out.println("Total CPUs: " + clusterMetrics.getTotalCpus());
System.out.println("Current CPU Load: " +
    String.format("%.2f%%", clusterMetrics.getCurrentCpuLoad() * 100));
System.out.println("Average CPU Load: " +
    String.format("%.2f%%", clusterMetrics.getAverageCpuLoad() * 100));

// Memory
System.out.println("Heap Memory Used: " +
    clusterMetrics.getHeapMemoryUsed() / (1024 * 1024) + " MB");
System.out.println("Heap Memory Max: " +
    clusterMetrics.getHeapMemoryMaximum() / (1024 * 1024) + " MB");

// Jobs
System.out.println("Active Jobs: " + clusterMetrics.getCurrentActiveJobs());
System.out.println("Total Executed Jobs: " + clusterMetrics.getTotalExecutedJobs());
Cluster metrics provide a global view of the entire cluster. CPU load above 70% sustained indicates you may need to add nodes. Heap usage approaching the maximum suggests a need to either increase heap or optimize memory usage. Active jobs count helps identify if the compute grid is overloaded. These metrics are aggregated across all nodes, giving you a single pane of glass for cluster health.

Data Region Metrics

ignite.dataRegionMetrics().forEach(metrics -> {
    System.out.println("Region: " + metrics.getName());

    // Memory Usage
    System.out.println("  Total Allocated: " +
        metrics.getTotalAllocatedSize() / (1024 * 1024) + " MB");
    System.out.println("  Physical Memory: " +
        metrics.getPhysicalMemorySize() / (1024 * 1024) + " MB");
    System.out.println("  Checkpoint Buffer: " +
        metrics.getCheckpointBufferSize() / (1024 * 1024) + " MB");

    // Page Activity
    System.out.println("  Pages Read: " + metrics.getPagesRead());
    System.out.println("  Pages Written: " + metrics.getPagesWritten());
    System.out.println("  Pages Replaced: " + metrics.getPagesReplaced());
    System.out.println("  Allocation Rate: " +
        String.format("%.2f", metrics.getAllocationRate()) + " pages/sec");
});
Data region metrics reveal off-heap memory usage patterns. Total allocated size shows how much memory the region has claimed. Physical memory size is the actual RAM usage. Pages replaced indicates eviction activity -- if this number is high, your region is too small. Allocation rate shows how fast new data is being written. A sudden spike in allocation rate could indicate a data loading operation or a memory leak in application logic.

These thresholds give you early warning before issues impact users.

Section 4: Benchmarking

Load Testing and Performance Measurement Strategies

Benchmarking is how you validate your tuning decisions. Without benchmarks, you are just guessing. This section covers best practices for writing meaningful benchmarks and interpreting results. The key is to test with realistic workloads and measure the right things.

Benchmarking Best Practices

  • Warmup phase - Let JIT compiler optimize before measuring
  • Consistent environment - Same hardware, config, data
  • Multiple iterations - Statistical significance
  • Realistic workload - Match production patterns
  • Measure what matters - Latency, throughput, percentiles
private static final int WARMUP_ITERATIONS = 1000;
private static final int TEST_ITERATIONS = 10000;
private static final int THREAD_COUNT = 10;
The warmup phase is critical because the JIT compiler optimizes hot code paths during the first few thousand executions. Measuring before warmup gives artificially slow results. Use at least 1000 warmup iterations. Run the actual benchmark multiple times and report averages and percentiles. P99 latency is more meaningful than average for production planning because it shows the worst-case experience for 1% of requests.

Atomic vs Transactional Benchmark

// Atomic Cache (faster, no transactions)
CacheConfiguration atomicCfg = new CacheConfiguration<>("atomicCache");
atomicCfg.setCacheMode(CacheMode.PARTITIONED);
atomicCfg.setAtomicityMode(CacheAtomicityMode.ATOMIC);
atomicCfg.setBackups(1);

// Transactional Cache (ACID guarantees)
CacheConfiguration txCfg = new CacheConfiguration<>("txCache");
txCfg.setCacheMode(CacheMode.PARTITIONED);
txCfg.setAtomicityMode(CacheAtomicityMode.TRANSACTIONAL);
txCfg.setBackups(1);
Atomic operations are typically 2-10x faster than transactional
This benchmark compares the two atomicity modes. Atomic mode provides single-operation atomicity and is faster because it avoids the overhead of transaction coordination. Transactional mode provides multi-operation ACID guarantees with pessimistic or optimistic locking. The 2-10x performance difference depends on the operation mix and contention level. Use atomic mode unless you specifically need multi-key transactions.

Batch Operations Benchmark

// Individual operations (slow)
long startTime = System.currentTimeMillis();
for (int i = 0; i < TEST_ITERATIONS; i++) {
    cache.put(i, "Value-" + i);
}
long individualTime = System.currentTimeMillis() - startTime;

// Batch operations (fast!)
cache.clear();
startTime = System.currentTimeMillis();
Map batch = new HashMap<>();
for (int i = 0; i < TEST_ITERATIONS; i++) {
    batch.put(i, "Value-" + i);
    if (batch.size() >= 500) {
        cache.putAll(batch);  // Batch write
        batch.clear();
    }
}
long batchTime = System.currentTimeMillis() - startTime;

System.out.println("Speedup: " + (float)individualTime / batchTime + "x");
This is one of the most impactful benchmarks students will run. Each individual put requires a network round trip to the primary node and potentially to backup nodes. With 10000 operations, that is 10000 round trips. The batch version sends 500 entries at once, reducing network round trips by 500x. The batch size of 500 is a good default; larger batches save more round trips but use more memory for the batch map.

Batch Operations: Results

Batch operations can provide 10-100x speedup over individual operations
Operation Individual Batch (500) Speedup
10,000 PUTs ~500ms ~50ms 10x
10,000 GETs ~300ms ~30ms 10x
Key Insight: Reduce network round trips with batch APIs
These numbers are representative of a local cluster. In a production cluster with network latency, the speedup can be even greater. The fundamental principle is reducing network round trips. Every individual operation requires at least one network hop. Batch operations amortize that cost across hundreds of entries. This is the single most impactful optimization most developers can make.

Concurrent Access Benchmark

ExecutorService executor = Executors.newFixedThreadPool(THREAD_COUNT);
AtomicLong operations = new AtomicLong(0);
Random random = new Random();

long startTime = System.currentTimeMillis();

for (int i = 0; i < THREAD_COUNT; i++) {
    executor.submit(() -> {
        for (int j = 0; j < TEST_ITERATIONS / THREAD_COUNT; j++) {
            int key = random.nextInt(10000);

            // Mix of read/write operations
            if (j % 3 == 0) {
                cache.put(key, "Updated-" + key);
            } else {
                cache.get(key);
            }
            operations.incrementAndGet();
        }
    });
}

executor.shutdown();
executor.awaitTermination(1, TimeUnit.MINUTES);

long elapsed = System.currentTimeMillis() - startTime;
System.out.println("Throughput: " + (operations.get() * 1000 / elapsed) + " ops/sec");
This benchmark tests concurrent access with a 2:1 read-to-write ratio, which is typical for many applications. Using 10 threads simulates realistic concurrency. The random key distribution ensures operations are spread across partitions. Monitor the throughput as you increase thread count to find the saturation point. Also watch CPU utilization -- if throughput stops increasing but CPU is below 80%, you may have a lock contention issue.

Benchmark Output Example

Throughput: 112,359 ops/sec
GET: 10000 operations in 45 ms

=== Benchmark 2: Transactional Cache ===

Walk through the output to highlight the key findings. Atomic is 4x faster than transactional for puts. Gets are faster than puts because they often only need to read from the primary node. Batch operations show an 11x speedup. Concurrent throughput of 64K ops/sec with 10 threads shows good scaling. Students will generate similar output in the lab and can compare their numbers against these baselines.

Section 5: Common Anti-Patterns

Performance Mistakes to Avoid

This section covers the most common performance mistakes we see in production Ignite deployments. Each anti-pattern shows the wrong approach alongside the correct one. These are lessons learned from real-world production issues, and avoiding them can save significant debugging time.

Anti-Pattern 1: Small Heap, Large Off-Heap

Wrong

-Xmx1g (heap)
with 10GB off-heap

GC overhead, metadata needs heap space

Correct

-Xmx4g (heap)
with 10GB off-heap

Proportional heap for metadata

Rule: Heap should be at least 20-30% of off-heap size
Even though data is stored off-heap, Ignite still needs heap memory for metadata, index structures, query processing, and internal bookkeeping. With 10GB of off-heap data and only 1GB of heap, the heap fills up with metadata and triggers constant GC cycles. The 20-30% rule is a good starting point. Monitor heap usage and adjust if needed. For query-heavy workloads, you may need even more heap for intermediate query results.

Anti-Pattern 2: Too Many Backups

Wrong

cfg.setBackups(3);
// In a 4-node cluster

4x memory usage, 4x write overhead

Correct

cfg.setBackups(1);
// or setBackups(2)

Balanced redundancy and performance

Each backup multiplies memory usage and network traffic
With 3 backups in a 4-node cluster, every node stores a copy of every entry -- you get no partition benefit at all. Each backup copy doubles the write overhead because every put must be replicated. One backup is sufficient for most use cases: it survives a single node failure. Two backups for critical data that must survive two simultaneous failures. Three backups is almost never justified.

Anti-Pattern 3: Large Transactions

Wrong

tx.begin();
for (int i = 0; i < 10000; i++) {
    cache.put(i, value);
}
tx.commit();

Lock contention, memory pressure

Correct

for (int batch = 0; batch < 100; batch++) {
    tx.begin();
    // 100 ops per transaction
    cache.putAll(batchData);
    tx.commit();
}
Large transactions hold locks on many keys simultaneously, blocking other operations and consuming memory for the transaction log. A 10000-entry transaction can hold thousands of locks across multiple nodes. Breaking it into smaller batches of 100 entries reduces lock contention dramatically. Each small transaction commits quickly, freeing locks for other operations. Combine with putAll for even better performance.

Anti-Pattern 4: Synchronous Loops

Wrong

for (Integer key : keys) {
    cache.put(key, value);
}
// 1000 network round trips!

Correct

Map data = new HashMap<>();
for (Integer key : keys) {
    data.put(key, value);
}
cache.putAll(data);
// Single network operation!
Use putAll(), getAll(), invokeAll() for batch operations
This is the single most common performance anti-pattern. It appears in nearly every first-time Ignite deployment. Each cache.put in the loop is a synchronous network call. With 1000 keys, you get 1000 round trips. Using putAll sends all entries in one network message. The performance difference is dramatic -- typically 10-100x faster. Review all loops over cache operations in your codebase and convert them to batch equivalents.

Anti-Pattern 5: No Affinity Keys

Wrong

// Orders on random nodes
// Customers on different nodes
// Distributed joins required

Correct

class OrderKey {
    @AffinityKeyMapped
    private int customerId;
    private int orderId;
}
// Colocated data = local joins
Distributed joins are 10-100x slower than colocated joins
Without affinity keys, related data like customers and their orders end up on different nodes. Joining them requires sending data across the network. With @AffinityKeyMapped, orders are stored on the same node as their customer, making joins local and fast. Design your data model for colocation from the start. Retrofitting affinity keys later requires data migration. This is one of the most impactful design decisions you can make.

Anti-Pattern 6: Missing Indexes

Wrong

SELECT * FROM Customer
WHERE name = 'John'
-- Full table scan!

Correct

CREATE INDEX idx_name
ON Customer(name);

SELECT * FROM Customer
WHERE name = 'John'
-- Index lookup
Use EXPLAIN to verify query plans use indexes
SQL queries without indexes perform full table scans, which means reading every entry in the cache. With millions of entries, this is extremely slow. Always create indexes for columns used in WHERE clauses, JOIN conditions, and ORDER BY clauses. Use EXPLAIN to verify the query planner is using your indexes. Be selective with indexes though -- each index consumes memory and slows down writes.

Anti-Pattern 7: Overusing Distributed Joins

Wrong

// Enable everywhere
SqlFieldsQuery query = new SqlFieldsQuery(
    "SELECT * FROM A JOIN B ON ...")
    .setDistributedJoins(true);

Correct

// Design for colocation first
// Use affinity keys
// Only enable when necessary
// Consider data denormalization
Distributed joins send data between nodes to perform the join operation. This is expensive in terms of network bandwidth and latency. The correct approach is to design your data model so that related data is colocated using affinity keys, making joins local. Only enable distributed joins as a last resort when colocation is not possible. Also consider denormalization -- storing redundant data to avoid joins entirely.

More Anti-Patterns

Anti-Pattern Problem Solution
No GC Monitoring Hidden performance issues Enable and analyze GC logs
Default Thread Pools Thread starvation under load Tune pools for workload
Ignoring Metrics Can't identify bottlenecks Enable statistics, monitor
Large Objects Serialization overhead Optimize object size
These additional anti-patterns are less dramatic individually but compound over time. No GC monitoring means you cannot diagnose the most common cause of latency spikes. Default thread pools work for demos but not production loads. Ignoring metrics means flying blind. Large objects (megabytes per entry) cause slow serialization and increased network traffic. Keep cache entries small and focused -- ideally under 10KB each.

Performance Checklist

JVM Configuration

  • Heap size = 60-70% of RAM
  • -Xms equals -Xmx
  • G1GC enabled
  • GC logs configured
  • Off-heap memory sized

Application Design

  • Batch operations used
  • Affinity keys configured
  • Indexes created for queries
  • Statistics enabled
  • Thread pools tuned
Use this checklist before going to production. Every unchecked item represents a potential performance issue. The left column covers infrastructure concerns that operations teams handle. The right column covers application design concerns that developers handle. Both sides must be addressed for optimal performance. Common Issues and Solutions

Issue Cause Solution
High GC Overhead Small heap, large data Increase heap, use off-heap
Poor Hit Ratio Wrong cache sizing Review eviction, increase size
Slow Queries Missing indexes Add indexes, check EXPLAIN
High Latency Network round trips Use batch operations
Memory Pressure Too many backups Reduce backup count
This troubleshooting guide covers the top five performance issues. For high GC overhead, check GC logs for full GC frequency and pause duration. For poor hit ratio, look at eviction metrics to see if data is being evicted too aggressively. For slow queries, always run EXPLAIN first. For high latency, profile your application to find synchronous loops. For memory pressure, calculate your actual memory needs: data size times (1 + backup count).
