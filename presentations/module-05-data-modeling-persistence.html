Section 1

Data Models in Apache Ignite

15 minutes
This section introduces the three primary ways to model data in Ignite. Students often come from a relational background, so connect each model to concepts they already know. The key takeaway is that Ignite is flexible and you choose the model that fits your use case.

Data Model Overview

Apache Ignite supports multiple data modeling approaches:

Key-Value

  • Simple and fast
  • Direct cache access
  • POJO support

Binary Objects

  • Schema evolution
  • No class deployment
  • Field-level access

SQL Tables

  • ANSI SQL support
  • Familiar interface
  • JDBC/ODBC drivers
Emphasize that all three models coexist in Ignite and can even be used on the same data simultaneously. Key-Value is the simplest and fastest, Binary Objects add flexibility without class deployment, and SQL provides a familiar query interface. Ask students which model they think fits their projects.

Key-Value Data Model

Characteristics

  • Primary storage paradigm
  • Keys and values are objects
  • Automatic serialization
  • JCache (JSR-107) compliant
// Key-Value operations
IgniteCache<Integer, Customer> cache =
    ignite.getOrCreateCache("customers");

// Put and Get
cache.put(1, new Customer(1, "John"));
Customer c = cache.get(1);

// Atomic operations
cache.putIfAbsent(2, newCustomer);
The Key-Value model is the foundation of Ignite. Highlight that it is JCache compliant so students with JSR-107 experience will find it familiar. The code shows basic put/get and atomic putIfAbsent operations. Mention that keys determine data placement across the cluster, which leads into the affinity discussion later.

Creating Domain Classes

public class Customer implements Serializable {
    private Integer customerId;
    private String name;
    private String email;

    public Customer() {}

    public Customer(Integer id, String name, String email) {
        this.customerId = id;
        this.name = name;
        this.email = email;
    }
    // Getters and setters...
}
Important: Domain classes must implement Serializable
Walk through the domain class structure. Stress the Serializable requirement as students frequently forget it and get confusing errors. Also mention that equals() and hashCode() should be implemented on key classes. A common student question is whether they need a no-arg constructor -- yes, for deserialization.

Binary Objects

Advantages

  • Schema evolution
  • No class deployment needed
  • Field-level access
  • Language agnostic
// Access as binary
IgniteCache<Integer, BinaryObject> cache =
    myCache.withKeepBinary();

// Create and store
BinaryObject obj = ignite.binary()
    .builder("Customer")
    .setField("id", 1)
    .setField("name", "John")
    .build();
cache.put(1, obj);
Binary Objects are powerful for schema evolution scenarios. The key advantage is that you do not need to deploy classes to server nodes. Highlight the withKeepBinary() call which switches the cache view to binary mode. This is commonly used in compute tasks running on server nodes that do not have the domain classes on their classpath.

SQL Tables

public class Customer implements Serializable {
    @QuerySqlField(index = true)
    private Integer customerId;

    @QuerySqlField
    private String name;

    @QuerySqlField(index = true)
    private String email;
}
@QuerySqlField exposes fields to SQL. Add index = true for indexed columns.
This shows the annotation-based approach to making fields queryable via SQL. Students should understand that without @QuerySqlField, the field exists in the cache but is invisible to SQL queries. The index=true parameter creates a B+ tree index which is critical for query performance. This will be explored further in Module 06.

SQL Table Creation via DDL

CREATE TABLE Customer (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255)
) WITH "template=partitioned, backups=1";

INSERT INTO Customer VALUES (1, 'John', 'john@example.com');
SELECT * FROM Customer WHERE name = 'John';
Access via: JDBC, ODBC, thin client, REST API
DDL-based table creation is the alternative to annotation-based configuration. This approach is useful when you want to create tables dynamically or when using Ignite primarily as a SQL database. The WITH clause controls partitioning and backup settings. You can demo this in the Ignite SQL command line tool if time permits.

Choosing a Data Model

Criterion Key-Value Binary SQL
Performance Fastest Fast Good
Schema Evolution Redeploy Dynamic ALTER
Best For Simple cache Heterogeneous Complex queries
Use this comparison table to help students decide which model to use. The most common choice is Key-Value with SQL annotations for querying. Binary Objects shine in polyglot environments or when schema changes frequently. Ask students about their production scenarios and help them map to the right model.

Section 2

Affinity and Colocation

10 minutes
Affinity and colocation is arguably the most important concept in this entire course for production performance. If students take away one thing from the data modeling module, it should be this section. Everything about distributed joins, compute tasks, and query performance depends on getting colocation right.

What is Affinity?

Definition

Affinity is the mechanism that determines which node stores a particular cache entry.

  • Based on key hash function
  • Consistent hashing algorithm
  • Predictable data location
  • Even distribution across nodes
   Affinity Function
        |
        v
+-------+-------+
|  Key Hash     |
+-------+-------+
        |
        v
+-------+-------+
| Partition ID  |  (0 to 1023)
+-------+-------+
        |
        v
+-------+-------+
| Primary Node  |
+-------+-------+
Walk through the affinity diagram step by step. The key hash determines a partition number between 0 and 1023, and each partition is assigned to a primary node. This is how Ignite knows exactly where every piece of data lives without scanning. Students often ask if they can control the affinity function -- yes, but the default RendezvousAffinityFunction works well for most cases.

Why Colocation Matters

Without Colocation:                    With Colocation:
+--------+     +--------+              +--------+
| Node 1 |     | Node 2 |              | Node 1 |
|--------|     |--------|              |--------|
|Cust #1 |---->|Order#1 |              |Cust #1 |
|        | NET |Order#2 |              |Order#1 |
+--------+     +--------+              |Order#2 |
                                       +--------+
    Network overhead!                  Local access!
Colocation ensures related data lives on the same node, enabling:
  • Efficient distributed joins (no network round-trips)
  • Co-located computations
  • Reduced latency for related data access
This diagram is critical for understanding why colocation matters. Without colocation, a join between Customer and Order requires network hops. With colocation, both records are on the same node so the join is local and fast. Draw this on a whiteboard if possible. Ask students what happens to performance when every query requires network round-trips across nodes.

Colocation: THE Design Decision

In ANY distributed system, colocation determines performance:

System Mechanism
Apache Ignite @AffinityKeyMapped
Redis Cluster {hash_tag}
Cassandra / DynamoDB Partition Key
Get colocation wrong = network latency on every query.
This slide reinforces that colocation is a universal distributed systems concept, not just an Ignite thing. Students coming from Redis, Cassandra, or DynamoDB will recognize the parallel. The key point is that every distributed data system requires you to think about data placement. Getting it wrong means every query pays a network penalty.

Implementing Affinity Keys

public class Order implements Serializable {
    private Integer orderId;

    @AffinityKeyMapped  // Orders go to same node as Customer
    private Integer customerId;

    private String product;
    private Double amount;
}
@AffinityKeyMapped uses customerId for node placement.
This is the most practical slide in the colocation section. The @AffinityKeyMapped annotation tells Ignite to use the customerId field for partition assignment, so Orders land on the same node as their parent Customer. Highlight that without this annotation, Orders would be distributed by their own orderId and likely land on different nodes.

Verifying Colocation

Affinity<Integer> custAff = ignite.affinity("customers");
Affinity<Integer> orderAff = ignite.affinity("orders");

ClusterNode custNode = custAff.mapKeyToNode(1);
ClusterNode orderNode = orderAff.mapKeyToNode(101);

boolean colocated = custNode.equals(orderNode);
System.out.println("Colocated: " + colocated);
This code demonstrates how to programmatically verify colocation using the Affinity API. This is a great technique for unit tests and debugging. In the lab, students will implement similar verification. Emphasize that verifying colocation should be part of integration testing before going to production.

AffinityKey Wrapper Class

// Use AffinityKey for composite keys
IgniteCache<AffinityKey<Integer>, Order> cache =
    ignite.getOrCreateCache("orders");

AffinityKey<Integer> key = new AffinityKey<>(orderId, customerId);
cache.put(key, order);
@AffinityKeyMapped - affinity in value class
AffinityKey - composite keys
AffinityKey is the wrapper class approach for when you need composite keys. The first parameter is the actual key, the second is the affinity key used for partition assignment. Use @AffinityKeyMapped when the affinity field is inside your domain object, and AffinityKey when you need an explicit composite key outside the object.

Colocation Best Practices

Do

  • Colocate parent-child data
  • Use consistent key types
  • Verify with tests

Avoid

  • Changing keys post-deploy
  • Complex objects as keys
  • Over-colocating
Review these best practices with the class. The most common mistake is changing affinity keys after deployment, which causes data to redistribute. Also caution against using complex objects as keys since hashCode behavior must be consistent. Over-colocating means forcing too many unrelated caches to colocate, which creates hotspots.

Section 3

Native Persistence Configuration

15 minutes
Now we shift from data modeling to persistence. This section covers how Ignite stores data durably on disk. Students should understand this is optional -- Ignite works perfectly as an in-memory-only cache. Persistence is for when Ignite is your primary data store or when you cannot tolerate cold-start data loading times.

Native Persistence Overview

What is Native Persistence?

Ignite Native Persistence is a distributed, ACID-compliant, and SQL-compatible disk store.

  • Data survives cluster restarts
  • Automatic page-based storage
  • RAM + Disk tiered storage
  • Full ACID transactions
  • Instant cluster restarts
+---------------------------+
|      Application          |
+---------------------------+
            |
            v
+---------------------------+
|   In-Memory Data (RAM)    |
|   Hot Data / Indexes      |
+---------------------------+
            |
            v
+---------------------------+
|   Native Persistence      |
|   (Disk Storage)          |
|   - Data Pages            |
|   - Write-Ahead Log       |
+---------------------------+
Walk through the tiered architecture diagram. Data lives in RAM for fast access and is also persisted to disk. The key benefit is instant cluster restarts -- data does not need to be reloaded from an external source. Mention that Ignite can store datasets larger than available RAM by paging data in and out from disk automatically.

When NOT to Use Native Persistence

Scenario Better Approach
Data exists in OLTP database Use Ignite as pure cache layer
Cache can be rebuilt from source In-memory only + warm-up
Small dataset (<10GB) Reload from source on startup
Kubernetes/ephemeral infra Stateless Ignite + external source
Use Persistence when: Ignite IS your primary store, or warm-up time is unacceptable.
This is an important slide because students often enable persistence when they do not need it. If their data already lives in an OLTP database and Ignite is just a caching layer, persistence adds unnecessary complexity and disk I/O. Walk through each scenario and ask students which applies to their use case. The Kubernetes point is especially relevant for modern deployments.

Configuring Native Persistence

IgniteConfiguration cfg = new IgniteConfiguration();

// Configure data storage
DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// Create persistent data region
DataRegionConfiguration persistentRegion = new DataRegionConfiguration();
persistentRegion.setName("Persistent_Region");
persistentRegion.setPersistenceEnabled(true);          // Enable persistence
persistentRegion.setInitialSize(100L * 1024 * 1024);   // 100 MB initial
persistentRegion.setMaxSize(500L * 1024 * 1024);       // 500 MB max

storageCfg.setDefaultDataRegionConfiguration(persistentRegion);

// Configure storage paths
storageCfg.setStoragePath("./ignite-data");
storageCfg.setWalPath("./ignite-wal");
storageCfg.setWalArchivePath("./ignite-wal-archive");

cfg.setDataStorageConfiguration(storageCfg);
Walk through each configuration option in this code. The three path settings are critical: storagePath for data files, walPath for the active write-ahead log, and walArchivePath for archived WAL segments. In production, these should be on separate physical disks for performance. The initial and max size settings control the off-heap memory region.

<bean class="org.apache.ignite.configuration.IgniteConfiguration">

This shows the same persistence configuration in XML format. Some organizations prefer XML configuration for operations teams who do not write Java code. Both approaches are equivalent. Point out the SpEL expression syntax for memory sizes. Students will use the Java API approach in the lab exercises.

Cluster Activation

Important: Persistent clusters require explicit activation before use! 
try (Ignite ignite = Ignition.start(cfg)) {
    // Check and activate cluster
    if (ignite.cluster().state() != ClusterState.ACTIVE) {
        System.out.println("Activating cluster...");
        ignite.cluster().state(ClusterState.ACTIVE);
    }

    System.out.println("Cluster state: " + ignite.cluster().state());

    // Now you can use caches
    IgniteCache<Integer, String> cache =
        ignite.getOrCreateCache("persistentCache");
}
Cluster States:
  • INACTIVE - Cluster is stopped, no operations allowed
  • ACTIVE - Full functionality enabled
  • ACTIVE_READ_ONLY - Read operations only
Cluster activation is a common gotcha for students. When persistence is enabled, the cluster starts in INACTIVE state and you must explicitly activate it before any cache operations work. Explain the three states: INACTIVE blocks everything, ACTIVE enables full operations, and ACTIVE_READ_ONLY is useful for maintenance. In the lab, students will see the activation step firsthand.

Data Recovery in Action

// Create persistent cache
CacheConfiguration<Integer, String> cacheCfg =
    new CacheConfiguration<>("persistentCache");
cacheCfg.setDataRegionName("Persistent_Region");

IgniteCache<Integer, String> cache = ignite.getOrCreateCache(cacheCfg);

// Check if data already exists (from previous run)
if (cache.size() > 0) {
    System.out.println("Data recovered from disk!");
    System.out.println("Cache size: " + cache.size());
    System.out.println("Sample data: " + cache.get(1));
} else {
    System.out.println("No existing data. Creating new data...");
    for (int i = 1; i <= 100; i++) {
        cache.put(i, "Persistent-Value-" + i);
    }
    System.out.println("Added 100 entries to persistent cache");
    System.out.println("Restart the application to see data recovery!");
}
This is a great demo opportunity. Run the code once to populate data, stop the application, then run it again to show data recovery from disk. The cache.size() check determines whether data already exists. Students will do exactly this in the lab. Emphasize that the data survives a full JVM restart without any external database.

Native Persistence Features

Durability

  • ACID compliance
  • Crash recovery
  • No data loss
  • Point-in-time recovery

Performance

  • Memory-speed reads
  • Async disk writes
  • Page-based storage
  • Efficient caching

Scalability

  • Larger-than-RAM datasets
  • Automatic tiering
  • Linear scaling
  • Instant restarts
Summarize the three pillars of native persistence: durability through ACID compliance and crash recovery, performance through memory-speed reads with async disk writes, and scalability for datasets larger than RAM. The instant restarts feature is a major selling point compared to solutions that require full data reload on startup.

Section 4

Write-Ahead Log (WAL)

10 minutes
The WAL is a foundational concept in database systems. If students have experience with PostgreSQL, MySQL, or any RDBMS, they will recognize the concept. The WAL is what makes persistence durable -- without it, a crash between memory updates and disk writes would lose data.

Write-Ahead Log (WAL)

What is WAL?

The Write-Ahead Log records all data modifications before they are applied to disk pages.

  • Ensures durability
  • Enables crash recovery
  • Supports point-in-time restore
  • Sequential write pattern
 Write Operation Flow:

 +-------------+
 |  Modify RAM |
 +------+------+
        |
        v
 +-------------+
 | Write to WAL|  (Sequential)
 +------+------+
        |
        v
 +-------------+
 |   Success!  |
 +-------------+
        |
        v (Async)
 +-------------+
 | Checkpoint  |  (Background)
 +-------------+
Walk through the write operation flow diagram. The key insight is that the WAL write is sequential and fast, while the actual disk page update happens asynchronously during checkpointing. This means write latency is determined by WAL speed, not random disk I/O. This is why placing WAL on a fast SSD is so important for write performance.

WAL Modes

Mode Description Performance Durability
FSYNC Sync to disk on every write Slowest Highest
LOG_ONLY Write to OS buffer, no sync Fast Good
BACKGROUND Async flushing thread Faster Medium
NONE WAL disabled Fastest None 
// Configure WAL mode
storageCfg.setWalMode(WALMode.LOG_ONLY);     // Recommended for most cases
storageCfg.setWalMode(WALMode.FSYNC);        // Maximum durability
storageCfg.setWalMode(WALMode.BACKGROUND);   // Higher performance
storageCfg.setWalMode(WALMode.NONE);         // No WAL (dangerous!)
This is a critical decision point. LOG_ONLY is the recommended default for most production systems. FSYNC gives maximum durability but at a performance cost. BACKGROUND offers a middle ground. NONE should only be used for bulk data loading and then switched back. A common student question is the difference between LOG_ONLY and FSYNC -- LOG_ONLY writes to the OS buffer cache, while FSYNC forces a physical disk write.

WAL Configuration Options

DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// WAL mode
storageCfg.setWalMode(WALMode.LOG_ONLY);

// WAL segment size (default 64MB)
storageCfg.setWalSegmentSize(64 * 1024 * 1024);

// Number of WAL segments (default 10)
storageCfg.setWalSegments(10);

// WAL history size for point-in-time recovery
storageCfg.setWalHistorySize(20);

// WAL paths
storageCfg.setWalPath("./ignite-wal");
storageCfg.setWalArchivePath("./ignite-wal-archive");

// WAL compaction (reduces archive size)
storageCfg.setWalCompactionEnabled(true);
storageCfg.setWalCompactionLevel(Deflater.BEST_SPEED);
Walk through each configuration parameter. The segment size and count determine how much WAL data is kept in the active directory before archiving. WAL compaction reduces archive disk usage at the cost of CPU. The walHistorySize controls how far back point-in-time recovery can go. For the lab, students will use default values, but production tuning requires understanding these settings.

WAL Architecture

+---------------------------------------------------------------------+
|                           WAL Segments                               |
+---------------------------------------------------------------------+

   Active Segment          Work Directory              Archive
   +------------+         +------------+            +-------------+
   | Segment N  |  --->   | Segment N-1| ------>   | Segment N-2 |
   | (Current)  |  Roll   | (Filled)   | Compress  | Segment N-3 |
   +------------+         +------------+            | Segment N-4 |
                                                    +-------------+
   Written to
   sequentially                                     Used for:
                                                    - Crash recovery
   Fast writes!                                     - Point-in-time restore
                                                    - Cluster snapshots
WAL Segment Lifecycle: Active segment receives writes, filled segments move to work directory, then get archived and optionally compressed.
This diagram shows the lifecycle of WAL segments. The active segment receives writes sequentially, then rolls over to a new segment when full. Filled segments move to the archive for crash recovery and point-in-time restore. Emphasize the sequential write pattern -- this is why WAL is much faster than random disk updates. The archive grows over time so monitoring and cleanup are important.

WAL Tuning Tips

Performance Optimization

  • Use fast SSD for WAL path
  • Separate WAL disk from data disk
  • Increase segment size for write-heavy workloads
  • Enable WAL compaction for long retention

Durability Considerations

  • Use FSYNC for financial data
  • LOG_ONLY sufficient for most cases
  • BACKGROUND for analytics workloads
  • Never use NONE in production!
Warning: Disabling WAL (NONE mode) means data loss on crash. Only use for initial bulk loading, then re-enable!
These tuning tips come from real production experience. The most impactful optimization is separating the WAL disk from the data disk to avoid I/O contention. For write-heavy workloads, larger segments reduce the overhead of segment rotation. The warning about NONE mode is critical -- students may be tempted to use it for speed, but it means certain data loss on crash.

Section 5

Checkpointing

5 minutes
Checkpointing completes the persistence picture. While WAL captures individual changes, checkpointing flushes accumulated dirty pages to disk. This keeps recovery time bounded and allows old WAL segments to be freed. Keep this section brief as it is supplementary to the WAL discussion.

Checkpointing Overview

What is Checkpointing?

Checkpointing is the process of writing dirty pages from memory to disk.

  • Background process
  • Reduces WAL replay time
  • Frees WAL segments
  • Ensures durability
  Memory (Dirty Pages)
  +------------------+
  | Page 1 (dirty)   |
  | Page 2 (dirty)   |    Checkpoint
  | Page 3 (clean)   |   ----------->
  | Page 4 (dirty)   |
  +------------------+

  Disk (Data Files)
  +------------------+
  | Page 1           |
  | Page 2           |
  | Page 3           |
  | Page 4           |
  +------------------+
Explain the dirty page concept: when data is modified in memory but not yet written to disk, the page is marked dirty. Checkpointing writes these dirty pages to their correct locations in data files. This is a background process that does not block normal operations. The more frequently you checkpoint, the less WAL replay is needed during recovery.

Checkpoint Configuration

DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// Checkpoint frequency (default 3 min)
storageCfg.setCheckpointFrequency(180000);  // 3 minutes in ms

// Checkpoint page buffer size
storageCfg.setCheckpointPageBufferSize(256L * 1024 * 1024);  // 256 MB

// Number of checkpoint threads
storageCfg.setCheckpointThreads(4);

// Checkpoint write order (SEQUENTIAL or RANDOM)
storageCfg.setCheckpointWriteOrder(CheckpointWriteOrder.SEQUENTIAL);

// Lock wait time during checkpoint
storageCfg.setLockWaitTime(60000);  // 60 seconds
Checkpoint triggers: Time-based (frequency), WAL size, dirty pages ratio
The default 3-minute checkpoint frequency works for most workloads. For write-heavy systems, you may need to increase checkpoint threads. The page buffer size determines how much write buffering is available during checkpointing. Mention that checkpoints can also be triggered by WAL size thresholds, not just timers.

Checkpoint Process Flow

  Checkpoint Flow:

  1. Mark Checkpoint Start
     |
     v
  2. Copy Dirty Pages List
     |
     v
  3. Begin Writing to Disk   <-- Can be parallel with new writes
     |
     v
  4. Sync All Written Pages
     |
     v
  5. Mark Checkpoint End
     |
     v
  6. Release Old WAL Segments

  +-----------------------------------------------------------+
  | Recovery Time = Time since last checkpoint + WAL replay   |
  +-----------------------------------------------------------+

Key insight: More frequent checkpoints = faster recovery but more I/O overhead

This flow diagram shows checkpointing is a multi-step process. The key point is step 3 where disk writes happen in parallel with new application writes. The recovery time formula at the bottom is important: recovery time equals the time since the last checkpoint plus WAL replay. This is the fundamental tradeoff between checkpoint frequency and I/O overhead.

Section 6

Data Regions

5 minutes
Data regions let you create isolated memory pools with different configurations. This is useful when you have different types of data with different persistence and eviction requirements in the same cluster. Keep this section concise as it builds on the persistence concepts already covered.

Data Regions Overview

What are Data Regions?

Data regions are isolated memory areas with independent configuration.

  • Memory isolation
  • Independent persistence settings
  • Different eviction policies
  • Separate memory limits
   +---------------------------+
   |     Total RAM             |
   +---------------------------+
   |  Default Region (100MB)   |
   |  - Persistent             |
   +---------------------------+
   |  Hot Data Region (200MB)  |
   |  - In-Memory Only         |
   +---------------------------+
   |  Analytics Region (500MB) |
   |  - Persistent             |
   |  - LRU Eviction           |
   +---------------------------+
The diagram shows a typical production setup with three regions: a persistent default region for critical data, an in-memory-only region for sessions or temporary data, and an analytics region with eviction for large datasets. Each region has independent memory limits so one workload cannot starve another. This is similar to resource pools in traditional databases.

Configuring Multiple Data Regions

DataStorageConfiguration storageCfg = new DataStorageConfiguration();

// Default region - persistent
DataRegionConfiguration defaultRegion = new DataRegionConfiguration();
defaultRegion.setName("Default_Region");
defaultRegion.setPersistenceEnabled(true);
defaultRegion.setInitialSize(100L * 1024 * 1024);
defaultRegion.setMaxSize(500L * 1024 * 1024);
storageCfg.setDefaultDataRegionConfiguration(defaultRegion);

// In-memory region - no persistence
DataRegionConfiguration inMemoryRegion = new DataRegionConfiguration();
inMemoryRegion.setName("InMemory_Region");
inMemoryRegion.setPersistenceEnabled(false);
inMemoryRegion.setInitialSize(50L * 1024 * 1024);
inMemoryRegion.setMaxSize(200L * 1024 * 1024);

// Analytics region - with eviction
DataRegionConfiguration analyticsRegion = new DataRegionConfiguration();
analyticsRegion.setName("Analytics_Region");
analyticsRegion.setPersistenceEnabled(true);
analyticsRegion.setInitialSize(200L * 1024 * 1024);
analyticsRegion.setMaxSize(1024L * 1024 * 1024);
analyticsRegion.setPageEvictionMode(DataPageEvictionMode.RANDOM_2_LRU);

storageCfg.setDataRegionConfigurations(inMemoryRegion, analyticsRegion);
This code shows how to create multiple data regions with different settings. Note that one region is set as the default using setDefaultDataRegionConfiguration, while additional regions are added via setDataRegionConfigurations. The analytics region demonstrates page eviction mode which allows it to handle datasets larger than its allocated memory by evicting least recently used pages.

Assigning Caches to Data Regions

// Persistent cache - uses default region
CacheConfiguration<Integer, Customer> customerCfg =
    new CacheConfiguration<>("customers");
customerCfg.setDataRegionName("Default_Region");

// Session cache - in-memory only
CacheConfiguration<String, Session> sessionCfg =
    new CacheConfiguration<>("sessions");
sessionCfg.setDataRegionName("InMemory_Region");

// Analytics cache - with eviction
CacheConfiguration<Long, AnalyticsData> analyticsCfg =
    new CacheConfiguration<>("analytics");
analyticsCfg.setDataRegionName("Analytics_Region");

// Create caches
IgniteCache<Integer, Customer> customers = ignite.getOrCreateCache(customerCfg);
IgniteCache<String, Session> sessions = ignite.getOrCreateCache(sessionCfg);
IgniteCache<Long, AnalyticsData> analytics = ignite.getOrCreateCache(analyticsCfg);
This shows the practical step of assigning caches to specific data regions via setDataRegionName. If you do not specify a region, the cache uses the default region. This is a common pattern: customer data in the persistent region, user sessions in the in-memory region, and analytics data in the evictable region. Students will configure this in the lab.

Data Region Eviction Policies

Policy Description Use Case
DISABLED No eviction Critical data that must stay in memory
RANDOM_LRU Random sampling with LRU General purpose, good performance
RANDOM_2_LRU Two random samples, evict LRU Better accuracy, slightly slower 
// Configure eviction
DataRegionConfiguration region = new DataRegionConfiguration();
region.setName("Evictable_Region");
region.setPageEvictionMode(DataPageEvictionMode.RANDOM_2_LRU);
region.setEvictionThreshold(0.9);  // Start evicting at 90% full
RANDOM_2_LRU is the recommended eviction policy for most cases. It samples two random pages and evicts the least recently used one, giving a good approximation of true LRU with minimal overhead. The eviction threshold of 0.9 means eviction starts when the region is 90% full. A common question is whether eviction causes data loss -- with persistence enabled, evicted pages can be read back from disk.

Storage Configuration Best Practices

Disk Layout

  • Separate disks for data and WAL
  • Use SSDs for WAL path
  • RAID-10 for data storage
  • Avoid network storage for WAL

Sizing

  • Plan for 2x data size growth
  • WAL archive needs ~10x segment size
  • Monitor disk usage regularly
  • Set memory limits appropriately
Recommended Disk Layout:
/data/ignite-storage   - Data files (SSD or fast HDD)
/wal/ignite-wal        - Active WAL (Fast SSD)
/archive/ignite-wal    - WAL archive (Can be slower storage)
The disk layout recommendation is crucial for production. Separating WAL from data files eliminates I/O contention between sequential WAL writes and random data page writes. SSD for WAL is a high-impact investment. The sizing guidelines help prevent running out of disk space, which is a common production incident. Show the recommended layout at the bottom of the slide.

Memory Configuration Best Practices

// Production memory configuration
DataRegionConfiguration region = new DataRegionConfiguration();
region.setName("Production_Region");
region.setPersistenceEnabled(true);

// Memory sizing
long totalRam = 32L * 1024 * 1024 * 1024;  // 32 GB total
long igniteHeap = 8L * 1024 * 1024 * 1024;  // 8 GB for JVM heap
long offHeapMax = totalRam - igniteHeap - (2L * 1024 * 1024 * 1024);  // Leave 2GB for OS

region.setInitialSize(offHeapMax / 2);  // Start at 50%
region.setMaxSize(offHeapMax);           // Max available

// Enable metrics for monitoring
region.setMetricsEnabled(true);

// Memory policy
region.setPageEvictionMode(DataPageEvictionMode.RANDOM_2_LRU);
region.setEvictionThreshold(0.9);  // Evict at 90%
Rule of thumb: JVM Heap + Off-Heap + 2GB (OS) should not exceed total RAM
Memory sizing is one of the most common sources of production issues. Walk through the calculation: total RAM minus JVM heap minus OS reserve equals available off-heap. The rule of thumb formula at the bottom is critical. If you exceed total RAM, the OS will swap and performance will collapse. Enable metrics so you can monitor actual usage and adjust over time.

Cache Store Patterns

Write-Through

CacheConfiguration cfg =
  new CacheConfiguration("cache");
cfg.setWriteThrough(true);
cfg.setReadThrough(true);
cfg.setCacheStoreFactory(
  () -> new MyCacheStore());

Synchronous writes to DB

Write-Behind

cfg.setWriteBehindEnabled(true);
cfg.setWriteBehindFlushSize(1000);
cfg.setWriteBehindFlushFrequency(5000);
cfg.setWriteBehindBatchSize(100);

Async batched writes

When to use:
  • Native Persistence: Ignite as primary store, full ACID
  • Write-Through: Immediate consistency with external DB
  • Write-Behind: High-throughput writes, eventual consistency
Cache store patterns are the alternative to native persistence for integrating with external databases. Write-through synchronously updates the database on every cache write, ensuring consistency. Write-behind batches writes asynchronously for much higher throughput but with eventual consistency. The choice depends on consistency requirements. Native persistence is for when Ignite is the primary store with no external DB.

Read-Through: The Safety Net

Read-through is a fallback, NOT primary sync.

Does

  • Cache miss → load from store
  • Handle cold cache startup
  • Recover from eviction

Does NOT

  • Proactively sync changes
  • Handle external DB updates
  • Guarantee freshness
Best Practice: Use CDC for proactive sync. Read-through catches what slips through.
This is a common misconception to address: read-through does NOT keep the cache in sync with the database. It only loads data on a cache miss. If the database is updated externally, the cache will serve stale data until the entry is evicted or expires. For proactive synchronization, you need Change Data Capture (CDC) or explicit invalidation. Read-through is a safety net, not a sync mechanism.
