ACID Properties

Foundation of Data Consistency

This section reviews the ACID properties that most students already know from relational databases. The key difference in Ignite is that these guarantees must be maintained across multiple nodes in a distributed cluster, which makes the implementation significantly more complex than a single-server database.

What is ACID?

A

Atomicity

All or nothing - complete success or complete rollback

C

Consistency

Data remains valid after transaction

I

Isolation

Concurrent transactions don't interfere

D

Durability

Committed data survives failures

Walk through each ACID property. Atomicity ensures a bank transfer either completes fully or not at all. Consistency means business rules like non-negative balances are always maintained. Isolation means concurrent transactions do not see each other's partial work. Durability means committed transactions survive crashes. Ask students which property they think is hardest to guarantee in a distributed system.

ACID in Distributed Systems

Challenge: Maintaining ACID across multiple nodes is complex

Traditional RDBMS

  • Single machine coordination
  • Simple lock management
  • Direct disk writes

Apache Ignite

  • Multi-node coordination
  • Distributed lock management
  • Two-Phase Commit (2PC)
The comparison between traditional RDBMS and Ignite highlights the distributed challenge. In a single-machine database, locks are just in-memory data structures. In Ignite, locks must be coordinated across the network. The Two-Phase Commit protocol is how Ignite ensures atomicity across nodes. This adds latency but guarantees correctness. Students often ask about CAP theorem implications here.

Enabling Transactions

Transactions require TRANSACTIONAL atomicity mode

CacheConfiguration<Integer, Integer> cfg =
    new CacheConfiguration<>("accountCache");

// Enable transactions
cfg.setAtomicityMode(CacheAtomicityMode.TRANSACTIONAL);
cfg.setBackups(1);

IgniteCache<Integer, Integer> cache =
    ignite.getOrCreateCache(cfg);

Note: ATOMIC mode (default) does not support transactions but offers better performance for single-key operations

This is a critical configuration step. The TRANSACTIONAL atomicity mode must be set on the cache before any transactions can be used. The default is ATOMIC which provides better performance for single-key operations but does not support multi-key transactions. A common mistake is trying to use transactions on an ATOMIC cache which silently ignores the transaction boundaries. Always verify this setting in your cache configuration.

Transaction API

Working with Ignite Transactions

This section covers the practical Transaction API that students will use in the lab. The patterns shown here are the building blocks for all transactional operations in Ignite. Pay special attention to the try-with-resources pattern which ensures transactions are always properly closed.

Basic Transaction Pattern

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ)) {

    // Read current values
    int balance1 = cache.get(1);
    int balance2 = cache.get(2);

    // Perform transfer
    cache.put(1, balance1 - 200);
    cache.put(2, balance2 + 200);

    // Commit the transaction
    tx.commit();
    System.out.println("Transaction committed successfully");
}

Key Pattern: Use try-with-resources for automatic cleanup

This is the fundamental transaction pattern students will use throughout the lab. The bank transfer example reads two balances, performs the transfer, and commits atomically. The try-with-resources ensures the transaction is closed even if an exception occurs. Highlight that if commit() is not called, the transaction is automatically rolled back when the try block exits. This is a safety net against forgotten commits.

Transaction Lifecycle

txStart() - Begin transaction
Operations - Read/Write cache entries
commit() - Apply all changes atomically
rollback() - Discard all changes
close() - Clean up resources
The transaction lifecycle follows a simple flow: start, operate, then commit or rollback. The close step is handled automatically by try-with-resources. If an exception occurs between txStart and commit, the transaction is rolled back automatically on close. This matches the lifecycle pattern of database transactions that students are familiar with from JDBC.

Rollback Scenarios

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ)) {

    int balance = cache.get(1);

    // Business validation
    if (balance < 2000) {
        System.out.println("Insufficient funds!");
        tx.rollback();  // Explicit rollback
        return;
    }

    cache.put(1, balance - 2000);
    tx.commit();

} catch (Exception e) {
    // Transaction auto-rolls back on exception
    System.out.println("Transaction rolled back: " + e.getMessage());
}
This example shows two rollback scenarios: explicit rollback on business validation failure (insufficient funds) and automatic rollback on exception. The explicit rollback with return pattern is clean and readable. The catch block handles unexpected exceptions. Emphasize that after rollback, all changes made within the transaction are discarded as if they never happened.

Transaction Methods

Method Description
txStart() Start with default concurrency and isolation
txStart(concurrency, isolation) Start with specific settings
txStart(concurrency, isolation, timeout, size) Full control including timeout
commit() Apply all changes permanently
rollback() Discard all changes
close() Clean up (auto-rollback if not committed)
This reference table shows all available transaction methods. The three overloads of txStart provide increasing levels of control. The full form with timeout and size is recommended for production use. The close method is the safety net that ensures cleanup. Note that close auto-rolls back an uncommitted transaction, which is why try-with-resources works so well.

Isolation Levels

READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE

Isolation levels determine what concurrent transactions can see of each other's changes. This is one of the most misunderstood areas of database systems. Take time on each level to ensure students understand the practical implications. The recommended default is REPEATABLE_READ which provides a good balance of consistency and performance.

Isolation Level Overview

Level Dirty Read Non-Repeatable Phantom Read Performance
READ_COMMITTED Prevented Possible Possible Fastest
REPEATABLE_READ Prevented Prevented Possible Balanced
SERIALIZABLE Prevented Prevented Prevented Slowest
This table summarizes the three isolation levels and what anomalies each prevents. Dirty reads (seeing uncommitted data) are prevented by all levels. Non-repeatable reads (same query returning different values) are prevented by REPEATABLE_READ and SERIALIZABLE. Phantom reads (new rows appearing between queries) are only prevented by SERIALIZABLE. Higher isolation means lower performance due to more locking.

READ_COMMITTED

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.READ_COMMITTED)) {

    // Can see committed changes from other transactions
    Integer value1 = cache.get("key");  // Returns 100

    // Another transaction commits: key -> 200

    Integer value2 = cache.get("key");  // Returns 200 (different!)

    tx.commit();
}

Use Case: When you need performance and can tolerate reading different values within the same transaction

The READ_COMMITTED example illustrates the non-repeatable read anomaly: reading the same key twice returns different values because another transaction committed between the reads. This is acceptable for reporting queries where absolute consistency is not required. It offers the best performance because read locks are released immediately after each read operation.

REPEATABLE_READ

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ)) {

    // Consistent reads throughout transaction
    Integer value1 = cache.get("key");  // Returns 100

    // Another transaction commits: key -> 200

    Integer value2 = cache.get("key");  // Still returns 100!

    tx.commit();
}

Recommended: Best balance of consistency and performance for most applications

REPEATABLE_READ guarantees that if you read a key, reading it again in the same transaction returns the same value. This is the recommended default for business operations like bank transfers and inventory management. The read lock is held for the duration of the transaction, preventing other transactions from modifying the data you have read. This is the level students will use in most lab exercises.

SERIALIZABLE

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.OPTIMISTIC,
        TransactionIsolation.SERIALIZABLE)) {

    // Strictest isolation - prevents all anomalies
    // Validates that no conflicting changes occurred

    Integer value = cache.get("key");
    cache.put("key", value + 1);

    // At commit: validates no other transaction modified "key"
    tx.commit();  // May throw TransactionOptimisticException

} catch (TransactionOptimisticException e) {
    // Handle conflict - typically retry
}

Note: SERIALIZABLE with OPTIMISTIC requires handling potential commit failures

SERIALIZABLE provides the strongest isolation but with OPTIMISTIC concurrency it requires handling TransactionOptimisticException. The validation at commit time checks that no other transaction modified the data you read. If a conflict is detected, the transaction must be retried. This is the recommended approach for counter updates and scenarios where you need compare-and-swap semantics. The retry pattern is essential and students must implement it in the lab.

Choosing Isolation Levels

READ_COMMITTED

  • Reporting queries
  • Non-critical reads
  • High-throughput scenarios

REPEATABLE_READ

  • Financial transactions
  • Inventory management
  • Most business operations

SERIALIZABLE

  • Audit logs | Compliance-critical operations | Counter updates
This decision guide helps students choose the right isolation level. READ_COMMITTED for read-heavy, non-critical scenarios. REPEATABLE_READ for most business operations where you need consistent reads within a transaction. SERIALIZABLE for strict requirements like audit logs and counter updates. Most students should default to REPEATABLE_READ and only use the others for specific requirements.

Concurrency Modes

PESSIMISTIC vs OPTIMISTIC

Concurrency modes determine WHEN locks are acquired. This is independent of isolation levels and the two settings are orthogonal. PESSIMISTIC locks on first access which prevents conflicts but reduces concurrency. OPTIMISTIC defers locking to commit time which allows more concurrency but may require retries. This is one of the most important design decisions for transactional applications.

Concurrency Mode Comparison

Aspect PESSIMISTIC OPTIMISTIC
Lock Acquisition On first access At commit time
Conflicts Prevented by waiting Detected at commit
Deadlock Risk Higher Lower
Throughput Lower under contention Higher for reads
Best For Write-heavy workloads Read-heavy workloads
Walk through each row of the comparison table. Lock acquisition timing is the fundamental difference. PESSIMISTIC prevents conflicts by blocking, which is simpler but limits concurrency. OPTIMISTIC allows conflicts and detects them at commit, which requires retry logic. For most production systems, PESSIMISTIC with REPEATABLE_READ is the safest starting point. Only move to OPTIMISTIC if you have measured the performance benefit.

PESSIMISTIC Mode

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ)) {

    // Lock is acquired HERE on first read
    Integer value = cache.get("counter");
    System.out.println("Lock acquired, value: " + value);

    // Other transactions wait for this lock
    Thread.sleep(100);  // Processing time

    cache.put("counter", value + 1);

    tx.commit();  // Lock released
}

Behavior: Locks acquired immediately prevent other transactions from accessing the same data

In PESSIMISTIC mode, the lock is acquired on the get() call. This means other transactions trying to read or write the same key will block until this transaction commits or rolls back. The Thread.sleep simulates processing time during which the lock is held. Emphasize that longer transactions mean longer lock hold times, which is why keeping transactions short is critical for PESSIMISTIC mode.

OPTIMISTIC Mode

int maxRetries = 3;
for (int retry = 0; retry < maxRetries; retry++) {
    try (Transaction tx = ignite.transactions().txStart(
            TransactionConcurrency.OPTIMISTIC,
            TransactionIsolation.SERIALIZABLE)) {

        // No lock acquired - just read value
        Integer value = cache.get("counter");

        cache.put("counter", value + 1);

        // Lock acquired and validated HERE
        tx.commit();  // May fail if data changed
        break;  // Success - exit retry loop

    } catch (TransactionOptimisticException e) {
        if (retry == maxRetries - 1) throw e;
        // Retry the transaction
    }
}
The OPTIMISTIC retry pattern is essential to understand. Since validation happens at commit time, the commit may fail with TransactionOptimisticException if another transaction modified the same data. The retry loop with maxRetries handles this gracefully. Note that OPTIMISTIC with SERIALIZABLE is the only valid combination for optimistic conflict detection. Students must implement this retry pattern in the lab exercise.

Lock Timing Visualization

PESSIMISTIC

txStart()

|

|

put()

|

commit() - UNLOCK

OPTIMISTIC

txStart()

|

get() - no lock

|

put() - no lock

|

This side-by-side visualization makes the locking difference clear. In PESSIMISTIC, the red LOCK happens at get() time and the green UNLOCK at commit(). In OPTIMISTIC, there are no locks during operations, but commit does both LOCK and VALIDATE atomically. Draw this on a whiteboard with a timeline to show how two concurrent transactions interleave under each mode.

When to Use Each Mode

Use PESSIMISTIC When:

  • High write contention expected
  • Conflicts are likely
  • Cannot afford retry overhead
  • Long-running transactions

Use OPTIMISTIC When:

  • Read-heavy workloads
  • Low contention scenarios
  • Short transactions
  • Can implement retry logic
This decision guide summarizes when to use each mode. The rule of thumb is: if conflicts are likely (write-heavy, high contention), use PESSIMISTIC to avoid wasted work from retries. If conflicts are unlikely (read-heavy, low contention), OPTIMISTIC gives better throughput. For long-running transactions, always use PESSIMISTIC because an optimistic failure after significant processing wastes all that work.

Deadlock Detection

Prevention and Resolution

Deadlocks are a critical topic for any system using pessimistic locking. In a distributed system, deadlocks are harder to detect because the lock waits span multiple nodes. Ignite has built-in deadlock detection but prevention through consistent lock ordering is always preferable. Students will create a deadlock scenario in the lab to see the detection in action.

What is a Deadlock?

Transaction 1

Holds Lock A

Waits for Lock B

Transaction 2

Holds Lock B

Waits for Lock A

Result: Both transactions blocked forever!

Deadlocks occur with PESSIMISTIC transactions when locks are acquired in different orders

The classic deadlock: Transaction 1 holds Lock A and waits for Lock B, while Transaction 2 holds Lock B and waits for Lock A. Neither can proceed. In a distributed system this can happen across nodes, making it even harder to diagnose manually. Ignite detects this situation and automatically rolls back one of the transactions (the victim) to break the cycle.

Deadlock Scenario

// Thread 1: Lock A then B
cache.get("resource1");  // Lock A
cache.get("resource2");  // Wait for B - BLOCKED!

// Thread 2: Lock B then A
cache.get("resource2");  // Lock B
cache.get("resource1");  // Wait for A - BLOCKED!
Solution: Always lock resources in consistent order
This concrete code example shows exactly how a deadlock happens. Thread 1 locks resource1 then tries to lock resource2, while Thread 2 does the opposite. The solution is simple: both threads should lock in the same order. This is easy to say but hard to enforce in large codebases. In the lab, students will reproduce this deadlock and then fix it with consistent ordering.

Ignite's Deadlock Detection

try (Transaction tx = ignite.transactions().txStart()) {
    // operations...
    tx.commit();
} catch (TransactionDeadlockException e) {
    // Auto rolled back, implement retry
}
Resolution: Ignite detects deadlocks and rolls back victim transaction
Ignite's built-in deadlock detection automatically identifies cycles in the lock wait graph. When detected, one transaction is chosen as the victim and rolled back with TransactionDeadlockException. The application should catch this exception and retry the transaction. The detection has a timeout delay so it is not instantaneous. This is why prevention through ordering is always better than detection.

Preventing Deadlocks

Best Practice: Consistent Lock Ordering

// Both transactions acquire locks in the SAME order
Runnable safeTransaction = () -> {
    try (Transaction tx = ignite.transactions().txStart(
            TransactionConcurrency.PESSIMISTIC,
            TransactionIsolation.REPEATABLE_READ)) {

        // Always lock resource1 first, then resource2
        cache.get("resource1");  // Lock A first
        cache.get("resource2");  // Then Lock B

        // Perform operations
        tx.commit();
    }
};

// Both threads use the same lock order - no deadlock!
The key prevention strategy is consistent lock ordering. Both transactions always lock resource1 first, then resource2. This eliminates the circular dependency that causes deadlocks. In production, establish a convention like always locking in alphabetical key order or by primary key value. This is the same pattern used in database systems like PostgreSQL's advisory locks.

Deadlock Prevention Strategies

Lock Ordering

Always acquire locks in consistent order

Timeouts

Set reasonable transaction timeouts

Use OPTIMISTIC

Eliminates lock-based deadlocks

Tip: Sort keys before accessing them to ensure consistent ordering

List<String> keys = Arrays.asList("keyC", "keyA", "keyB");
Collections.sort(keys);  // Consistent order
for (String key : keys) cache.get(key);
Three prevention strategies: lock ordering eliminates circular dependencies, timeouts break deadlocks by aborting after a period, and OPTIMISTIC mode eliminates lock-based deadlocks entirely since locks are only held during the commit phase. The sorting tip at the bottom is practical -- sort your keys before accessing them to guarantee consistent order regardless of the order they were passed to your method.

Transaction Timeout

Managing Long-Running Transactions

Transaction timeouts are a safety mechanism against runaway transactions that hold locks indefinitely. Without timeouts, a stuck transaction can block other transactions and eventually cause cascading failures. Always set timeouts in production. This section covers per-transaction and default timeout configuration.

Setting Transaction Timeout

// Method 1: Per-transaction timeout
try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ,
        10000,  // 10 second timeout
        0)) {   // 0 = unlimited transaction size

    // Operations must complete within 10 seconds
    tx.commit();

} catch (TransactionTimeoutException e) {
    System.out.println("Transaction exceeded timeout!");
}
The per-transaction timeout is set as the third parameter to txStart. The value 10000 means 10 seconds. If the transaction has not committed within this time, it is automatically rolled back with TransactionTimeoutException. The fourth parameter 0 means unlimited transaction size in terms of number of entries. Students should always handle TransactionTimeoutException in their catch blocks.

Default Timeout Configuration

// Configure default timeout for all transactions
TransactionConfiguration txCfg = new TransactionConfiguration();
txCfg.setDefaultTxTimeout(30000);  // 30 seconds default
txCfg.setDefaultTxConcurrency(TransactionConcurrency.PESSIMISTIC);
txCfg.setDefaultTxIsolation(TransactionIsolation.REPEATABLE_READ);

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setTransactionConfiguration(txCfg);

Ignite ignite = Ignition.start(cfg);

// Now transactions use default settings
try (Transaction tx = ignite.transactions().txStart()) {
    // Uses 30 second timeout automatically
    tx.commit();
}
Setting default transaction configuration avoids repeating settings on every txStart call. The defaults apply to all transactions started with the no-argument txStart(). This is the recommended approach for production applications. Individual transactions can still override these defaults. Mention that the default timeout of 0 (unlimited) is dangerous in production and should always be overridden.

Timeout Best Practices

Scenario Recommended Timeout
Simple CRUD operations 5-10 seconds
Batch processing 30-60 seconds
Complex business logic 15-30 seconds
Cross-cache operations 20-45 seconds

Warning: Never use unlimited timeout (0) in production - it can cause resource exhaustion

These timeout recommendations come from production experience. Simple CRUD should complete in under 10 seconds. Batch processing may need up to 60 seconds for large batches. The warning about unlimited timeouts is critical -- in production, a stuck transaction with no timeout will hold locks forever, blocking other transactions and potentially causing cascading failures across the cluster.

Handling Timeout Exceptions

try (Transaction tx = ignite.transactions().txStart()) {
    operation.run();
    tx.commit();
} catch (TransactionTimeoutException e) {
    // Retry with exponential backoff
    Thread.sleep(100 * (long)Math.pow(2, attempt));
}
The exponential backoff retry pattern prevents thundering herd problems when many transactions time out simultaneously. Each retry waits longer: 100ms, 200ms, 400ms, and so on. This gives the system time to recover from whatever caused the timeout. In production, add jitter to the backoff to prevent synchronized retries from multiple clients.

Cross-Cache Transactions

Atomic Operations Across Multiple Caches

Cross-cache transactions are a powerful feature that allows atomic operations spanning multiple caches. The classic example is a bank transfer with an audit log: both the balance update and the audit record must succeed or fail together. This is implemented using the Two-Phase Commit protocol across nodes.

Multi-Cache Transaction Example

// Create two transactional caches
CacheConfiguration<Integer, Double> accountCfg =
    new CacheConfiguration<>("accounts");
accountCfg.setAtomicityMode(CacheAtomicityMode.TRANSACTIONAL);

CacheConfiguration<Integer, String> auditCfg =
    new CacheConfiguration<>("auditLog");
auditCfg.setAtomicityMode(CacheAtomicityMode.TRANSACTIONAL);

IgniteCache<Integer, Double> accounts = ignite.getOrCreateCache(accountCfg);
IgniteCache<Integer, String> auditLog = ignite.getOrCreateCache(auditCfg);
Both caches must be configured with TRANSACTIONAL atomicity mode. This is a prerequisite for cross-cache transactions. If either cache is ATOMIC, the transaction will not work correctly. In the lab, students will create similar dual-cache configurations for the bank transfer exercise. Remind students to verify the atomicity mode setting on all caches involved in a transaction.

Cross-Cache Transfer

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ)) {

    // Operation 1: Debit from accounts cache
    Double balance = accounts.get(fromAccount);
    if (balance < amount) {
        tx.rollback();
        throw new InsufficientFundsException();
    }
    accounts.put(fromAccount, balance - amount);

    // Operation 2: Credit to accounts cache
    Double toBalance = accounts.get(toAccount);
    accounts.put(toAccount, toBalance + amount);

    // Operation 3: Log to audit cache
    String logEntry = String.format("Transfer: %d -> %d: $%.2f",
        fromAccount, toAccount, amount);
    auditLog.put(auditId++, logEntry);

    tx.commit();  // All three operations commit atomically
}
This is a complete cross-cache transaction example. Three operations happen atomically: debit from one account, credit to another, and write an audit log entry. If any operation fails or the commit fails, all three are rolled back. The business validation (insufficient funds check) with explicit rollback is a best practice pattern. Students will implement this exact pattern in the lab.

Cross-Cache Requirements

All Caches Must:

  • Have TRANSACTIONAL atomicity mode
  • Be on the same Ignite cluster
  • Be accessible from the same transaction context

Limitations:

  • Cannot mix ATOMIC and TRANSACTIONAL caches
  • Cross-cluster transactions not supported
  • Performance overhead increases with more caches
These requirements and limitations are important to understand. All caches must be TRANSACTIONAL -- mixing ATOMIC and TRANSACTIONAL caches in a transaction is not supported and will cause undefined behavior. Cross-cluster transactions are not supported. Performance overhead increases with more caches because more nodes must participate in the Two-Phase Commit protocol.

Two-Phase Commit Protocol

How Cross-Cache Transactions Work

Phase 1: Prepare

  • Coordinator sends prepare request to all nodes
  • Each node acquires locks and prepares changes
  • Nodes vote: COMMIT or ABORT

Phase 2: Commit/Rollback

  • If all vote COMMIT: coordinator sends commit
  • If any vote ABORT: coordinator sends rollback
  • All nodes apply or discard changes
The Two-Phase Commit protocol is how Ignite ensures atomicity across nodes. In Phase 1 (Prepare), the coordinator asks all participating nodes if they can commit. Each node acquires locks and votes. In Phase 2, if all nodes voted COMMIT, the coordinator tells them to apply the changes. If any voted ABORT, all nodes roll back. This protocol adds network round-trips which is why cross-node transactions are slower than local ones.

Transaction Best Practices

Writing Efficient and Safe Transactions

This best practices section pulls together the practical lessons from the entire module. Each practice is numbered for easy reference. These recommendations come from real production experience and common mistakes. Students should bookmark this section and refer back to it when implementing transactions in their projects.

1. Keep Transactions Short

Bad Practice

try (Transaction tx = ...) {
    // Heavy computation inside tx
    String result = compute();
    cache.put(key, result);
    tx.commit();
}

Good Practice

// Compute OUTSIDE transaction
String result = compute();

try (Transaction tx = ...) {
    cache.put(key, result);
    tx.commit();
}

Principle: Do heavy work outside, only data operations inside

This is the most impactful best practice. Compute results before starting the transaction, then only do cache operations inside the transaction. The bad example shows heavy computation inside the transaction holding locks. The good example computes first, then opens a short transaction for just the put operation. This minimizes lock hold time and dramatically improves concurrency under load.

2. Use Batch Operations

try (Transaction tx = ignite.transactions().txStart(
        TransactionConcurrency.PESSIMISTIC,
        TransactionIsolation.REPEATABLE_READ)) {

    // Instead of multiple puts:
    // cache.put(1, "a");
    // cache.put(2, "b");
    // cache.put(3, "c");

    // Use putAll for better performance
    Map<Integer, String> batch = new HashMap<>();
    batch.put(1, "a");
    batch.put(2, "b");
    batch.put(3, "c");
    cache.putAll(batch);  // Single network round-trip

    tx.commit();
}
Batch operations like putAll reduce the number of network round-trips within a transaction. Instead of three separate put calls each requiring a network message, putAll sends all three in a single message. This is especially important in distributed transactions where network latency accumulates. The same principle applies to getAll for reading multiple keys. Students should use this pattern whenever they need to read or write multiple keys.

3. Proper Exception Handling

public void safeTransaction() {
    Transaction tx = null;
    try {
        tx = ignite.transactions().txStart(
            TransactionConcurrency.PESSIMISTIC,
            TransactionIsolation.REPEATABLE_READ);

        // Perform operations
        performBusinessLogic();

        tx.commit();

    } catch (TransactionOptimisticException e) {
        log.warn("Optimistic conflict - retry needed");
    } catch (TransactionDeadlockException e) {
        log.warn("Deadlock detected - will retry");
    } catch (Exception e) {
        log.error("Transaction failed", e);
    } finally {
        if (tx != null) {
            tx.close();  // Ensures cleanup, auto-rollback if not committed
        }
    }
}
This shows the comprehensive exception handling pattern for production code. Note the specific catch blocks for TransactionOptimisticException and TransactionDeadlockException before the general Exception catch. The finally block ensures the transaction is always closed. In production, each exception type should have appropriate handling: retry for optimistic conflicts and deadlocks, alert for unexpected exceptions.

4. Avoid Nested Transactions

Ignite does not support nested transactions!

// This will throw an exception!
try (Transaction tx1 = ignite.transactions().txStart()) {
    cache.put(1, "value1");

    // ERROR: Cannot start nested transaction
    try (Transaction tx2 = ignite.transactions().txStart()) {
        cache.put(2, "value2");
        tx2.commit();
    }

    tx1.commit();
}

Solution: Complete all operations in a single transaction or use separate sequential transactions

Ignite does not support nested transactions, which surprises students coming from Spring's @Transactional where nested transactions are common. If you try to start a transaction while another is active on the same thread, Ignite throws an exception. The solution is to combine all operations into a single transaction or use separate sequential transactions. Design your service layer to avoid nesting.

5. Choose Right Concurrency Mode

Workload Type Recommended Mode Reason
Read-heavy, low contention OPTIMISTIC Better throughput
Write-heavy, high contention PESSIMISTIC Avoids retry overhead
Mixed workload PESSIMISTIC More predictable
Long-running transactions PESSIMISTIC Avoids late failures
This decision table summarizes the concurrency mode recommendation based on workload type. The key insight is that PESSIMISTIC is the safe default for most scenarios. OPTIMISTIC only makes sense for read-heavy, low-contention workloads where the retry overhead is acceptable. For mixed or unclear workloads, always start with PESSIMISTIC and only switch to OPTIMISTIC after measuring the performance benefit.

6. Monitor Transaction Metrics

// Get transaction metrics
TransactionMetrics metrics = ignite.transactions().metrics();

System.out.println("Committed transactions: " + metrics.txCommits());
System.out.println("Rolled back transactions: " + metrics.txRollbacks());

// JMX monitoring
// org.apache:group=Transactions,name=TransactionMetrics

// Key metrics to monitor:
// - Average commit time
// - Rollback rate
// - Active transaction count
// - Lock wait times

Tip: Set up alerts for high rollback rates or long commit times

Transaction metrics are essential for production monitoring. The txCommits and txRollbacks counters show the success rate. A high rollback rate indicates contention problems or frequent conflicts. JMX monitoring allows integration with tools like Prometheus, Grafana, or Datadog. Set up alerts on rollback rate exceeding a threshold and on average commit time exceeding expected latency.

Summary: Best Practices Checklist

  • Keep transactions short - minimize time locks are held
  • Use batch operations (putAll, getAll) within transactions
  • Always use try-with-resources or explicit close()
  • Handle all transaction-specific exceptions
  • Avoid nested transactions
  • Use consistent lock ordering to prevent deadlocks
  • Set appropriate timeouts
  • Choose the right concurrency mode for your workload
  • Monitor transaction metrics in production
  • Test deadlock scenarios before deployment
This is the master checklist for transaction best practices. Go through each item and ask students to identify which ones they have seen demonstrated in the slides. All ten practices should be followed in production code. The first three (short transactions, batch operations, try-with-resources) have the most impact on performance. The deadlock prevention and timeout practices are critical for reliability.
