Cluster Topology Overview

What is an Ignite Cluster?

Definition: A group of Ignite nodes connected together, sharing data and computation.

Ignite Cluster
Node 1
Node 2
Node 3
Distributed Data Grid
Start with the big picture: an Ignite cluster is a group of interconnected nodes that share data and computation. Unlike master-slave architectures, Ignite is peer-to-peer -- there is no single point of failure. Each node is equal and can serve any request. The distributed data grid spans all nodes.

Key Cluster Characteristics

  • Peer-to-peer: All nodes equal
  • Automatic discovery: Nodes find each other
  • Self-healing: Recovers from failures
  • Dynamic topology: Nodes can join/leave anytime
Peer-to-peer means no single coordinator that must be available. Automatic discovery simplifies deployment since nodes find each other. Self-healing means when a node fails, data is automatically recovered from backups. Dynamic topology allows scaling without downtime. These characteristics make Ignite suitable for cloud environments.

Node Types

Server Nodes vs Client Nodes

Server Nodes

  • Store data
  • Participate in compute operations
  • Full members of cluster
  • Contribute resources (CPU, RAM)
  • Participate in baseline topology

Client Nodes

  • Do not store data
  • Lightweight
  • Connect to cluster
  • Can execute operations
  • Route requests to server nodes
  • Good for application servers
The server vs client distinction is fundamental. Server nodes are the workhorses -- they store data and do heavy computation. Client nodes are lightweight connectors that route requests to the right server node. A typical production setup has a fixed number of server nodes and a variable number of client nodes scaling with application load.

This visual shows the typical topology. Client nodes on the left connect to server nodes on the right. Data only lives on server nodes. Client nodes are stateless from a data perspective, making them easy to scale up and down. In Kubernetes, client nodes would be your application pods and server nodes would be a StatefulSet.

Client vs Server

Practical Deployment Guidance

The Key Question: Where does your application code run?

This is a critical architectural decision that affects performance, scaling, and operational complexity.
This section dives deeper into the practical implications of the client vs server choice. It is one of the most impactful architectural decisions. Get it wrong and you face cluster instability or unnecessary complexity. The key question on screen should prompt students to think about their own deployment scenarios.

Connection Options

Option What It Is When to Use
Server Node Full cluster member, stores data Dedicated Ignite servers only
Thick Client Cluster member, no data storage Long-running apps, compute tasks
Thin Client TCP socket, minimal footprint Microservices, short-lived apps
Walk through the three connection options. Server nodes should only be dedicated Ignite servers -- never embed a server node in an application container. Thick clients join the cluster and have full API access but add overhead. Thin clients are lightweight TCP connections ideal for microservices. Most modern deployments should default to thin clients.

Thick Client (Client Mode)

When Your App Joins the Cluster

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setClientMode(true);
Ignite ignite = Ignition.start(cfg);

Advantages:

  • Full API access
  • Near cache support
  • Compute grid participation
  • Topology awareness

Disadvantages:

  • Startup time (~seconds)
  • Memory overhead (~100MB+)
  • Must handle topology events
  • Affects cluster stability
The thick client code is what students will use in most labs. The advantages are significant: full API access including compute grid, near cache for local data copies, and topology awareness for smart routing. The disadvantages matter in production: startup time of several seconds, 100MB+ memory overhead, and every thick client adds to cluster discovery traffic.

Thin Client

Lightweight TCP Connection

ClientConfiguration cfg = new ClientConfiguration()
    .setAddresses("node1:10800", "node2:10800");
IgniteClient client = Ignition.startClient(cfg);

Advantages:

  • Instant startup
  • Minimal memory (~10MB)
  • No cluster impact
  • Multi-language support

Disadvantages:

  • Limited API
  • No near cache
  • No compute grid
  • Extra network hop
The thin client uses a simple TCP connection on port 10800. Show the code -- it is much simpler than the thick client. Instant startup and minimal memory make it ideal for containerized microservices. The trade-offs are limited API (no compute grid, no near cache) and an extra network hop since the thin client does not know which node owns which partition. Multi-language support is a big plus for polyglot organizations.

Decision Framework

Choose Your Connection Type

Does your app need compute grid? | +-- YES --> Thick Client | +-- NO --> Is app long-running (> minutes)? | +-- YES --> Thick Client (for near cache) | +-- NO --> Thin Client (for simplicity)
Rule of Thumb: Start with Thin Client. Move to Thick Client only when you need compute grid or near cache.
This decision tree simplifies the choice. The rule of thumb at the bottom is the key takeaway: start simple with thin clients and only upgrade to thick clients when you have a concrete need for compute grid or near cache functionality. This avoids premature complexity.

Data Distribution Fundamentals

How Data is Spread Across Nodes

Partitioning:

  • Data divided into partitions (default: 1024)
  • Each partition assigned to specific nodes
  • Even distribution across cluster
  • Key -> Hash -> Partition -> Node(s)
Key: "user123" | (hash function) v Partition: 456 | (affinity) v Nodes: [Node 2 (primary), Node 3 (backup)]
Partitioning is how Ignite distributes data across nodes. The default 1024 partitions provides good distribution for most clusters. The key-to-partition mapping is deterministic: the same key always maps to the same partition. This means any node can calculate which node owns a particular key without a lookup table. The affinity function assigns each partition to primary and backup nodes.

Partitioning Example

Data Distribution Process

1024 Partitions distributed across 4 nodes: Node 1: Partitions [0-255] (256 partitions) Node 2: Partitions [256-511] (256 partitions) Node 3: Partitions [512-767] (256 partitions) Node 4: Partitions [768-1023] (256 partitions) When you put key "X": 1. Hash("X") = 1234567890 2. Partition = 1234567890 % 1024 = 442 3. Primary Node = Node 2 (owns partition 442) 4. Backup Node = Node 3 (if backups=1)

Characteristics: Deterministic, consistent hashing, automatic rebalancing

Walk through the example step by step. The hash function produces a large number, the modulo operation maps it to one of 1024 partitions, and the affinity function determines which node owns that partition. When a new node joins, only a portion of partitions need to move -- this is the benefit of consistent hashing versus simple modulo-based distribution.

Backup Strategy

Ensuring Data Availability

CacheConfiguration<K, V> cfg = new CacheConfiguration<>();
cfg.setBackups(1); // One backup copy
Backups Fault Tolerance Use Case
0 None (fastest) Temporary/regenerable data
1 Survive 1 node failure Recommended for most cases
2 Survive 2 node failures High availability
The backup configuration is a critical trade-off decision. Zero backups gives maximum performance but any node failure loses data. One backup is the sweet spot for most production systems -- it survives a single node failure with moderate memory overhead. Two backups are for high-availability requirements like financial systems. Students will configure backups in the lab.

Backup Trade-offs

Primary Data: Node 1, Node 2, Node 3 Backup Data: Node 2, Node 3, Node 1 Node 1 fails -> Node 2's backup becomes primary No data loss!
  • More backups = better availability
  • More backups = more memory used
  • More backups = more network traffic
The visual shows how backup promotion works when a node fails. Node 1 fails and Node 2's backup copy of that data is automatically promoted to primary. No data is lost and no manual intervention is needed. The trade-off triangle of availability, memory, and network traffic should guide the backup count decision. For development and testing, zero backups is fine.

Memory Architecture Overview

Three-Tier Memory Model

+-------------------------------------+ | On-Heap (JVM Heap) | | - Java objects | | - Fast access | | - GC overhead | | - Size limited | +-------------------------------------+ | eviction v +-------------------------------------+ | Off-Heap (Native RAM) | | - Binary format | | - No GC overhead | | - Large capacity | | - Serialization cost | +-------------------------------------+ | checkpointing v +-------------------------------------+ | Disk (Native Persistence) | | - Durable storage | | - Unlimited capacity | | - Slowest access | | - Write-Ahead Log | +-------------------------------------+
The three-tier memory model is unique to Ignite. On-heap is standard Java objects with fast access but GC overhead. Off-heap is native memory managed by Ignite directly, avoiding GC pauses -- this is where most data should live. Disk persistence via the native persistence layer provides durability. Data flows down through eviction and checkpointing, and is read back up on demand.

On-Heap vs Off-Heap

Memory Comparison

On-Heap Memory

  • Fast access (Java objects)
  • No serialization needed
  • GC pauses
  • Size limitations
  • Memory fragmentation

Off-Heap Memory

  • No GC pauses
  • Large datasets (100s of GB)
  • Efficient memory use
  • Serialization overhead
  • Manual memory management
For production, off-heap is almost always recommended. The key benefit is avoiding GC pauses which can cause latency spikes. On-heap is fine for small datasets or when you need zero-serialization access to Java objects. The serialization overhead of off-heap is the price you pay for predictable latency. A common student question: "How much off-heap should I allocate?" Answer: 60-70% of available RAM.

Off-Heap Configuration

Recommended Approach

DataRegionConfiguration region = new DataRegionConfiguration();
region.setMaxSize(10L * 1024 * 1024 * 1024); // 10 GB off-heap
region.setPersistenceEnabled(false); // In-memory only
Show this code example -- it is straightforward. The setMaxSize call defines the upper bound of off-heap memory for this region. If persistence is disabled, data that exceeds this limit triggers eviction. Students will configure data regions in the Module 4 lab on configuration and deployment.

Logical Memory Areas

Data regions let you create logical memory areas with different characteristics. You can have a large in-memory-only region for hot data and a smaller persistent region for critical data. Each cache can be assigned to a specific region. This gives fine-grained control over memory allocation and persistence behavior.

Data Region Use Cases

Use Case Region Type Configuration
Hot data In-memory region Large size, no persistence

Focus on the table: hot data should be in-memory only for maximum speed, cold data should use persistence for durability, and temporary data should use smaller regions with eviction enabled. A common pattern is to have three regions: hot, warm, and cold, with different size limits and persistence settings for each.

Native Persistence

Durability Without External Database

What is Native Persistence? Ignite's own disk storage mechanism.

Features:

  • Write-Ahead Log (WAL) for durability
  • Checkpointing for crash recovery
  • Page-based storage
  • Instant cluster restarts
  • No external database needed
Native persistence is one of Ignite's strongest differentiators. Unlike Redis which uses RDB snapshots or AOF logging, Ignite has a full page-based storage engine with WAL. This means the cluster can be completely restarted and all data is preserved. Instant cluster restarts mean no lengthy data loading phase -- data is read from disk on demand.

Persistence Architecture

+-------------------------------------+ | RAM (Active Data) | +-------------------------------------+ | (async writes) v +-------------------------------------+ | WAL (Write-Ahead Log) | | - All changes logged first | | - Sequential writes (fast) | +-------------------------------------+ | (checkpointing) v +-------------------------------------+ | Disk Storage (Data Pages) | | - Permanent storage | | - Random access structure | +-------------------------------------+
The persistence architecture follows a classic database design pattern. Changes go to RAM first for speed, then to the WAL for durability (sequential writes are fast), and finally to disk storage via checkpointing. This means even if the node crashes between checkpoints, the WAL can replay changes to restore consistency. Students familiar with PostgreSQL or MySQL will recognize this pattern.

WAL (Write-Ahead Log)

Ensuring Durability

How WAL Works:

  1. Change made in memory
  2. Change written to WAL (append-only)
  3. WAL fsync'd to disk
  4. Acknowledgment returned
  5. Eventually checkpointed to data files
The five-step WAL process ensures durability. The key insight is step 2-3: changes are written to the append-only WAL before being acknowledged. This guarantees that committed data survives crashes. The fsync to disk in step 3 is the performance bottleneck, which is why different WAL modes offer different trade-offs between performance and durability.

WAL Modes

// LOG_ONLY - best performance
storageCfg.setWalMode(WALMode.LOG_ONLY);

// FSYNC - maximum durability
storageCfg.setWalMode(WALMode.FSYNC);

// BACKGROUND - balanced
storageCfg.setWalMode(WALMode.BACKGROUND);
Mode Performance Durability
LOG_ONLY Fastest Slight risk of data loss
FSYNC Slower writes Maximum safety
BACKGROUND Middle ground Balanced
LOG_ONLY is the most common choice for production -- it writes to the OS page cache but does not force fsync on every write. FSYNC forces every write to disk, providing maximum durability but at significant performance cost. BACKGROUND is a middle ground that flushes periodically. For most use cases with backups enabled, LOG_ONLY provides sufficient durability since data exists on multiple nodes.

Discovery Mechanisms

How Nodes Find Each Other

Three Main Discovery Methods:

  1. Multicast Discovery (Default)
  2. Static IP Discovery
  3. Cloud/Kubernetes Discovery
Discovery is how nodes find each other to form a cluster. Getting discovery wrong is the number one cause of cluster startup failures. Multicast works out of the box for development but is often disabled in production networks. Static IP is reliable but requires maintaining a list of addresses. Kubernetes discovery uses the K8s API to find pods automatically.

Multicast Discovery

Default - Zero Configuration

// Automatic, zero configuration
TcpDiscoverySpi spi = new TcpDiscoverySpi();
// Uses IP multicast for node discovery
Best for: Development environments, simple setups where multicast is available
Multicast discovery requires zero configuration, which is why it is the default. Nodes broadcast their presence on the network and other nodes respond. The caveat is that multicast is often blocked in cloud environments and corporate data centers. If students have trouble with nodes not finding each other in the lab, switching to static IP discovery is usually the fix.

Static IP Discovery

TcpDiscoverySpi spi = new TcpDiscoverySpi();
TcpDiscoveryVmIpFinder ipFinder = new TcpDiscoveryVmIpFinder();
ipFinder.setAddresses(Arrays.asList(
    "192.168.1.10:47500",
    "192.168.1.11:47500",
    "192.168.1.12:47500"
));
spi.setIpFinder(ipFinder);
Best for: Production environments with known node addresses
Static IP discovery is the most common production configuration. You list the addresses of seed nodes that new nodes can contact to join the cluster. Not every node needs to be listed -- just enough seed nodes to ensure at least one is always available. The port range 47500 is the default discovery port. Students will configure this in their lab exercises.

Kubernetes Discovery

// Kubernetes IP Finder
TcpDiscoveryKubernetesIpFinder ipFinder =
    new TcpDiscoveryKubernetesIpFinder();
ipFinder.setNamespace("ignite");
ipFinder.setServiceName("ignite-service");
Best for: Cloud-native deployments on Kubernetes
The Kubernetes IP finder queries the K8s API to discover Ignite pods by namespace and service name. This eliminates the need to maintain static IP lists in a dynamic container environment. It requires the ignite-kubernetes Maven dependency and appropriate RBAC permissions for the pod to query the K8s API.

Node Join Sequence

Walk through each step of the join sequence. The coordinator (oldest node) manages the join process. The topology exchange in step 5 is where the new node learns about all existing nodes and caches. Rebalancing in step 7 redistributes data partitions to include the new node. This entire process typically takes seconds to a minute depending on data volume.

Discovery Key Concepts

  • Coordinator: Oldest node in cluster
  • Topology Version: Increments on changes
  • Exchange: Synchronization of node info
  • Ring Topology: Nodes form logical ring
The coordinator is always the oldest server node in the cluster. If the coordinator fails, the next oldest node takes over automatically. The topology version increments on every change, providing a monotonically increasing version for consistency. The ring topology is used for discovery protocol messages, not for data communication -- data uses direct TCP connections.

Firewall Requirements

  • Open discovery port range
  • Open communication port range
  • Allow both TCP and UDP
  • Consider cloud security groups
Firewall issues are the most common reason nodes cannot discover each other. Make sure both TCP and UDP are allowed for the discovery port range. In cloud environments, security groups must allow traffic between all nodes on discovery and communication ports. A quick diagnostic: if nodes start but do not form a cluster, check firewall rules first.

Baseline Topology

Stable Server Node Configuration

What is Baseline Topology? A set of server nodes that store data in a persistent cluster.

Why Baseline?

  • Defines which nodes are data nodes
  • Ensures data consistency
  • Controls rebalancing
  • Required for persistent clusters
Baseline topology is an advanced concept that matters when persistence is enabled. It defines which server nodes are authorized to store data. Without baseline management, a new node joining could trigger unexpected data rebalancing. This is a safety mechanism to prevent accidental data redistribution in production clusters.

Baseline Topology Visual

All Nodes: [Node1] [Node2] [Node3] [Client1] [Client2] Baseline: [Node1] [Node2] [Node3] ^ ^ ^ (Only these store data)
Key Points:
  • New nodes don't automatically join baseline
  • Must explicitly add nodes to baseline
  • Prevents unexpected rebalancing
  • Controls data distribution
The visual makes the concept clear: only the three server nodes are in the baseline and store data. Client nodes are excluded. New server nodes that join the cluster are NOT automatically added to the baseline -- this is intentional to prevent unplanned rebalancing. An administrator must explicitly add nodes to the baseline topology.

Cluster Activation

Starting a Persistent Cluster

Cluster States:

  • INACTIVE: Cluster started but not ready
  • ACTIVE: Cluster ready for operations
  • READ_ONLY: Can read but not write
Cluster activation is required for persistent clusters. When a persistent cluster starts, it begins in INACTIVE state to prevent data inconsistency before all nodes have joined. The administrator must explicitly activate the cluster once all expected nodes are present. READ_ONLY mode is useful for maintenance operations.

Activation Process

// Check state
ClusterState state = ignite.cluster().state();

// Activate cluster
ignite.cluster().state(ClusterState.ACTIVE);

// Set baseline (first time)
ignite.cluster().setBaselineTopology(
    ignite.cluster().topologyVersion()
);

Command Line:

# Activate cluster
bin/ignite.sh --activate

# Set baseline
bin/ignite.sh --baseline add <nodeId>

# View baseline
bin/ignite.sh --baseline
Show both the Java API and command-line approaches. The Java API is useful for programmatic cluster management. The command-line tools are useful for operations teams. The setBaselineTopology call sets the baseline to the current topology version, which includes all currently joined server nodes. In production, this is typically done once during initial cluster setup.

Baseline Topology Management

Adding/Removing Nodes

Adding Node to Baseline:

# Start new node (joins cluster but not baseline)
bin/ignite.sh

# Add to baseline
bin/ignite.sh --baseline add <consistentId>

Removing Node from Baseline:

# Stop node gracefully
kill -SIGTERM <pid>

# Remove from baseline
bin/ignite.sh --baseline remove <consistentId>
Adding and removing nodes from the baseline is a critical operations task. When adding a new node: first start it so it joins the cluster, then add it to the baseline. When removing: stop the node gracefully first, then remove from baseline. Always do this in a controlled manner to avoid data loss during rebalancing.

Auto-Adjust Baseline

Ignite 2.4+

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setDataStorageConfiguration(
    new DataStorageConfiguration()
        .setBaselineAutoAdjustEnabled(true)
        .setBaselineAutoAdjustTimeout(30000) // 30 seconds
);
Best Practices:
  • Manually manage in production
  • Use auto-adjust cautiously
  • Always backup before topology changes
Auto-adjust baseline was introduced in Ignite 2.4 and automatically adds or removes nodes from the baseline after a configurable timeout. The 30-second default gives temporary failures time to recover before triggering rebalancing. However, use with caution in production -- manual baseline management gives you more control. Always backup data before making topology changes.

Communication SPI

Node-to-Node Communication

Purpose: Handles all inter-node communication (data, messages).

TcpCommunicationSpi commSpi = new TcpCommunicationSpi();
commSpi.setLocalPort(47100);
commSpi.setLocalPortRange(100); // 47100-47199

// Connection pooling
commSpi.setConnectionsPerNode(1);

// Message queue size
commSpi.setMessageQueueLimit(1024);

cfg.setCommunicationSpi(commSpi);
The Communication SPI handles all data transfer between nodes, separate from the Discovery SPI which handles membership. The default settings work well for most cases. The connectionsPerNode setting controls how many TCP connections are opened between each pair of nodes. The message queue limit prevents memory issues under high load.

Communication Tuning

Parameter Effect
Connections per node More = higher throughput
Message queue Larger = handle bursts better
Socket buffer sizes Match network capacity
These tuning parameters are for advanced optimization. Increasing connections per node helps with throughput-heavy workloads by allowing parallel data transfer. Larger message queues help absorb burst traffic. Socket buffer sizes should match your network MTU and bandwidth. Most students will not need to change these defaults initially.

Cluster Membership

Node Lifecycle

START -> JOINING -> JOINED -> ACTIVE -> LEAVING -> LEFT START: Node process started JOINING: Discovery in progress JOINED: Part of topology ACTIVE: Fully operational LEAVING: Graceful shutdown LEFT: No longer in cluster
Understanding the node lifecycle helps with debugging. A common issue is a node stuck in JOINING state, which usually indicates a discovery problem. The difference between LEAVING and LEFT is that LEAVING is a graceful shutdown where the node announces its departure, while a failed node goes directly to LEFT. Graceful shutdowns are preferred because they allow orderly data migration.

Segmentation

Split-Brain Prevention

Segmentation: When network split causes multiple sub-clusters.

Prevention Mechanisms:

  • Segmentation resolvers
  • Majority-based decisions
  • Network partition detection
Split-brain is one of the hardest problems in distributed systems. If the network splits a cluster into two groups, each group might think it is the surviving cluster and continue accepting writes, leading to data inconsistency. Ignite uses segmentation resolvers to detect this situation and shut down the minority partition. This is why odd numbers of nodes are recommended.

Rebalancing

Data Redistribution

When Rebalancing Occurs:

  • Node joins cluster
  • Node leaves cluster
  • Baseline topology changes
  • Cache configuration changes
Rebalancing is the process of redistributing data when the cluster topology changes. It happens automatically and in the background, but can temporarily impact performance. Understanding when rebalancing occurs helps operators plan for topology changes. The most common trigger is adding or removing nodes.

Rebalancing Process

1. Detect topology change
v
2. Calculate new partition mapping
v
3. Transfer partitions to new locations
v
4. Update partition counters
v
5. Verify data consistency
The five-step rebalancing process runs automatically. Step 2 uses the affinity function to determine the new optimal partition layout. Step 3 is the most time-consuming -- actual data transfer across the network. The cluster remains fully operational during rebalancing, though performance may be slightly degraded due to network bandwidth usage.

Rebalancing Configuration

CacheConfiguration cfg = new CacheConfiguration();

// Rebalancing mode
cfg.setRebalanceMode(CacheRebalanceMode.ASYNC);

// Batch size
cfg.setRebalanceBatchSize(512 * 1024); // 512 KB

// Thread pool size
cfg.setRebalanceThreadPoolSize(2);

// Throttle
cfg.setRebalanceThrottle(100); // 100ms pause
These configuration options let you control how aggressively rebalancing uses resources. ASYNC mode allows the cluster to serve requests during rebalancing. Larger batch sizes speed up rebalancing but use more network bandwidth. The throttle parameter adds pauses between batches to reduce impact on production traffic. For large datasets, tuning these parameters is important.

Affinity Function

Controlling Data Placement

Default Affinity: Rendezvous Affinity (consistent hashing)

// Customize partitions
AffinityFunction aff = new RendezvousAffinityFunction(
    false,  // exclude neighbors
    2048    // number of partitions
);
cfg.setAffinity(aff);
The affinity function determines how keys map to partitions and partitions map to nodes. The default Rendezvous affinity uses consistent hashing which minimizes data movement when nodes join or leave. You can customize the number of partitions -- more partitions give finer-grained distribution but increase memory overhead. 1024 partitions is optimal for clusters up to about 100 nodes.

Affinity Key

Control Data Colocation

public class Order {
    private int orderId;

    @AffinityKeyMapped
    private int customerId; // Orders colocated with customer
}

Benefits:

  • Colocation of related data
  • Reduced network hops
  • Faster joins and computations
Affinity keys are a powerful optimization. By annotating the customerId field with @AffinityKeyMapped, all orders for the same customer are stored on the same node. This means a join between customers and orders can be executed locally without network hops. This concept is called data colocation and is critical for distributed SQL performance. We will explore this in depth during the data modeling module.

Topology Events

Monitoring Cluster Changes

Event Types:

  • Node joined
  • Node left
  • Node failed
  • Node segmented
Topology events let your application react to cluster changes. This is useful for monitoring, alerting, and custom logic like redistributing work when nodes fail. The four event types cover all topology changes. In production, you should at minimum log these events for operational visibility.

Listening for Events

ignite.events().localListen(event -> {
    if (event instanceof DiscoveryEvent) {
        DiscoveryEvent de = (DiscoveryEvent) event;

        System.out.println("Event: " + de.name());
        System.out.println("Node: " + de.eventNode().id());
    }
    return true;
}, EventType.EVT_NODE_JOINED, EventType.EVT_NODE_LEFT);

  • Monitoring

  • Custom rebalancing logic
  • Application coordination
The code example shows how to register a local event listener. The lambda receives events and returns true to continue listening. You specify which event types to listen for. This is useful for building monitoring dashboards, sending alerts when nodes fail, or implementing custom coordination logic in your application.

Architecture Best Practices

Cluster

  • 3-5 server nodes (odd #s)
  • 60-70% RAM to Ignite

Network & Backups

  • Low-latency network
  • 1-2 backups per cache
These best practices come from production experience. Odd numbers of server nodes help with split-brain resolution. Allocating 60-70% of RAM to Ignite leaves room for JVM heap, OS, and other processes. Low-latency networking is critical since distributed operations require network round trips. One to two backups provide a good balance of fault tolerance and memory usage.

Common Architecture Patterns

Deployment Topologies

These deployment patterns give students concrete architectures to reference when designing their own systems. Each pattern has trade-offs in terms of complexity, performance, and operational overhead. Most organizations start with Pattern 1 or 2 and evolve as needed.

Pattern 1: All-in-One

[Application + Ignite Server Node]
  • Simplest deployment
  • Good for small apps
  • Tight coupling
The all-in-one pattern is what students use in the labs. It is the simplest to set up and understand. The application and Ignite share the same JVM, so data access is local and fast. The downside is tight coupling -- if the application crashes, the data node goes down too. This is acceptable for development but not recommended for production with important data.

Pattern 2: Separate Data Tier

[Application (Client)] --> [Ignite Cluster (Servers)]
  • Better separation
  • Independent scaling
  • Production recommended
This is the production-recommended pattern. The application connects as a client to a dedicated Ignite cluster. Independent scaling means you can add more application instances without affecting data distribution, and add more Ignite nodes without restarting applications. This pattern also allows different teams to manage the application and data tiers independently.

Pattern 3: Multi-Datacenter

[DC1: Ignite Cluster] <--> [DC2: Ignite Cluster]
  • Geographic distribution
  • Disaster recovery
  • Application-level replication
Multi-datacenter deployment is the most complex pattern. Ignite does not natively support cross-datacenter replication in the open-source version -- this requires application-level replication or the GridGain commercial product. This pattern is for disaster recovery scenarios where you need data in multiple geographic locations.

Troubleshooting Architecture Issues

Common Problems

Troubleshooting is a practical skill students will need immediately. The next few slides cover the four most common architecture issues. Encourage students to take notes on these since they will encounter them in the lab and in production.

Problem 1: Nodes Not Discovering

  • Check network connectivity
  • Verify discovery configuration
  • Check firewall rules
  • Ensure port availability
Discovery failures are the number one issue during initial setup. Check these four things in order: Can nodes ping each other? Is the discovery SPI configured with correct addresses? Are firewall rules allowing traffic on ports 47500-47509? Is another process already using those ports? In the lab, this is usually resolved by verifying the IP finder configuration.

Problem 2: Segmentation

  • Check network stability
  • Review segmentation resolver config
  • Adjust failure detection timeout
Segmentation issues are more subtle and usually indicate network instability. If you see frequent segmentation events in the logs, the network between nodes is unreliable. Increasing the failure detection timeout can help with transient network issues but at the cost of slower failure detection. A segmentation resolver can be configured to handle split-brain scenarios gracefully.

Problem 3: Slow Rebalancing

  • Increase rebalance threads
  • Adjust batch sizes
  • Check network bandwidth
  • Review throttling settings
Slow rebalancing is common with large datasets. Increasing rebalance threads allows parallel data transfer. Larger batch sizes reduce per-batch overhead. Check that network bandwidth is not saturated during rebalancing. If rebalancing impacts production performance too much, increase the throttle setting to add pauses between batches.

Problem 4: Memory Issues

  • Increase data region size
  • Enable eviction
  • Review data model
  • Check for memory leaks
Memory issues manifest as OutOfMemoryErrors or degraded performance. First, check if data region size is large enough for your data volume including backups. Enable eviction if data can exceed available memory. Review your data model for unnecessary fields or overly large objects. Memory leaks can occur if cache entries are never removed -- consider using expiry policies.

Key Takeaways

Remember These Points

  1. Cluster is peer-to-peer - All nodes equal (no master), self-healing and elastic
  2. Data is partitioned and distributed - Consistent hashing, automatic rebalancing
  3. Three-tier memory model - On-heap, off-heap, disk - each has trade-offs
  4. Baseline topology for persistence - Controls which nodes store data, manual management recommended
  5. Discovery is critical - Must be configured correctly for different environments
These five takeaways summarize the entire module. The peer-to-peer nature eliminates single points of failure. Partitioning and consistent hashing enable horizontal scaling. The three-tier memory model gives flexibility for different workloads. Baseline topology is essential for persistent clusters. Discovery configuration varies by environment. Students should be able to explain each of these concepts after this module.
