Near Caches

Client-Side Caching for Performance

Near caches are one of the simplest yet most impactful performance optimizations in Ignite. They keep a local copy of frequently accessed data on the client node, eliminating network round-trips for repeated reads. This is especially useful for reference data that changes infrequently but is read constantly.

What is a Near Cache?

A near cache is a local cache on client nodes that stores frequently accessed data, reducing network latency for repeated reads.

Client Node
(Near Cache)
→
Server Node
(Primary Data)
The diagram shows the basic architecture: the client node has a local near cache that sits between the application and the server node. On first access, data comes from the server. On subsequent access, data is served from the local near cache with zero network latency. The near cache is automatically invalidated when data changes on the server, though there is a brief window of staleness.

Near Cache Benefits

  • Reduced Latency - Local data access
  • Lower Server Load - Fewer network requests
  • Better Performance - For frequently accessed data
  • Automatic Invalidation - Updates propagated from server
The four benefits map to common production needs. Reduced latency is the primary benefit, especially for client nodes that are geographically distant from server nodes. Lower server load means the cluster can handle more clients. Automatic invalidation means the developer does not need to manually manage consistency, though they should understand the brief staleness window.

Near Cache Architecture

First Access:
Client --[GET key=100]--> Server --[Return value]--> Client
                                                       |
                                                  [Store in
                                                   Near Cache]

Subsequent Access:
Client --[GET key=100]--> Near Cache --[Return value]--> Client
         (No network call!)
This text diagram shows the two access paths. On first access, the request goes to the server, the value is returned and stored in the near cache. On subsequent access, the near cache serves the value directly with no network call. In production, this difference can be 0.1ms local versus 1-5ms network, which is significant for high-frequency read operations.

Configuring Near Cache

// Create near cache configuration
NearCacheConfiguration<Integer, String> nearCfg =
    new NearCacheConfiguration<>();

// Set eviction policy for near cache (max 100 entries)
nearCfg.setNearEvictionPolicyFactory(
    () -> new LruEvictionPolicy<>(100)
);

// Create cache with near cache on client
IgniteCache<Integer, String> cache =
    ignite.getOrCreateNearCache("dataCache", nearCfg);
The configuration is straightforward. The LruEvictionPolicy with maxSize 100 means the near cache will keep at most 100 entries locally and evict the least recently used when full. The getOrCreateNearCache method creates the near cache on the client side. Students should size the near cache based on their working set, not the total data size.

Near Cache Performance Example

// First access - fetches from server
long start = System.currentTimeMillis();
String value1 = cache.get(100);  // Network call
long time1 = System.currentTimeMillis() - start;
System.out.println("First access: " + time1 + " ms");

// Second access - from near cache
start = System.currentTimeMillis();
String value2 = cache.get(100);  // Local access
long time2 = System.currentTimeMillis() - start;
System.out.println("Second access: " + time2 + " ms");
System.out.println("Speedup: " + (float)time1/time2 + "x faster");
This performance measurement code is a great demo opportunity. Run it in the lab and students will see the first access taking milliseconds while the second access takes microseconds. The speedup can be 10x to 100x depending on network latency. This makes the value proposition of near caches immediately tangible.

Complete Near Cache Example

// Client-side near cache config
NearCacheConfiguration<Integer, String> nearCfg =
    new NearCacheConfiguration<>();
nearCfg.setNearEvictionPolicyFactory(
    () -> new LruEvictionPolicy<>(100));

// Get cache with near cache enabled
IgniteCache<Integer, String> cache =
    ignite.getOrCreateNearCache("dataCache", nearCfg);
This is a condensed version showing the essential near cache setup. In the lab, students will expand this to include performance measurement and multiple entries. Note that near caches are only relevant for client nodes; server nodes already have local data through partitioning. A common mistake is trying to create near caches on server nodes, which is unnecessary.

When to Use Near Caches

Good Use Cases

  • Read-heavy workloads
  • Reference data
  • Client-side processing
  • Tolerable staleness

Avoid When

  • Write-heavy workloads
  • Strict consistency needed
  • Memory constrained clients
  • Random access patterns
The good and avoid columns help students decide when near caches are appropriate. The key insight is that near caches work best for read-heavy workloads with reference data. For write-heavy workloads, the invalidation overhead outweighs the read benefit. For memory-constrained clients, the near cache consumes local heap. Random access patterns do not benefit because the cached data is rarely reused.

Expiry Policies

Time-to-Live Management

Expiry policies control how long data stays in the cache based on time. This is essential for caching data that has a known freshness requirement, like session tokens that should expire after 30 minutes or API response caches that should refresh every 5 minutes. The three policy types provide different timer reset behaviors for different use cases.

Expiry Policy Types

Policy Timer Starts Timer Resets Use Case
Created On creation Never Session tokens
Modified On creation On update Active data
Touched On creation On access/update LRU-like behavior
This comparison table is the key reference for understanding the three policies. Created never resets so the timer counts from creation only. Modified resets on updates but not reads. Touched resets on any access including reads. Use Created for absolute TTL like session tokens, Modified for data that should stay alive while being updated, and Touched for keeping hot data alive.

Created Expiry Policy

Entry expires a fixed time after creation

import javax.cache.expiry.CreatedExpiryPolicy;
import javax.cache.expiry.Duration;

CacheConfiguration<Integer, String> cfg =
    new CacheConfiguration<>("sessionCache");

// Expire 5 seconds after creation
cfg.setExpiryPolicyFactory(
    CreatedExpiryPolicy.factoryOf(Duration.FIVE_SECONDS)
);

IgniteCache<Integer, String> cache = ignite.getOrCreateCache(cfg);

cache.put(1, "Session data");    // Timer starts
Thread.sleep(6000);              // Wait 6 seconds
cache.get(1);                    // Returns null - expired!
The Created expiry policy is the simplest. The entry expires exactly 5 seconds after creation regardless of whether it is read or updated. This is perfect for session tokens, OTP codes, and any data with an absolute lifetime. The code demonstrates the full lifecycle: put, wait, then get returns null. Students will implement this in the lab and verify the expiration timing.

Modified Expiry Policy

Timer resets on every update

import javax.cache.expiry.ModifiedExpiryPolicy;

CacheConfiguration<Integer, String> cfg =
    new CacheConfiguration<>("activeDataCache");

// Expire 3 seconds after last modification
cfg.setExpiryPolicyFactory(
    ModifiedExpiryPolicy.factoryOf(new Duration(TimeUnit.SECONDS, 3))
);

IgniteCache<Integer, String> cache = ignite.getOrCreateCache(cfg);

cache.put(1, "Initial value");   // Timer starts (3 sec)
Thread.sleep(2000);
cache.put(1, "Updated value");   // Timer resets (3 sec)
Thread.sleep(2000);
cache.get(1);                    // Still there! (only 2 sec elapsed)
Thread.sleep(4000);
cache.get(1);                    // null - expired after 3 seconds
Modified expiry resets the timer on every put operation but not on get. The example shows the timer starting at creation, then resetting when the value is updated. After the update, only 2 seconds pass before the next get, so the entry is still alive. But then 4 seconds pass without any update, exceeding the 3-second TTL. This is useful for configuration data that should expire only if it stops being updated.

Touched Expiry Policy

Timer resets on any access (read or write)

import javax.cache.expiry.TouchedExpiryPolicy;

CacheConfiguration<Integer, String> cfg =
    new CacheConfiguration<>("frequentAccessCache");

// Expire 4 seconds after last access
cfg.setExpiryPolicyFactory(
    TouchedExpiryPolicy.factoryOf(new Duration(TimeUnit.SECONDS, 4))
);

IgniteCache<Integer, String> cache = ignite.getOrCreateCache(cfg);

cache.put(1, "Touched expiry value");
for (int i = 0; i < 5; i++) {
    Thread.sleep(2000);
    cache.get(1);  // Each read resets the 4-second timer
    System.out.println("Still alive after " + ((i+1)*2) + " seconds");
}
Thread.sleep(5000);
cache.get(1);  // null - no access for 5 seconds
Touched expiry keeps data alive as long as it is being accessed, even by reads. The loop reads the entry every 2 seconds, which resets the 4-second timer each time. As long as the gap between accesses is less than 4 seconds, the entry survives. Once access stops for 5 seconds, the entry expires. This implements LRU-like behavior at the data level rather than the memory level.

Per-Entry Expiry Policy

Different TTL for different entries

IgniteCache<Integer, String> baseCache =
    ignite.getOrCreateCache("dynamicExpiryCache");

// Create view with 2-second TTL
IgniteCache<Integer, String> shortTTL = baseCache.withExpiryPolicy(
    CreatedExpiryPolicy.factoryOf(
        new Duration(TimeUnit.SECONDS, 2)).create()
);

// Create view with 10-second TTL
IgniteCache<Integer, String> longTTL = baseCache.withExpiryPolicy(
    CreatedExpiryPolicy.factoryOf(
        new Duration(TimeUnit.SECONDS, 10)).create()
);

shortTTL.put(1, "Quick expiry");    // 2-second TTL
longTTL.put(2, "Long expiry");      // 10-second TTL

Thread.sleep(3000);
baseCache.get(1);  // null (expired)
baseCache.get(2);  // Still there
Per-entry expiry is a powerful technique for when different entries need different TTLs. The withExpiryPolicy method creates a cache view with a specific policy. The key insight is that entries put through the shortTTL view get a 2-second TTL while entries put through the longTTL view get 10 seconds. The base cache reads both entries regardless of their TTL settings. This is commonly used for tiered data freshness requirements.

Expiry Policy Use Cases

  • Created: Session data, JWT tokens, OTP codes
  • Modified: Configuration that updates periodically
  • Touched: Recently accessed data (keep hot data)
This summary helps students match the right policy to their use case. Session tokens and OTP codes have fixed lifetimes so use Created. Configuration data should stay fresh while being actively updated so use Modified. Hot data caches should keep frequently accessed entries alive so use Touched. Ask students what policy they would use for their specific application scenarios.

Eviction Policies

Memory Management Strategies

Eviction policies manage memory by removing entries from the on-heap cache when it gets too full. This is fundamentally different from expiry which removes entries based on time. Students often confuse the two, so the comparison on the next slide is critical. Eviction is about memory management, expiry is about data freshness.

Eviction vs Expiry

Aspect Eviction Expiry
Purpose Memory management Data freshness
Trigger Memory pressure Time elapsed
Data Location Moves to off-heap/disk Completely removed
Recoverable Yes (from off-heap) No
This is the most important distinction students need to understand. Eviction moves entries from on-heap to off-heap storage, while expiry completely removes entries. Evicted data is still accessible (just slower), while expired data is gone forever. Eviction is triggered by memory pressure, expiry by time elapsed. Both can be used together on the same cache for comprehensive data management.

LRU Eviction Policy

Least Recently Used - evicts oldest accessed entries

import org.apache.ignite.cache.eviction.lru.LruEvictionPolicy;

CacheConfiguration<Integer, String> cfg =
    new CacheConfiguration<>("lruCache");

// Enable on-heap caching
cfg.setOnheapCacheEnabled(true);

// Configure LRU eviction - max 100 entries on heap
LruEvictionPolicy<Integer, String> policy = new LruEvictionPolicy<>();
policy.setMaxSize(100);

cfg.setEvictionPolicyFactory(() -> policy);

IgniteCache<Integer, String> cache = ignite.getOrCreateCache(cfg);

// Add 200 entries - 100 oldest will be evicted to off-heap
for (int i = 0; i < 200; i++) {
    cache.put(i, "Value-" + i);
}
LRU eviction keeps the most recently used entries on heap and evicts the least recently used. The setOnheapCacheEnabled(true) call is required to enable on-heap caching which is where eviction operates. The maxSize of 100 means at most 100 entries stay on heap. When the 101st entry is added, the least recently accessed entry is evicted to off-heap. In the lab, students will verify this behavior by checking cache sizes.

FIFO Eviction Policy

First In, First Out - evicts in insertion order

import org.apache.ignite.cache.eviction.fifo.FifoEvictionPolicy;

CacheConfiguration<Integer, String> cfg =
    new CacheConfiguration<>("fifoCache");

cfg.setOnheapCacheEnabled(true);

// Configure FIFO eviction - max 1000 entries
FifoEvictionPolicy<Integer, String> policy = new FifoEvictionPolicy<>();
policy.setMaxSize(1000);

cfg.setEvictionPolicyFactory(() -> policy);

IgniteCache<Integer, String> cache = ignite.getOrCreateCache(cfg);
FIFO eviction is simpler than LRU: entries are evicted in the order they were inserted regardless of access patterns. This is useful when all entries have equal importance and you just need to bound memory usage. FIFO has slightly less overhead than LRU because it does not need to track access times. Choose FIFO when access patterns are unpredictable or uniform.

Memory-Based Eviction

LruEvictionPolicy<Integer, String> policy = new LruEvictionPolicy<>();

// Size-based eviction
policy.setMaxSize(10000);           // Max entries

// Or memory-based eviction
policy.setMaxMemorySize(100_000_000); // Max 100 MB

// Batch eviction for better performance
policy.setBatchSize(10);            // Evict 10 at a time

cfg.setEvictionPolicyFactory(() -> policy);
Memory-based eviction allows you to set limits in bytes rather than entry count. This is more accurate when entries have variable sizes. The maxMemorySize of 100MB means the on-heap cache will not exceed 100MB. The batchSize parameter controls how many entries are evicted at once for better performance. Use memory-based eviction when entry sizes vary significantly.

Eviction Flow


[Put Entry] --> [On-Heap Cache]
                    |
                    v
            [Max Size Reached?]
                    |
          Yes       |        No
            v       |         |
    [Eviction Policy]        v
            |           [Store Entry]
            v
    [Remove Oldest/LRU]
            |
            v
    [Move to Off-Heap]
This flow diagram shows the eviction decision process. On each put, Ignite checks if the on-heap cache has reached its maximum size. If not, the entry is stored normally. If yes, the eviction policy selects which entry to remove from on-heap and the evicted entry moves to off-heap storage. The data is not lost, just stored in a slower tier. Reads of evicted data still work but incur an off-heap access penalty.

Complete Eviction Example

public class EvictionDemo {
    public static void main(String[] args) throws Exception {
        try (Ignite ignite = Ignition.start()) {
            CacheConfiguration<Integer, String> cfg =
                new CacheConfiguration<>("evictionCache");

            cfg.setOnheapCacheEnabled(true);

            LruEvictionPolicy<Integer, String> policy =
                new LruEvictionPolicy<>();
            policy.setMaxSize(100);

            cfg.setEvictionPolicyFactory(() -> policy);

            IgniteCache<Integer, String> cache =
                ignite.getOrCreateCache(cfg);

            // Add 200 entries
            for (int i = 0; i < 200; i++) {
                cache.put(i, "Value-" + i);
            }

            System.out.println("Total size: " + cache.size());
            System.out.println("On-heap: ~100 (LRU managed)");

            // Access entries 0-9 to make them "recent"
            for (int i = 0; i < 10; i++) {
                cache.get(i);  // Now protected from eviction
            }
        }
    }
}
This complete example demonstrates the LRU eviction lifecycle. After inserting 200 entries with a max of 100 on-heap, the total cache size is still 200 but only 100 are on-heap. Then accessing entries 0-9 makes them recent and protects them from eviction. Students will implement this in the lab and observe how access patterns affect which entries stay on-heap.

Cache Entry Processors

Atomic Server-Side Operations

Entry processors are one of the most powerful features in Ignite but also the most underutilized. They move the computation to the data rather than moving data to the computation. This eliminates race conditions and reduces network traffic. Students who understand entry processors will write much more efficient and correct distributed code.

Why Entry Processors?

Without Entry Processor

// 3 network calls!
Integer value = cache.get(key);
value = value + 10;
cache.put(key, value);
// Race condition possible!

With Entry Processor

// 1 network call, atomic!
cache.invoke(key,
    new IncrementProcessor(10));
// No race condition!
This side-by-side comparison is the key motivation for entry processors. Without them, a read-modify-write requires three network calls and has a race condition window between get and put. With entry processors, the entire operation executes atomically on the server in a single network call. Ask students what happens if two threads execute the left-hand pattern simultaneously on the same key.

Entry Processor Interface

public interface CacheEntryProcessor<K, V, T> extends Serializable {
    /**
     * @param entry   The mutable cache entry
     * @param args    Optional arguments
     * @return        The result of processing
     */
    T process(MutableEntry<K, V> entry, Object... args)
        throws EntryProcessorException;
}
  • K - Key type
  • V - Value type
  • T - Return type
The CacheEntryProcessor interface has three type parameters: K for key type, V for value type, and T for the return type. The process method receives a MutableEntry which allows both reading and writing the value atomically. The optional args parameter allows passing additional data without creating a new class. The Serializable requirement is because the processor is shipped to the server node where the data lives.

Increment Processor Example

public class IncrementProcessor
    implements CacheEntryProcessor<String, Integer, Integer> {

    private final int increment;

    public IncrementProcessor(int increment) {
        this.increment = increment;
    }

    @Override
    public Integer process(MutableEntry<String, Integer> entry,
                          Object... args) throws EntryProcessorException {
        Integer current = entry.getValue();
        if (current == null) {
            current = 0;
        }
        Integer newValue = current + increment;
        entry.setValue(newValue);  // Atomic update
        return newValue;
    }
}
Walk through the IncrementProcessor code. The constructor takes the increment value. The process method reads the current value, handles null for missing entries, adds the increment, and atomically sets the new value. The return value lets the caller know the new count. This entire operation runs on the server node that owns the key, so there is no network round-trip for the read-modify-write cycle. Students will implement this exact pattern in the lab.

Using the Increment Processor

CacheConfiguration<String, Integer> cfg =
    new CacheConfiguration<>("counters");
cfg.setAtomicityMode(CacheAtomicityMode.ATOMIC);

IgniteCache<String, Integer> cache = ignite.getOrCreateCache(cfg);

cache.put("pageViews", 0);

// Atomic increment - returns new value
Integer newCount = cache.invoke("pageViews",
    new IncrementProcessor(1));

System.out.println("New count: " + newCount);  // 1

// Increment by 10
newCount = cache.invoke("pageViews",
    new IncrementProcessor(10));

System.out.println("New count: " + newCount);  // 11
This shows how to invoke the entry processor. The cache.invoke method takes a key and a processor instance. The processor is serialized, sent to the server node that owns the key, and executed there. The return value comes back to the client. Note that ATOMIC mode is sufficient for entry processors since they are inherently atomic -- you do not need TRANSACTIONAL mode for single-key atomic operations.

Conditional Update Processor

public class WithdrawProcessor
    implements CacheEntryProcessor<String, Integer, Boolean> {

    private final int amount;

    public WithdrawProcessor(int amount) {
        this.amount = amount;
    }

    @Override
    public Boolean process(MutableEntry<String, Integer> entry,
                          Object... args) throws EntryProcessorException {
        Integer balance = entry.getValue();

        if (balance != null && balance >= amount) {
            entry.setValue(balance - amount);
            return true;   // Withdrawal successful
        }
        return false;      // Insufficient funds
    }
}
The WithdrawProcessor demonstrates conditional logic inside an entry processor. It checks if the balance is sufficient before deducting the amount. The return value of Boolean indicates success or failure. This is a compare-and-swap pattern that is completely atomic -- no other transaction can modify the balance between the check and the deduction. This pattern is essential for financial applications.

Using Conditional Processor

cache.put("account:1234", 100);  // $100 balance

// Try to withdraw $30
Boolean success = cache.invoke("account:1234",
    new WithdrawProcessor(30));

System.out.println("Withdraw $30: " + success);     // true
System.out.println("Balance: $" + cache.get("account:1234")); // 70

// Try to withdraw $100 (more than available)
success = cache.invoke("account:1234",
    new WithdrawProcessor(100));

System.out.println("Withdraw $100: " + success);    // false
System.out.println("Balance: $" + cache.get("account:1234")); // 70
The usage example shows two withdrawal attempts. The first succeeds (balance goes from 100 to 70), the second fails because 100 exceeds the remaining 70. The balance is unchanged after the failed withdrawal. This pattern eliminates the need for pessimistic locking in many scenarios because the entry processor provides atomicity without explicit transactions.

Batch Processing with invokeAll

// Initialize counters
cache.put("metric1", 0);
cache.put("metric2", 0);
cache.put("metric3", 0);

Set<String> keys = new HashSet<>(
    Arrays.asList("metric1", "metric2", "metric3")
);

// Increment all counters atomically
Map<String, EntryProcessorResult<Integer>> results =
    cache.invokeAll(keys, new IncrementProcessor(5));

// Check results
for (Map.Entry<String, EntryProcessorResult<Integer>> e :
        results.entrySet()) {
    System.out.println(e.getKey() + ": " + e.getValue().get());
}
invokeAll applies the same entry processor to multiple keys in parallel. Each key's processor executes atomically on the node that owns that key. The results map contains the return value for each key. Note that invokeAll does not guarantee all-or-nothing atomicity across keys -- each key is processed independently. For multi-key atomic operations, use transactions instead.

Entry Processor Benefits

  • Atomic operations - No race conditions
  • Single network call - Reduced latency
  • Server-side processing - Less data transfer
  • Guaranteed consistency - Under contention
  • Transactional support - Works with transactions
Summarize the five benefits. Atomic operations eliminate race conditions that plague naive get-then-put patterns. Single network call reduces latency from 3 round-trips to 1. Server-side processing means less data crosses the network. Guaranteed consistency under contention means entry processors work correctly even with hundreds of concurrent clients. They also integrate with transactions for multi-key atomicity.

Cache Events

Monitoring Cache Activity

Cache events provide a way to react to changes in the cache. They are useful for audit logging, monitoring, and triggering external processes. Events are disabled by default for performance so they must be explicitly enabled. This section covers the event types, how to register listeners, and practical use cases.

Event Types

Event Type Constant Triggered When
Put EVT_CACHE_OBJECT_PUT Entry created or updated
Read EVT_CACHE_OBJECT_READ Entry accessed
Removed EVT_CACHE_OBJECT_REMOVED Entry deleted
Expired EVT_CACHE_OBJECT_EXPIRED Entry expired
The four main event types correspond to the basic cache operations. PUT fires on both create and update. READ fires on get. REMOVED fires on explicit delete. EXPIRED fires when an entry is removed by an expiry policy. There are additional event types for eviction, rebalancing, and other internal operations but these four cover most monitoring needs.

Enabling Events

// Enable specific events locally
ignite.events().enableLocal(
    EventType.EVT_CACHE_OBJECT_PUT,
    EventType.EVT_CACHE_OBJECT_REMOVED,
    EventType.EVT_CACHE_OBJECT_READ
);

// Or enable via configuration
IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setIncludeEventTypes(
    EventType.EVT_CACHE_OBJECT_PUT,
    EventType.EVT_CACHE_OBJECT_REMOVED,
    EventType.EVT_CACHE_OBJECT_READ
);
Note: Events are disabled by default for performance. Enable only what you need.
There are two ways to enable events: at runtime via enableLocal or at configuration time via setIncludeEventTypes. The runtime approach is more flexible but must be called on each node. The configuration approach ensures events are enabled from startup. The warning is important: enabling events has a measurable performance impact, especially READ events on high-throughput caches. Only enable the specific event types you need.

Creating Event Listeners

IgnitePredicate<CacheEvent> listener = evt -> {
    System.out.println("Event Type: " + evt.name());
    System.out.println("Cache: " + evt.cacheName());
    System.out.println("Key: " + evt.key());
    System.out.println("Old Value: " + evt.oldValue());
    System.out.println("New Value: " + evt.newValue());
    System.out.println("Node: " + evt.node().id());
    return true;  // Continue listening
};

// Register listener
ignite.events().localListen(listener,
    EventType.EVT_CACHE_OBJECT_PUT,
    EventType.EVT_CACHE_OBJECT_REMOVED);
The listener is an IgnitePredicate that receives CacheEvent objects. The event provides the cache name, key, old value, new value, and the node where the event occurred. Returning true means continue listening; returning false unregisters the listener. The localListen method only receives events from the local node. For cluster-wide events, use remoteListen instead.

Complete Events Example

public class CacheEventsDemo {
    public static void main(String[] args) throws Exception {
        try (Ignite ignite = Ignition.start()) {
            // Enable events
            ignite.events().enableLocal(
                EventType.EVT_CACHE_OBJECT_PUT,
                EventType.EVT_CACHE_OBJECT_REMOVED,
                EventType.EVT_CACHE_OBJECT_READ);

            // Create listener
            IgnitePredicate<CacheEvent> listener = evt -> {
                System.out.println("[" + evt.name() + "] " +
                    evt.key() + " = " + evt.newValue());
                return true;
            };

            ignite.events().localListen(listener,
                EventType.EVT_CACHE_OBJECT_PUT,
                EventType.EVT_CACHE_OBJECT_REMOVED);

            IgniteCache<Integer, String> cache =
                ignite.getOrCreateCache("eventCache");

            cache.put(1, "Hello");      // Triggers PUT event
            cache.put(1, "Updated");    // Triggers PUT event
            cache.remove(1);            // Triggers REMOVED event
        }
    }
}
This complete example demonstrates the full lifecycle: enable events, register a listener, and trigger events through cache operations. The put operation fires PUT events, and the remove fires a REMOVED event. Students will run this in the lab and see the events printed in real-time. Common issue: if no events appear, verify that enableLocal was called before the listener was registered.

Event Use Cases

  • Audit Logging - Track all data changes
  • Cache Statistics - Monitor hit/miss ratios
  • Workflow Triggers - Start processes on changes
  • Replication - Sync to external systems
  • Alerting - Notify on specific conditions
Walk through each use case. Audit logging captures all data changes for compliance. Cache statistics can be computed from READ events to calculate hit/miss ratios. Workflow triggers start downstream processes when specific data changes. Replication to external systems like Elasticsearch or Kafka is a common integration pattern. Alerting can notify operations teams when specific conditions occur in the cache.

Stopping Event Listeners

// Keep reference to listener
IgnitePredicate<CacheEvent> listener = evt -> {
    // Handle event
    return true;
};

// Register
ignite.events().localListen(listener,
    EventType.EVT_CACHE_OBJECT_PUT);

// Later: unregister when done
ignite.events().stopLocalListen(listener);
Proper cleanup of event listeners is important to prevent memory leaks. Keep a reference to the listener so you can call stopLocalListen later. In production applications, register listeners during initialization and unregister them during shutdown. If you forget to unregister, the listener continues receiving events and consuming resources even if the processing code is no longer relevant.

Continuous Queries

Real-Time Notifications

Continuous queries are the most sophisticated notification mechanism in Ignite. Unlike cache events which fire on every operation, continuous queries filter on the server side and only push matching changes to the client. This makes them much more efficient for scenarios where you only care about specific data changes like stock price alerts or threshold monitoring.

What are Continuous Queries?

Continuous Queries provide real-time notifications when cache data matching specific criteria changes.

  • Server-side filtering
  • Push-based notifications
  • Low latency updates
  • Reduced network traffic
The four properties of continuous queries make them ideal for real-time applications. Server-side filtering means only relevant changes cross the network, reducing bandwidth. Push-based means the client receives updates immediately without polling. Low latency is achieved because the filter executes on the same node as the data. Reduced network traffic is the key advantage over polling or client-side event filtering.

Continuous Query Components


+-------------------+     +-------------------+
|   Cache Entry     |     |   Remote Filter   |
|   (on server)     | --> |   (on server)     |
+-------------------+     +-------------------+
                                   |
                              [matches?]
                                   |
                    Yes            v            No
                     +-------------------------+
                     |                         |
                     v                         v
          +------------------+          [discard]
          | Local Listener   |
          | (on client)      |
          +------------------+
                     |
                     v
          [Process notification]
This diagram shows the two components of a continuous query. The remote filter runs on the server where the cache entry lives. It evaluates each change and decides whether to forward it. Only matching changes are sent to the client where the local listener processes them. Non-matching changes are discarded on the server with no network cost. This architecture is key to efficiency.

Creating a Continuous Query

ContinuousQuery<Integer, Double> query = new ContinuousQuery<>();

// Local listener - called when filter matches
query.setLocalListener(events -> {
    for (CacheEntryEvent<? extends Integer, ? extends Double> e : events) {
        System.out.println("Key: " + e.getKey());
        System.out.println("Old: " + e.getOldValue());
        System.out.println("New: " + e.getValue());
    }
});

// Remote filter - runs on server, filters what gets sent
query.setRemoteFilterFactory(() ->
    event -> event.getValue() > 100.0  // Only notify if value > 100
);

// Start the continuous query
QueryCursor<Cache.Entry<Integer, Double>> cursor =
    cache.query(query);
This code shows the three components: the local listener that processes matching events on the client, the remote filter factory that creates the server-side filter, and the query execution. The remote filter checks if the value exceeds 100.0 and only matching events reach the local listener. Note that the cursor returned by cache.query must be kept open for the continuous query to remain active. Closing it stops the query.

Stock Price Alert Example

CacheConfiguration<String, Double> cfg =
    new CacheConfiguration<>("stockPrices");
IgniteCache<String, Double> cache = ignite.getOrCreateCache(cfg);

ContinuousQuery<String, Double> alertQuery = new ContinuousQuery<>();

// Alert when any stock goes above $150
alertQuery.setLocalListener(events -> {
    for (var event : events) {
        System.out.println("ALERT: " + event.getKey() +
            " price spiked to $" + event.getValue());
    }
});

alertQuery.setRemoteFilterFactory(() ->
    event -> event.getValue() > 150.0
);

try (QueryCursor<?> cursor = cache.query(alertQuery)) {
    cache.put("AAPL", 145.0);   // No alert
    cache.put("GOOGL", 155.0);  // ALERT!
    cache.put("AAPL", 160.0);   // ALERT!
}
The stock price alert example is a realistic use case that students can relate to. The filter checks if any stock price exceeds 150. AAPL at 145 does not trigger an alert, but GOOGL at 155 does. When AAPL is updated to 160, it also triggers. The try-with-resources on the cursor ensures the continuous query is properly closed when done. This pattern is used in financial systems, IoT monitoring, and real-time dashboards.

Complete Continuous Query Example

public class ContinuousQueryDemo {
    public static void main(String[] args) throws Exception {
        try (Ignite ignite = Ignition.start()) {
            IgniteCache<Integer, Double> cache =
                ignite.getOrCreateCache("prices");

            ContinuousQuery<Integer, Double> query =
                new ContinuousQuery<>();

            query.setLocalListener(events -> {
                for (var e : events) {
                    System.out.printf("Stock %d: $%.2f -> $%.2f%n",
                        e.getKey(), e.getOldValue(), e.getValue());
                }
            });

            // Filter: only prices > $100
            query.setRemoteFilterFactory(() -> evt -> evt.getValue() > 100.0);

            try (QueryCursor<?> cursor = cache.query(query)) {
                cache.put(1, 50.0);   // Below threshold - no notification
                cache.put(2, 150.0);  // Above - notification!
                cache.put(1, 120.0);  // Crosses threshold - notification!

                Thread.sleep(1000);   // Wait for notifications
            }
        }
    }
}
This complete example demonstrates the full continuous query workflow in a runnable main method. The Thread.sleep at the end is necessary to give time for asynchronous notifications to be processed. In a real application, the continuous query would run indefinitely. The three cache.put calls show different scenarios: below threshold (no notification), above threshold (notification), and crossing threshold (notification).

Initial Query Option

ContinuousQuery<String, Double> query = new ContinuousQuery<>();

// Set listener for updates
query.setLocalListener(events -> { /* handle updates */ });

// Also get existing entries matching a condition
query.setInitialQuery(new ScanQuery<>(
    (k, v) -> v > 100.0  // Get all stocks > $100
));

try (QueryCursor<Cache.Entry<String, Double>> cursor =
        cache.query(query)) {

    // First: iterate existing entries
    for (Cache.Entry<String, Double> entry : cursor) {
        System.out.println("Existing: " + entry.getKey() +
            " = $" + entry.getValue());
    }

    // Then: receive real-time updates via listener
}
The initial query option solves a common race condition: you want to get all existing matching entries AND subscribe to future changes. Without it, you would query first and then start the continuous query, potentially missing changes that happen between the two calls. With setInitialQuery, the cursor first returns existing matches, then the listener receives future changes. This ensures no data is missed during setup.

Continuous Query Use Cases

Best For

  • Real-time dashboards
  • Alert systems
  • Live data feeds
  • Event-driven architecture
  • Cache invalidation

Consider Carefully

  • High-frequency updates
  • Many active queries
  • Complex filter logic
  • Large result sets
The best-for and consider-carefully columns help students decide when continuous queries are appropriate. Real-time dashboards and alert systems are the primary use cases. For high-frequency updates, the notification overhead may become significant. For many active queries on the same cache, each one adds server-side processing overhead. Complex filter logic should be kept simple for performance.

Continuous Queries vs Events

Feature Continuous Query Cache Events
Filtering Server-side (efficient) Client-side only
Scope Specific cache All caches
Initial Data Yes (optional) No
Use Case Real-time updates Audit/monitoring
This comparison helps students choose between continuous queries and cache events. The key difference is filtering location: continuous queries filter on the server and are more efficient, while cache events filter on the client and are simpler to set up. Continuous queries support initial data retrieval while events do not. Use continuous queries for targeted real-time updates and events for broad monitoring and auditing.

Real-Time Notifications

Choosing the Right Approach

This section ties together all the notification approaches covered in the module. Students should understand when to use each one and be able to justify their choice based on the requirements. The decision flow on the next slide provides a quick reference for making this choice.

Notification Options Summary

Method Use When Filtering
Cache Events Audit, monitoring all changes Client-side
Continuous Queries Targeted real-time updates Server-side
Messaging (Pub/Sub) Custom notifications Topic-based
The three notification methods serve different purposes. Cache events are for broad monitoring of all cache activity. Continuous queries are for targeted real-time updates with server-side filtering. Messaging via pub/sub is for custom notifications that are not tied to specific cache operations. Most applications use continuous queries for real-time features and cache events for audit logging.

Decision Flow


Need real-time cache updates?
           |
     +-----+-----+
     |           |
    Yes          No --> Consider polling
     |
Need server-side filtering?
     |
+----+----+
|         |
Yes       No
|         |
|         +--> Cache Events
|              (all changes, filter client-side)
|
+--> Continuous Query
     (filtered updates, efficient)
This decision tree simplifies the choice. First ask if you need real-time updates -- if not, polling may be sufficient and simpler. If yes, ask if you need server-side filtering. If no, cache events with client-side filtering work fine. If yes, continuous queries are the right choice. Walk through this flow with a few example scenarios to cement the decision process.

Performance Considerations

Keep in Mind:

  • Continuous queries have overhead - use selectively
  • Events are disabled by default for performance
  • Remote filters reduce network traffic
  • Too many listeners can impact performance
  • Always close query cursors when done
These performance considerations are critical for production. Each continuous query and event listener adds overhead to every cache operation on the relevant nodes. Remote filters reduce network traffic but still have CPU cost on the server. Closing query cursors when done is essential to prevent resource leaks. In production, limit the number of active continuous queries and keep filters simple and fast.

Key Takeaways

  • Near caches reduce latency for read-heavy client workloads
  • Expiry policies manage data freshness (Created, Modified, Touched)
  • Eviction policies manage memory, not data lifetime
  • Entry processors enable atomic read-modify-write operations
  • Cache events provide monitoring and audit capabilities
  • Continuous queries deliver efficient real-time notifications
Reinforce each takeaway. The most important distinction students should remember is eviction versus expiry since they are commonly confused. Entry processors should be the default approach for any read-modify-write operation. Continuous queries should be used instead of polling for real-time features. These patterns are the building blocks for production-quality Ignite applications.
