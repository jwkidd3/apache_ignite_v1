SQL in Apache Ignite

Overview and Capabilities

This section introduces the SQL engine in Ignite. Many students are surprised to learn that Ignite supports full ANSI SQL. The key differentiator from a traditional RDBMS is that queries are automatically distributed across cluster nodes and executed in parallel.

SQL Engine Overview

Apache Ignite provides a fully-featured SQL engine that allows you to query distributed data using standard SQL syntax.

  • Built on Apache Calcite query optimizer
  • ANSI-99 SQL compliant
  • Distributed query execution
  • Automatic query parallelization
  • Cost-based optimization
Highlight that Ignite uses Apache Calcite as its query optimizer, which is the same optimizer used by many other systems like Apache Flink and Apache Druid. The cost-based optimization means Ignite chooses the best execution plan based on data statistics. Ask students if they have experience with EXPLAIN plans from other databases -- the concept is the same here.

ANSI-99 SQL Support

Category Supported Features
DDL CREATE, ALTER, DROP (tables, indexes, schemas)
DML INSERT, UPDATE, DELETE, MERGE
DQL SELECT, JOIN, UNION, subqueries
Aggregations COUNT, SUM, AVG, MIN, MAX, GROUP BY
Joins INNER, LEFT, RIGHT, FULL OUTER, CROSS
Functions String, numeric, date/time, aggregate
This table shows the breadth of SQL support. DDL lets you create tables and indexes dynamically. DML provides full data manipulation. The joins support is especially important for distributed queries. Point out that MERGE is supported which is useful for upsert operations. Students coming from Oracle or SQL Server will find the syntax familiar.

The three-stage architecture is standard for SQL engines. The parser validates syntax, the optimizer chooses the best execution plan, and the executor runs the query across nodes. The key insight is that the optimizer decides how to split the query across nodes and where to execute each part. This is what makes distributed SQL transparent to the developer.

SqlFieldsQuery API

Programmatic SQL Access

This section covers the Java API for executing SQL queries programmatically. SqlFieldsQuery is the primary class students will use in the lab. It provides full control over query execution parameters and is the most common way to run SQL from Java application code.

SqlFieldsQuery Basics

// Create a SqlFieldsQuery
SqlFieldsQuery query = new SqlFieldsQuery(
    "SELECT name, age, city FROM Person WHERE city = ?");

// Set parameters
query.setArgs("New York");

// Execute the query
List<List<?>> results = cache.query(query).getAll();

// Process results
for (List<?> row : results) {
    String name = (String) row.get(0);
    Integer age = (Integer) row.get(1);
    String city = (String) row.get(2);
    System.out.println(name + " - " + age + " - " + city);
}
Walk through this code line by line. The SqlFieldsQuery takes a SQL string with parameterized placeholders. setArgs provides the parameter values safely to prevent SQL injection. The result is a list of lists where each inner list is a row. Note the type casting required when extracting values -- this is a common source of ClassCastException errors students encounter.

Setting Up SQL Schema

// Configure cache with query entity
CacheConfiguration<Long, Object> cfg = new CacheConfiguration<>("Person");

// Define query entity (table schema)
QueryEntity personEntity = new QueryEntity(Long.class, Object.class);
personEntity.setTableName("Person");

// Define fields
LinkedHashMap<String, String> fields = new LinkedHashMap<>();
fields.put("id", "java.lang.Long");
fields.put("name", "java.lang.String");
fields.put("age", "java.lang.Integer");
fields.put("city", "java.lang.String");
fields.put("salary", "java.lang.Double");

personEntity.setFields(fields);
personEntity.setKeyFieldName("id");

cfg.setQueryEntities(Arrays.asList(personEntity));
cfg.setSqlSchema("PUBLIC");
This is the QueryEntity approach to defining SQL schemas programmatically. The LinkedHashMap preserves field order which matters for SQL table layout. The setKeyFieldName call tells Ignite which field is the primary key. Students often forget setSqlSchema which can cause tables to be invisible in SQL queries. The PUBLIC schema is the default and recommended for most use cases.

Query Options

SqlFieldsQuery query = new SqlFieldsQuery(sql);

// Set query timeout (milliseconds)
query.setTimeout(5000, TimeUnit.MILLISECONDS);

// Enable lazy result loading
query.setLazy(true);

// Set page size for pagination
query.setPageSize(1000);

// Enable distributed joins
query.setDistributedJoins(true);

// Set local execution only
query.setLocal(true);

// Enforce join order
query.setEnforceJoinOrder(true);

// Enable collocated mode
query.setCollocated(true);
These query options are critical for production use. setTimeout prevents runaway queries. setLazy is essential for large result sets to avoid memory issues. setDistributedJoins must be explicitly enabled for cross-node joins. setCollocated tells the optimizer that the query only touches colocated data, allowing optimizations. setEnforceJoinOrder overrides the optimizer's join order when you know better.

Cursor-Based Iteration

// For large result sets, use cursor-based iteration
SqlFieldsQuery query = new SqlFieldsQuery(
    "SELECT * FROM LargeTable");
query.setLazy(true);  // Enable lazy loading

try (QueryCursor<List<?>> cursor = cache.query(query)) {
    for (List<?> row : cursor) {
        // Process each row without loading all into memory
        processRow(row);
    }
}

// Or use iterator
try (QueryCursor<List<?>> cursor = cache.query(query)) {
    Iterator<List<?>> iterator = cursor.iterator();
    while (iterator.hasNext()) {
        List<?> row = iterator.next();
        processRow(row);
    }
}
Cursor-based iteration is essential for production code dealing with large datasets. The try-with-resources pattern ensures the cursor is closed even if an exception occurs. Without lazy mode, getAll() loads everything into memory which can cause OutOfMemory errors. Emphasize that the cursor must be closed or resources leak on the server side.

DDL and DML Operations

Data Definition & Manipulation

This section covers the full range of SQL data definition and manipulation operations. Students will see how to create tables, insert data, update records, and run complex queries all through SQL. This is the section where Ignite starts to feel like a traditional database to students with RDBMS backgrounds.

DDL: Creating Tables

// Create table using SQL DDL
cache.query(new SqlFieldsQuery(
    "CREATE TABLE IF NOT EXISTS Employee (" +
    "  id INT PRIMARY KEY," +
    "  name VARCHAR(100)," +
    "  department VARCHAR(50)," +
    "  salary DECIMAL(10,2)," +
    "  hire_date DATE" +
    ") WITH \"template=partitioned,backups=1\""
)).getAll();

// Create table with value type
cache.query(new SqlFieldsQuery(
    "CREATE TABLE Product (" +
    "  id INT PRIMARY KEY," +
    "  name VARCHAR," +
    "  price DECIMAL" +
    ") WITH \"VALUE_TYPE=com.example.Product\""
)).getAll();
The CREATE TABLE syntax is standard SQL with Ignite-specific WITH clause options. The template parameter controls whether the table is partitioned or replicated. The backups parameter sets the number of backup copies. Note the IF NOT EXISTS clause which makes the statement idempotent. The VALUE_TYPE option maps the table to a specific Java class for type-safe access.

DDL: Table Options

WITH clause options:

template=partitioned|replicated
backups=N
atomicity=ATOMIC|TRANSACTIONAL
cache_name=custom_name
key_type=com.example.KeyClass
value_type=com.example.ValueClass
affinity_key=column_name
The WITH clause options control how the underlying cache is configured. The template option is the most important -- partitioned distributes data across nodes while replicated copies to all nodes. The affinity_key option ties back to Module 05's colocation discussion. Setting atomicity to TRANSACTIONAL is required if you need multi-row transactions on this table.

DML: INSERT Operations

// Single INSERT with parameters
cache.query(new SqlFieldsQuery(
    "INSERT INTO Person (id, name, age, city, salary) " +
    "VALUES (?, ?, ?, ?, ?)")
    .setArgs(1L, "John Doe", 30, "New York", 75000.0)
).getAll();

// Batch INSERT
String insertSQL = "INSERT INTO Person VALUES (?, ?, ?, ?, ?)";
for (Person person : persons) {
    cache.query(new SqlFieldsQuery(insertSQL)
        .setArgs(person.getId(), person.getName(),
                 person.getAge(), person.getCity(),
                 person.getSalary())
    ).getAll();
}

// INSERT ... SELECT
cache.query(new SqlFieldsQuery(
    "INSERT INTO HighEarners SELECT * FROM Person WHERE salary > 100000")
).getAll();
Show the three INSERT patterns: single row with parameters, batch insert in a loop, and INSERT SELECT for copying data between tables. Always use parameterized queries to prevent SQL injection. The getAll() call at the end is required to execute the DML statement -- forgetting it is a common mistake. For bulk loading, consider using the streaming API instead of individual INSERTs for much better performance.

DML: UPDATE and DELETE

// UPDATE with WHERE clause
cache.query(new SqlFieldsQuery(
    "UPDATE Person SET salary = salary * 1.1 WHERE city = ?")
    .setArgs("New York")
).getAll();

// UPDATE multiple columns
cache.query(new SqlFieldsQuery(
    "UPDATE Employee SET department = ?, salary = ? WHERE id = ?")
    .setArgs("Engineering", 95000.0, 101)
).getAll();

// DELETE with condition
cache.query(new SqlFieldsQuery(
    "DELETE FROM Person WHERE age < ?")
    .setArgs(29)
).getAll();

// DELETE all (use with caution!)
cache.query(new SqlFieldsQuery("DELETE FROM TempTable")).getAll();
UPDATE and DELETE work as expected from standard SQL. The salary raise example shows arithmetic in the SET clause. Warn students about DELETE without WHERE -- it deletes all rows. In a distributed system, DML operations are coordinated across nodes that own the affected partitions. Mention that DML operations respect the cache's atomicity setting.

DQL: SELECT Queries

// Simple SELECT
SqlFieldsQuery query1 = new SqlFieldsQuery(
    "SELECT name, age, city FROM Person");

// WHERE clause with parameters
SqlFieldsQuery query2 = new SqlFieldsQuery(
    "SELECT name, age, salary FROM Person WHERE city = ?")
    .setArgs("New York");

// Aggregation with GROUP BY
SqlFieldsQuery query3 = new SqlFieldsQuery(
    "SELECT city, AVG(salary) as avg_salary " +
    "FROM Person GROUP BY city");

// ORDER BY with LIMIT
SqlFieldsQuery query4 = new SqlFieldsQuery(
    "SELECT name, salary FROM Person " +
    "ORDER BY salary DESC LIMIT 10");

// Results
cache.query(query3).getAll().forEach(row ->
    System.out.println(row.get(0) + ": $" + row.get(1)));
These SELECT examples show the range of query capabilities: simple select, parameterized WHERE, aggregation with GROUP BY, and ORDER BY with LIMIT. The aggregation query runs in a map-reduce fashion across nodes -- each node computes local aggregates which are then merged. LIMIT is important for large tables to avoid transferring excessive data across the network.

Complex Queries

// Subquery
SqlFieldsQuery subquery = new SqlFieldsQuery(
    "SELECT * FROM Employee " +
    "WHERE salary > (SELECT AVG(salary) FROM Employee)");

// CASE expression
SqlFieldsQuery caseQuery = new SqlFieldsQuery(
    "SELECT name, salary, " +
    "  CASE " +
    "    WHEN salary > 100000 THEN 'High' " +
    "    WHEN salary > 50000 THEN 'Medium' " +
    "    ELSE 'Low' " +
    "  END as salary_band " +
    "FROM Employee");

// HAVING clause
SqlFieldsQuery havingQuery = new SqlFieldsQuery(
    "SELECT department, COUNT(*) as emp_count " +
    "FROM Employee " +
    "GROUP BY department " +
    "HAVING COUNT(*) > 5");
These advanced query patterns show subqueries, CASE expressions, and HAVING clauses. The subquery example finds employees above average salary, which executes the inner query first across all nodes. CASE expressions are useful for data categorization in reports. HAVING filters groups after aggregation. These are all standard SQL patterns that work identically to traditional databases.

JDBC/ODBC Connectivity

Standard Database Access

JDBC and ODBC connectivity makes Ignite accessible from virtually any programming language or tool. This is often the easiest way for existing applications to start using Ignite. The thin JDBC driver requires no Ignite dependency on the client side -- just a standard JDBC connection string.

JDBC Thin Driver

JDBC URL Format:

jdbc:ignite:thin://host[:port][/schema][?parameters] 
// Register JDBC driver
Class.forName("org.apache.ignite.IgniteJdbcThinDriver");

// Connection URL
String JDBC_URL = "jdbc:ignite:thin://127.0.0.1:10800/";

// Establish connection
try (Connection conn = DriverManager.getConnection(JDBC_URL)) {
    System.out.println("Connected to Ignite!");

    // Execute queries using standard JDBC
    DatabaseMetaData metadata = conn.getMetaData();
    System.out.println("Driver: " + metadata.getDriverName());
}
The JDBC thin driver connects to port 10800 by default. The Class.forName call registers the driver, though with modern JDBC this is often optional due to auto-discovery. The connection URL format supports multiple hosts for failover. Students will use this JDBC approach in the lab. Common gotcha: make sure the Ignite node is running and the port is accessible before attempting the connection.

Using PreparedStatement

// Create table
try (Statement stmt = conn.createStatement()) {
    stmt.execute("CREATE TABLE IF NOT EXISTS Employee (" +
        "id INT PRIMARY KEY, " +
        "name VARCHAR, " +
        "department VARCHAR, " +
        "salary DECIMAL)");
}

// Insert with PreparedStatement
String insertSQL = "INSERT INTO Employee VALUES (?, ?, ?, ?)";
try (PreparedStatement pstmt = conn.prepareStatement(insertSQL)) {
    pstmt.setInt(1, 1);
    pstmt.setString(2, "Alice Johnson");
    pstmt.setString(3, "Engineering");
    pstmt.setDouble(4, 95000);
    pstmt.executeUpdate();
}
This shows standard JDBC PreparedStatement usage which students with Java experience will find familiar. The important point is that this is completely standard JDBC code that would work with any database. The only Ignite-specific part is the connection URL. This makes Ignite a drop-in replacement for many JDBC-based applications with minimal code changes.

Query with ResultSet

// Query with parameters
String querySQL = "SELECT name, department, salary FROM Employee " +
    "WHERE salary > ? ORDER BY salary DESC";

try (PreparedStatement pstmt = conn.prepareStatement(querySQL)) {
    pstmt.setInt(1, 80000);

    try (ResultSet rs = pstmt.executeQuery()) {
        System.out.println("Name              | Department    | Salary");
        System.out.println("------------------+---------------+--------");

        while (rs.next()) {
            String name = rs.getString("name");
            String dept = rs.getString("department");
            double salary = rs.getDouble("salary");
            System.out.printf("%-17s | %-13s | $%.2f%n",
                name, dept, salary);
        }
    }
}
The ResultSet example demonstrates column access by name which is more readable than index-based access. The try-with-resources pattern ensures proper cleanup. Note the formatted output using printf. Students should practice this pattern in the lab. A common mistake is not closing the ResultSet or PreparedStatement which can leak resources on the server.

Index Types

Optimizing Query Performance

Indexes are the single most important tool for query performance. Without proper indexes, Ignite must scan every partition on every node to answer a query. This section covers the types of indexes available and how to create them. Students should pay close attention as indexing decisions directly impact their lab exercise performance.

Types of Indexes

Primary

Automatic on key field
Unique constraint
B-tree structure

Secondary

On any field(s)
SORTED or FULLTEXT
Speed up queries

Composite

Multiple columns
Order matters
Range queries

Primary indexes are created automatically on the key field. Secondary indexes must be explicitly created on columns you query frequently. Composite indexes cover multi-column queries and the column order is critical -- the leftmost prefix rule applies just like in MySQL or PostgreSQL. Full-text indexes enable efficient text search on string fields.

Creating Indexes - Java API

// Define query entity with indexes
QueryEntity entity = new QueryEntity(Long.class, Product.class);
entity.setTableName("Product");

// Single-column SORTED index
QueryIndex nameIdx = new QueryIndex("name", QueryIndexType.SORTED);

// Single-column index with custom name
QueryIndex categoryIdx = new QueryIndex("category", QueryIndexType.SORTED);
categoryIdx.setName("idx_category");

// Composite index on multiple columns
QueryIndex compositeIdx = new QueryIndex(
    Arrays.asList("category", "price"), QueryIndexType.SORTED);
compositeIdx.setName("idx_category_price");

// Full-text index for text search
QueryIndex textIdx = new QueryIndex("description", QueryIndexType.FULLTEXT);

// Add all indexes
entity.setIndexes(Arrays.asList(nameIdx, categoryIdx, compositeIdx, textIdx));
This shows index creation through the Java API using QueryIndex objects. Each index has a type: SORTED for B-tree indexes and FULLTEXT for text search. Custom names help identify indexes in EXPLAIN output. The composite index on category and price is especially important -- it handles queries that filter on both columns efficiently. Students will create these exact indexes in the lab.

Creating Indexes - SQL DDL

-- Single-column index
CREATE INDEX idx_name ON Product (name);

-- Composite index
CREATE INDEX idx_cat_price ON Product (category, price);

-- Unique index
CREATE UNIQUE INDEX idx_email ON Customer (email);

-- Drop index
DROP INDEX idx_name;
SQL DDL index creation is simpler and can be done at runtime without restarting the cluster. This is the preferred approach for operational changes. The UNIQUE index enforces uniqueness which is useful for email addresses or other natural keys. DROP INDEX removes an index when it is no longer needed. Note that creating indexes on large tables can take time and temporarily impact performance.

Composite Index Ordering

Important: Column order in composite indexes matters!

Effective:

-- Index: (category, price)
-- These queries use the index:
WHERE category = 'Electronics'
WHERE category = 'Electronics'
  AND price < 500
WHERE category = 'Electronics'
  AND price BETWEEN 100 AND 500

Ineffective:

-- Index: (category, price)
-- These queries may NOT use index:
WHERE price < 500
-- (Missing leading column!)

WHERE price = 100
  AND category = 'Electronics'
-- (Order reversed, may not use)
This is one of the most important slides in the module. Column order in composite indexes follows the leftmost prefix rule. An index on (category, price) can be used for queries on category alone or category AND price, but NOT for price alone. This surprises many students. Use the analogy of a phone book sorted by last name then first name -- you can look up by last name, but not efficiently by first name alone.

Full-Text Search Index

// Create full-text index
QueryIndex textIdx = new QueryIndex("description", QueryIndexType.FULLTEXT);

// Query using LIKE (basic text search)
SqlFieldsQuery textQuery = new SqlFieldsQuery(
    "SELECT name, description FROM Product " +
    "WHERE description LIKE ?")
    .setArgs("%wireless%");

cache.query(textQuery).getAll().forEach(row ->
    System.out.println(row.get(0) + ": " + row.get(1)));
Note: Full-text indexes use more memory but enable efficient text search operations.
Full-text indexes use Lucene under the hood and are suitable for text search on description or comment fields. The LIKE operator with a prefix pattern can use a regular SORTED index, but for contains-type searches a FULLTEXT index is needed. Note that FULLTEXT indexes consume more memory and slow down writes since the Lucene index must be maintained.

Index Performance Impact

// Test query performance with timing
long startTime = System.currentTimeMillis();

// Query using single index
SqlFieldsQuery query1 = new SqlFieldsQuery(
    "SELECT name, price FROM Product WHERE category = ?")
    .setArgs("Electronics");
cache.query(query1).getAll();
System.out.println("Single index query: " +
    (System.currentTimeMillis() - startTime) + " ms");

// Query using composite index
startTime = System.currentTimeMillis();
SqlFieldsQuery query2 = new SqlFieldsQuery(
    "SELECT name, price FROM Product WHERE category = ? AND price < ?")
    .setArgs("Electronics", 500.0);
cache.query(query2).getAll();
System.out.println("Composite index query: " +
    (System.currentTimeMillis() - startTime) + " ms");
This code measures query performance with and without composite indexes. In the lab, students will see the dramatic difference between indexed and non-indexed queries. With thousands of rows, the difference can be 10x or more. Timing queries is a simple but effective way to validate index effectiveness. In production, use Ignite's built-in query metrics instead of manual timing.

Query Optimization

Understanding and Improving Performance

Query optimization is where theory meets practice. This section teaches students how to use EXPLAIN to understand query plans, how to identify performance bottlenecks, and how to fix them. These skills transfer directly to any SQL database. Encourage students to always check EXPLAIN before deploying queries to production.

EXPLAIN Query Plan

// View query execution plan
SqlFieldsQuery explainQuery = new SqlFieldsQuery(

cache.query(explainQuery).getAll().forEach(row ->
    System.out.println(row.get(0)));

// Output shows:
// - Index scans vs table scans
// - Join algorithms used

// - Sort operations
Example output:
SELECT
  PUBLIC.PRODUCT.NAME
FROM PUBLIC.PRODUCT
  /* PUBLIC.IDX_CATEGORY_PRICE: CATEGORY = 'Electronics' */

EXPLAIN is the most important debugging tool for SQL performance. Walk through the example output: it shows the index being used (IDX_CATEGORY_PRICE) and the filter conditions. Query Optimization Tips

Do:

  • Use indexed columns in WHERE
  • Create composite indexes for common query patterns
  • Use LIMIT for large result sets
  • Enable lazy loading for big queries
  • Use parameterized queries

Avoid:

  • SELECT * when not needed
  • Functions on indexed columns
  • Leading wildcards in LIKE
  • Unnecessary distributed joins
  • Cross joins without filters
The Do and Avoid lists are practical guidelines. The most common mistakes are SELECT * when only a few columns are needed, and applying functions to indexed columns which prevents index usage. Leading wildcards in LIKE bypass the index entirely. Parameterized queries allow plan caching. These tips apply universally to all SQL databases, not just Ignite.

Index Usage Patterns

-- Index on 'name' column

-- USES INDEX (equality)
SELECT * FROM Product WHERE name = 'Laptop';

-- USES INDEX (range)
SELECT * FROM Product WHERE name BETWEEN 'A' AND 'M';

-- USES INDEX (prefix pattern)
SELECT * FROM Product WHERE name LIKE 'Lap%';

-- DOES NOT USE INDEX (leading wildcard)
SELECT * FROM Product WHERE name LIKE '%top';

-- DOES NOT USE INDEX (function on column)
SELECT * FROM Product WHERE UPPER(name) = 'LAPTOP';

-- DOES NOT USE INDEX (expression)
SELECT * FROM Product WHERE price * 1.1 > 100;
This is a reference slide students should bookmark. It shows exactly which query patterns use indexes and which do not. The expression example at the bottom is subtle -- price * 1.1 > 100 cannot use the index, but rewriting it as price > 100/1.1 can. Similarly UPPER(name) prevents index use, but you can create a functional index or store a normalized column. These are common interview questions too.

Query Hints

// Force specific join order
SqlFieldsQuery query = new SqlFieldsQuery(sql)
    .setEnforceJoinOrder(true);

// Collocated mode - skip nodes without data
query.setCollocated(true);

// Local execution only
query.setLocal(true);

// Set query parallelism
query.setQueryParallelism(4);

Use setEnforceJoinOrder(true) when you know the optimal join order better than the optimizer.
Query hints give you manual control over the optimizer. setEnforceJoinOrder is useful when you know the data distribution better than the optimizer. setCollocated skips nodes that do not have relevant data. setLocal restricts execution to the local node only. setQueryParallelism increases intra-node parallelism for CPU-intensive queries. Always set timeouts in production to prevent runaway queries.

ANALYZE TABLE updates the statistics that the cost-based optimizer uses to choose execution plans. Distributed Joins

Joining Data Across Nodes

This section ties back to Module 05's colocation concepts and shows the practical SQL implications. Distributed joins are the most performance-sensitive SQL feature in Ignite. The key message is to design your data model so that frequently joined tables are colocated, avoiding distributed joins entirely when possible.

Colocated vs Distributed Joins

Colocated Joins

  • Data on same node
  • No network traffic
  • Fast execution
  • Uses affinity keys
Employee + Department
on SAME node

Distributed Joins

  • Data on different nodes
  • Requires network communication
  • Slower execution
  • Enabled explicitly
Data scattered
across nodes
The visual comparison makes the performance difference clear. Colocated joins execute entirely on one node with no network traffic. Distributed joins must send data between nodes to find matching rows. In production with millions of rows, this difference can be orders of magnitude. Always prefer colocated joins and only fall back to distributed joins when the data model cannot support colocation.

Enabling Distributed Joins

// Enable distributed joins on SqlFieldsQuery
SqlFieldsQuery distributedJoin = new SqlFieldsQuery(
    "SELECT e.name, e.salary, d.dept_name " +
    "FROM Employee e JOIN Department d ON e.dept_id = d.id " +
    "ORDER BY e.salary DESC")
    .setDistributedJoins(true);  // <-- Enable here

List<List<?>> results = empCache.query(distributedJoin).getAll();

results.forEach(row ->
    System.out.printf("%s - $%.2f - %s%n",
        row.get(0), row.get(1), row.get(2)));
Warning: Distributed joins are slower than colocated joins. Consider data modeling to avoid them when possible.
Note the setDistributedJoins(true) call which must be explicit. Without it, Ignite assumes the join is colocated and may return incorrect results if the data is not actually colocated. This is a safety mechanism. The warning box reinforces that distributed joins should be a last resort. In the lab, students will compare performance of colocated versus distributed joins to see the difference firsthand.

Affinity Colocation

// Define affinity key for colocation
public class OrderKey {
    @AffinityKeyMapped
    private Long customerId;  // Colocates orders with customers
    private Long orderId;

    public OrderKey(Long customerId, Long orderId) {
        this.customerId = customerId;
        this.orderId = orderId;
    }
}

// Now orders are stored on same node as their customer
// Joins between Customer and Order are colocated (fast!)
SqlFieldsQuery query = new SqlFieldsQuery(
    "SELECT c.name, o.total FROM Customer c " +
    "JOIN \"OrderCache\".Order o ON c.id = o.customerId");
// No need for setDistributedJoins(true) - data is colocated!
This example shows the complete picture: @AffinityKeyMapped on customerId in the Order key class ensures orders are stored on the same node as their customer. Then the SQL join between Customer and Order executes locally without network traffic. The comment at the bottom emphasizes that setDistributedJoins is not needed because the data is colocated by design. This is the ideal pattern to follow.

Join with Aggregation

// Complex join with aggregation
SqlFieldsQuery aggJoin = new SqlFieldsQuery(
    "SELECT d.dept_name, " +
    "       COUNT(e.id) as emp_count, " +
    "       AVG(e.salary) as avg_salary, " +
    "       MAX(e.salary) as max_salary " +
    "FROM Department d " +
    "LEFT JOIN Employee e ON d.id = e.dept_id " +
    "GROUP BY d.dept_name " +
    "ORDER BY avg_salary DESC")
    .setDistributedJoins(true);

empCache.query(aggJoin).getAll().forEach(row ->
    System.out.printf("%s: %d employees, avg $%.2f, max $%.2f%n",
        row.get(0), row.get(1), row.get(2), row.get(3)));
This example combines joins with aggregation which is common in reporting queries. The LEFT JOIN ensures departments with no employees still appear in the results. The GROUP BY and ORDER BY clauses work as in standard SQL. Note that setDistributedJoins is needed here since Employee and Department may not be colocated. In production, you would colocate these tables to avoid the distributed join overhead.

Distributed Join Best Practices

Design for Colocation First

  1. Identify frequently joined tables
  2. Use affinity keys to colocate related data
  3. Consider data denormalization
  4. Enable distributed joins only when necessary
Rule of thumb: If you frequently join two tables, they should share an affinity key.
The design-first approach is key: identify frequently joined tables during the design phase, use affinity keys to colocate them, and consider denormalization to avoid joins entirely. The rule of thumb at the bottom is practical: if two tables are joined in more than one query, they should share an affinity key. This may require schema redesign but the performance gains are worth it.

Query Performance Tuning

Advanced Optimization Techniques

This section covers advanced performance tuning techniques for production deployments. These are the knobs you turn after getting indexes and colocation right. Query parallelism, lazy execution, and memory configuration are all important for handling large-scale workloads. Students should treat this as reference material for when they move to production.

Query Parallelism

// Configure cache with query parallelism
CacheConfiguration<Long, Product> cfg = new CacheConfiguration<>("Product");
cfg.setQueryParallelism(4);  // Use 4 threads per node

// Or set per-query
SqlFieldsQuery query = new SqlFieldsQuery(
    "SELECT * FROM Product WHERE price > 100")
    .setQueryParallelism(4);
Parallelism guidelines:
  • Default is 1 (single-threaded)
  • Increase for large, complex queries
  • Don't exceed CPU cores
  • May increase memory usage
Query parallelism splits a single query across multiple threads within each node. The default of 1 is conservative. For analytical queries on large datasets, increasing to 4 or 8 can significantly reduce query time. However, higher parallelism uses more memory and CPU. Do not set it higher than the number of CPU cores on the node. This setting is independent of the number of cluster nodes.

Lazy vs Eager Execution

Eager (Default)

// Loads all results into memory
SqlFieldsQuery query =
    new SqlFieldsQuery(sql);

List<List<?>> results =
    cache.query(query).getAll();

// Good for small result sets
// All data available immediately

Lazy

// Streams results on demand
SqlFieldsQuery query =
    new SqlFieldsQuery(sql)
        .setLazy(true);

try (QueryCursor<List<?>> cursor =
        cache.query(query)) {
    for (List<?> row : cursor) {
        process(row);
    }
}
Use lazy execution for large result sets to avoid OutOfMemory errors.
Eager execution loads all results into memory at once which is fine for small result sets. Lazy execution streams results on demand which is essential for queries that return thousands or millions of rows. The try-with-resources pattern is critical for lazy queries because the cursor holds server-side resources that must be released. Default to lazy for production code unless you specifically need all results in memory at once.

Memory Configuration

// Configure SQL query memory limit
IgniteConfiguration cfg = new IgniteConfiguration();

// Set memory limit for queries
SqlConfiguration sqlCfg = new SqlConfiguration()
    .setQueryMemoryQuota("256M")  // Max memory per query
    .setQueryGlobalMemoryQuota("2G");  // Max for all queries

cfg.setSqlConfiguration(sqlCfg);
Memory-intensive operations:
  • Sorting large result sets
  • GROUP BY with many groups
  • Distinct on non-indexed columns
  • Cross joins
Memory quotas prevent individual queries from consuming all available memory. The per-query limit prevents a single bad query from impacting the cluster, while the global limit caps total SQL memory usage. The memory-intensive operations list helps students predict which queries need attention. Sorting large result sets is the most common memory hog because it requires materializing the entire result set in memory.

Troubleshooting Slow Queries

Symptom Possible Cause Solution
Query not using index No index on WHERE columns Create appropriate index
Full table scan Leading wildcard in LIKE Use prefix search or full-text index
Slow distributed join Data not colocated Use affinity keys
High memory usage Large result set Use lazy execution, add LIMIT
Timeout errors Query too complex Optimize query, add indexes
This troubleshooting table is a practical reference. Walk through each symptom-cause-solution row. The most common issue students encounter is queries not using indexes because the WHERE clause does not match the index structure. The slow distributed join is always solved by proper affinity key design from Module 05. High memory usage from large result sets is solved by lazy execution and LIMIT.

  3. Use composite indexes for multi-column filters
  4. Configure affinity for frequently joined tables

Lab Part 4: Distributed Joins

// Colocated join (fast)
SqlFieldsQuery colocatedJoin = new SqlFieldsQuery(
    "SELECT e.name, e.salary, d.dept_name " +
