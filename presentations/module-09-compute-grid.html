Distributed Computing Concepts

Harnessing the Power of the Cluster

This section introduces the fundamental idea behind compute grids. Ask students if they have experience with distributed computing frameworks like Hadoop MapReduce or Spark. Ignite's compute grid is similar in concept but tightly integrated with the in-memory data grid.

What is Compute Grid?

Compute Grid enables distributed execution of computationally intensive tasks across cluster nodes.

  • Execute code on any cluster node
  • Automatic load balancing
  • Failover support
  • Parallel processing
Stress that the compute grid lets you send code to execute where the data lives, rather than pulling data to a central location. This is the fundamental paradigm shift. The automatic load balancing and failover mean developers get distributed computing without managing the complexity themselves.

Compute Grid Architecture

    +------------------+
    |   Application    |
    +--------+---------+
             |
             v
    +------------------+
    |  IgniteCompute   |
    |   (Coordinator)  |
    +--------+---------+
             |
    +--------+---------+--------+
    |        |         |        |
    v        v         v        v
+------+ +------+ +------+ +------+
|Node 1| |Node 2| |Node 3| |Node N|
|Task A| |Task B| |Task C| |Task D|
+------+ +------+ +------+ +------+
             |
             v
    +------------------+
    |  Aggregated      |
    |    Results       |
    +------------------+
Walk through this diagram step by step. The application submits a task, IgniteCompute acts as coordinator to split and distribute work across nodes, each node processes its portion, and results are aggregated back. Point out that this happens transparently to the developer.

Key Benefits

Performance

  • Parallel execution
  • Data locality
  • Reduced latency

Reliability

  • Automatic failover
  • Task redistribution
  • Fault tolerance
Data locality is the biggest performance win. When you run computation on the same node that holds the data, you eliminate network transfer entirely. On the reliability side, if a node fails mid-computation, Ignite can automatically retry the task on another node without the application needing to handle it.

Compute vs Cache Operations

Aspect Cache Operations Compute Operations
Purpose Data storage/retrieval Task execution
Data Flow Data moves to client Code moves to data
Use Case CRUD operations Complex processing
This comparison helps students understand when to use compute vs regular cache operations. The key insight is the "Data Flow" row: with cache ops, data travels over the network to the client; with compute, the code travels to where data already resides. Use compute when you need to process large amounts of data without transferring it all.

IgniteCompute API

Your Gateway to Distributed Execution

Now we dive into the actual API. IgniteCompute is the main entry point for all distributed computation. Make sure students understand they can scope compute operations to specific subsets of the cluster using cluster groups.

Getting IgniteCompute


// Get compute instance for all cluster nodes
IgniteCompute compute = ignite.compute();

// Get compute for specific cluster group
ClusterGroup serverNodes = ignite.cluster().forServers();
IgniteCompute serverCompute = ignite.compute(serverNodes);

// Get compute for remote nodes only
ClusterGroup remoteNodes = ignite.cluster().forRemotes();
IgniteCompute remoteCompute = ignite.compute(remoteNodes);
Show that ignite.compute() targets all nodes by default. In production, you almost always want to target server nodes only, since client nodes are typically lightweight and not meant for heavy computation. The forRemotes() variant excludes the local node, which is useful when you want to offload work.

Core API Methods

Method Description
run() Execute Runnable (no return)
call() Execute Callable (with return)
broadcast() Execute on all nodes
execute() Execute ComputeTask
affinityRun() Run colocated with data
affinityCall() Call colocated with data
This table summarizes the six primary methods. Point out the pattern: run/call for single tasks, broadcast for all nodes, execute for MapReduce, and affinity variants for data-colocated execution. Each has both synchronous and async versions (with Async suffix).

Cluster Group Targeting


// Execute on server nodes only
ClusterGroup servers = ignite.cluster().forServers();
ignite.compute(servers).broadcast(() ->
    System.out.println("On server"));

// Execute on nodes with specific attribute
ClusterGroup highMem = ignite.cluster()
    .forAttribute("memory", "high");

// Execute on oldest node (primary coordinator)
ClusterGroup oldest = ignite.cluster().forOldest();

// Execute on random node
ClusterGroup random = ignite.cluster().forRandom();
Cluster groups give you fine-grained control over where tasks execute. The forAttribute approach is particularly useful in production where you tag nodes with capabilities like "high memory" or "GPU enabled." The oldest node is often used as a singleton coordinator since it is the most stable node in the topology.

Runnable and Callable Tasks

Simple Task Execution

These are the simplest forms of distributed compute. If students are familiar with Java's Runnable and Callable interfaces, they will feel right at home. Ignite's versions are serializable so they can be sent over the network to remote nodes.

IgniteRunnable - Fire and Forget


IgniteCompute compute = ignite.compute();

// Simple runnable - executes on one random node
compute.run(() -> {
    System.out.println("Hello from node: " +
        Ignition.ignite().cluster().localNode().id());
});

// Using IgniteRunnable interface
compute.run(new IgniteRunnable() {
    @Override
    public void run() {
        // Task logic here
        System.out.println("Task executed!");
    }
});

No return value - use for side effects

IgniteRunnable is the simplest compute primitive. The lambda form is concise but the explicit class form is useful when you need resource injection. Note that run() is synchronous and blocks until the remote node completes execution. The output appears on the remote node's console, not the caller's.

IgniteCallable - With Return Value


IgniteCompute compute = ignite.compute();

// Single callable with return value
String result = compute.call(() -> {
    return "Computed on node: " +
        Ignition.ignite().cluster().localNode().consistentId();
});
System.out.println("Result: " + result);

// Callable with explicit type
Integer square = compute.call(() -> {
    int value = 10;
    return value * value;  // Returns 100
});
IgniteCallable is like Runnable but returns a value. The result is serialized on the remote node and sent back over the network. Make sure students understand the serialization requirement: both the callable and its return type must be serializable. This is a common source of errors.

Multiple Callables - Parallel Execution


Collection<IgniteCallable<Integer>> calls = new ArrayList<>();
for (int i = 1; i <= 5; i++) {
    final int num = i;
    calls.add(() -> num * num);
}

// Execute in parallel across cluster
Collection<Integer> results = compute.call(calls);
// Results: [1, 4, 9, 16, 25]
When you pass a collection of callables, Ignite distributes them across the cluster using the configured load balancer. Each callable runs on a different node if possible. The results are collected and returned in order. This is an easy way to parallelize independent computations.

Injecting Resources


compute.run(new IgniteRunnable() {
    @IgniteInstanceResource
    private Ignite ignite;

    @Override
    public void run() {
        IgniteCache cache = ignite.cache("myCache");
        // Process locally...
    }
});
Resource injection is critical for accessing the local Ignite instance inside a compute task. The @IgniteInstanceResource annotation tells Ignite to inject the local Ignite instance before the task executes. Without this, you would need to call Ignition.ignite() which is less clean. This pattern is especially important for accessing caches and services from within tasks.

Broadcast Operations

Execute on All Nodes

Broadcast is used when you need every node in the cluster to execute the same task. This is fundamentally different from run/call which target a single node. Common real-world uses include cache warming, configuration updates, and cluster-wide diagnostics.

Broadcast Runnable


IgniteCompute compute = ignite.compute();

// Broadcast to ALL nodes in the cluster
compute.broadcast(() -> {
    System.out.println("[" +
        Ignition.ignite().cluster().localNode().consistentId() +
        "] Received broadcast message");
});

// Broadcast to specific cluster group
ClusterGroup servers = ignite.cluster().forServers();
ignite.compute(servers).broadcast(() -> {
    System.out.println("Running on server node");
});
The first example broadcasts to every node including clients. The second example scopes the broadcast to server nodes only using a cluster group. In production you typically broadcast only to servers. The call blocks until all nodes have completed execution.

Broadcast Callable - Collect Results


// Broadcast callable and collect results from all nodes
Collection<NodeInfo> nodeInfos = compute.broadcast(() -> {
    ClusterNode node = Ignition.ignite().cluster().localNode();

    return new NodeInfo(
        node.id().toString(),
        node.hostNames(),
        Runtime.getRuntime().availableProcessors(),
        Runtime.getRuntime().freeMemory()
    );
});

// Process results from all nodes
for (NodeInfo info : nodeInfos) {
    System.out.println("Node: " + info.getId() +
        ", CPUs: " + info.getCpus());
}
This pattern is extremely useful for building monitoring dashboards or health checks. Each node reports its own local information, and the caller collects all responses. The NodeInfo class must be serializable. This is a great way to build cluster-wide diagnostic tools.

Broadcast Use Cases

Common Uses

  • Cache warm-up
  • Configuration refresh
  • Health checks
  • Log level changes

Example


// Warm up cache on all nodes
compute.broadcast(() -> {
    IgniteCache cache =
        ignite.cache("myCache");
    cache.loadCache(null);
});
Cache warm-up via broadcast ensures every node loads its local partition data from the persistent store into memory. Configuration refresh is useful when you change external configs and need all nodes to re-read them. Log level changes via broadcast let you dynamically adjust logging across the entire cluster without restarts.

Affinity-Aware Computing

Colocate Compute with Data

This is arguably the most important concept in this module. Affinity-aware computing is what makes Ignite's compute grid truly powerful compared to generic distributed computing frameworks. The key idea is sending computation to the node that already owns the data, avoiding network transfers entirely.

The Data Locality Problem

Without Affinity:                    With Affinity:

+--------+     +--------+            +--------+     +--------+
| Client |     | Node 1 |            | Client |     | Node 1 |
|  App   |     | Data A |            |  App   |     | Data A |
+---+----+     +---+----+            +---+----+     | Task A |
    |              |                     |          +--------+
    | 1. Send Task |                     |              ^
    +------------->|                     | 1. Send Task |
    |              |                     +------------->|
    | 2. Fetch Data from Node 2          |              |
    |<-------------|                     | 2. Local Access
    |              |                     |              |
    | 3. Return Result                   | 3. Return Result
    |<-------------|                     |<-------------|

    NETWORK OVERHEAD!                    NO DATA TRANSFER!
This diagram is the key visual for this concept. On the left, the task lands on a node that does not own the data, so a network fetch is required. On the right, using affinity routing, the task is sent directly to the node that owns the data, so all access is local. In a large cluster with lots of data, this difference can be dramatic -- often 2 to 10 times faster.

affinityRun - No Return Value


// Run computation on the node where key 42 resides
ignite.compute().affinityRun("dataCache", 42, () -> {
    Ignite localIgnite = Ignition.ignite();
    IgniteCache<Integer, String> cache =
        localIgnite.cache("dataCache");

    // LOCAL access - no network transfer!
    String value = cache.localPeek(42);

    if (value != null) {
        System.out.println("Processing key 42 locally");
        System.out.println("Value: " + value);

        // Update locally
        cache.put(42, value.toUpperCase());
    }
});
The three arguments are: cache name, key, and the runnable. Ignite uses the cache name and key to determine which node is the primary owner, then sends the task there. Inside the task, localPeek() reads directly from local memory with zero network overhead. Note that cache.put() still goes through the normal path to ensure consistency with backup nodes.

affinityCall - With Return Value


// Call computation on node where data resides
Integer result = ignite.compute().affinityCall(
    "dataCache",
    key,
    new IgniteCallable<Integer>() {
        @IgniteInstanceResource
        private Ignite ignite;

        @Override
        public Integer call() throws Exception {
            IgniteCache<Integer, String> cache =
                ignite.cache("dataCache");

            // Local peek - no network!
            String value = cache.localPeek(key);
            return value != null ? value.length() : 0;
        }
    }
);
This is the callable variant that returns a result. The explicit class form is shown here to demonstrate @IgniteInstanceResource injection. The result is computed locally and then sent back to the caller. This pattern is ideal for read-heavy operations where you need to process data and return a derived value.

Performance Comparison


// Non-affinity computation (may require network transfer)
long start = System.currentTimeMillis();
for (int i = 0; i < 1000; i++) {
    final int key = i;
    compute.call(() -> {
        return cache.get(key).length();  // Network call!
    });
}
long nonAffinityTime = System.currentTimeMillis() - start;

// Affinity-aware computation (colocated with data)
start = System.currentTimeMillis();
for (int i = 0; i < 1000; i++) {
    final int key = i;
    compute.affinityCall("cache", key, () -> {
        return cache.localPeek(key).length();  // Local!
    });
}
long affinityTime = System.currentTimeMillis() - start;

// Affinity is typically 2-10x faster!
This benchmark is something students will run in the lab. The non-affinity version has two potential network hops: one to send the task and one for cache.get() to fetch the data. The affinity version has only one hop to send the task, and the data access is local. With 1000 iterations, the difference becomes very visible. Results vary by network latency and cluster size.

Affinity Best Practices

  • Use for data-intensive operations
  • Leverage localPeek() for reads
  • Group related data with affinity keys
  • Consider data distribution
Note: Affinity compute only helps when processing data. For pure computation, use regular compute.
Emphasize the warning: affinity routing adds overhead to determine the target node. If your task does not actually access cache data, regular compute with round-robin is simpler and equally fast. Also mention affinity colocation keys, which let you group related entries on the same node so a single affinity task can access multiple related records locally.

MapReduce Pattern

Distributed Data Processing

MapReduce is the most sophisticated compute pattern in Ignite. It gives you full control over how work is split (mapped) across nodes and how results are combined (reduced). This is Ignite's equivalent of Hadoop MapReduce but runs entirely in-memory.

MapReduce Concept

         +-------------+
         |    Input    |
         |    Data     |
         +------+------+
                |
        +-------+-------+
        |               |
        v               v
   +---------+     +---------+
   |   MAP   |     |   MAP   |
   | (Node 1)|     | (Node 2)|
   +---------+     +---------+
        |               |
        v               v
   +---------+     +---------+
   |Partial  |     |Partial  |
   |Results  |     |Results  |
   +---------+     +---------+
        |               |
        +-------+-------+
                |
                v
         +------+------+
         |   REDUCE    |
         | (Aggregate) |
         +------+------+
                |
                v
         +------+------+
         |   Final     |
         |   Result    |
         +-------------+
The MapReduce flow is: input data is split, map phase processes each split on its respective node producing partial results, and the reduce phase aggregates all partial results into the final answer. In Ignite, the map runs on the coordinator node to create the job assignments, the jobs execute on worker nodes, and reduce runs back on the coordinator.

ComputeTaskAdapter


public class WordCountTask
    extends ComputeTaskAdapter<String, Map<String, Integer>> {

    @IgniteInstanceResource
    private Ignite ignite;

    @Override
    public Map<ClusterNode, ComputeJob> map(
            List<ClusterNode> nodes, String cacheName) {
        // MAP: Split work and assign to nodes
        // ...
    }

    @Override
    public Map<String, Integer> reduce(
            List<ComputeJobResult> results) {
        // REDUCE: Aggregate partial results
        // ...
    }
}
ComputeTaskAdapter is the base class for MapReduce tasks. The two type parameters are the input argument type and the final result type. The map method receives the list of available nodes and the input argument, and returns a mapping of which job runs on which node. The reduce method receives all job results and produces the final output.

Map Phase - Distribute Work


@Override
public Map<ClusterNode, ComputeJob> map(
        List<ClusterNode> subgrid, String cacheName) {

    Map<ClusterNode, ComputeJob> map = new HashMap<>();
    IgniteCache<Integer, String> cache = ignite.cache(cacheName);

    // Create a job for each cache entry
    for (Cache.Entry<Integer, String> entry :
            cache.query(new ScanQuery<>())) {

        // Get the node where data resides (affinity)
        ClusterNode node = ignite.affinity(cacheName)
            .mapKeyToNode(entry.getKey());

        // Create job for this entry
        map.put(node, new WordCountJob(entry.getValue()));
    }

    return map;
}
The map phase uses affinity to ensure each job runs on the node that owns the data. The ScanQuery iterates all cache entries, and mapKeyToNode determines the primary owner. Note that if multiple entries map to the same node, only the last job assignment is kept in this simplified example. In production, you would batch entries per node.

ComputeJob - Process Data


public class WordCountJob implements ComputeJob {
    private final String text;

    public WordCountJob(String text) {
        this.text = text;
    }

    @Override
    public Map<String, Integer> execute() {
        Map<String, Integer> counts = new HashMap<>();

        if (text != null) {
            String[] words = text.toLowerCase().split("\\s+");
            for (String word : words) {
                counts.merge(word, 1, Integer::sum);
            }
        }

        return counts;  // Partial results
    }

    @Override
    public void cancel() { /* Handle cancellation */ }
}
Each ComputeJob processes its portion of the data independently. The text field is passed during construction and serialized to the target node. The execute method returns partial results (word counts for this chunk). The cancel method should clean up resources if the task is cancelled. Keep jobs lightweight and focused on a single unit of work.

Reduce Phase - Aggregate Results


@Override
public Map<String, Integer> reduce(
        List<ComputeJobResult> results) {

    Map<String, Integer> totalCounts = new HashMap<>();

    // Aggregate all partial results
    for (ComputeJobResult result : results) {
        Map<String, Integer> jobCounts = result.getData();

        for (Map.Entry<String, Integer> entry :
                jobCounts.entrySet()) {
            totalCounts.merge(
                entry.getKey(),
                entry.getValue(),
                Integer::sum
            );
        }
    }

    return totalCounts;  // Final aggregated result
}
The reduce phase runs on the originating node after all jobs complete. It merges all partial word count maps into a single total. The merge method with Integer::sum is a clean way to combine counts. Note that result.getData() returns the object from the job's execute method. You should also check result.getException() for failed jobs.

Executing MapReduce Task


// Populate cache with sample text data
cache.put(1, "hello world");
cache.put(2, "hello ignite");
cache.put(3, "world of computing");
cache.put(4, "ignite computing platform");
cache.put(5, "hello computing world");

// Execute MapReduce
Map<String, Integer> wordCounts =
    ignite.compute().execute(WordCountTask.class, "textCache");

// Print sorted results
wordCounts.entrySet().stream()
    .sorted(Map.Entry.<String, Integer>comparingByValue()
        .reversed())
    .forEach(e ->
        System.out.println(e.getKey() + ": " + e.getValue()));
// Output: hello: 3, world: 3, computing: 3, ignite: 2, ...
This ties together the complete MapReduce example. The execute method takes the task class and the argument (cache name). Ignite instantiates the task, calls map to create jobs, distributes them, waits for completion, then calls reduce. The sorted stream output shows the final aggregated word counts. Students will implement a similar example in the lab.

Load Balancing

Distribute Work Efficiently

Load balancing determines how tasks are distributed across cluster nodes. Ignite provides several built-in strategies and also lets you implement custom ones. Good load balancing is crucial for maximizing cluster utilization and avoiding hotspots.

Default Load Balancing

Ignite uses round-robin load balancing by default, distributing tasks evenly across available nodes.


// Tasks automatically distributed across nodes
for (int i = 0; i < 10; i++) {
    final int taskNum = i;
    compute.run(() -> {
        System.out.println("Task " + taskNum + " on node " +
            Ignition.ignite().cluster().localNode().consistentId());
    });
}
// Output: Tasks distributed to Node1, Node2, Node3, Node1, ...
Round-robin is simple and works well when all nodes have similar capacity and tasks have similar cost. The output shows tasks cycling through nodes sequentially. For heterogeneous clusters or variable task sizes, more sophisticated strategies may be needed.

Load Balancing Strategies

Strategy Description
Round Robin Default, sequential distribution
Random Random node selection
Weighted Based on node weights
Adaptive Based on current load
Custom User-defined SPI
Weighted balancing is good when nodes have different hardware specs. Adaptive balancing uses real-time CPU metrics to send tasks to the least loaded node, which handles variable task durations well. Custom SPI lets you implement any strategy, for example routing certain task types to specialized nodes.

Configuring Load Balancing


IgniteConfiguration cfg = new IgniteConfiguration();

// Use weighted round-robin load balancing
WeightedRandomLoadBalancingSpi spi =
    new WeightedRandomLoadBalancingSpi();
spi.setNodeWeight(node -> {
    // More weight to nodes with more memory
    return (int)(Runtime.getRuntime().maxMemory() / 1024 / 1024);
});

cfg.setLoadBalancingSpi(spi);

// Or use adaptive load balancing
AdaptiveLoadBalancingSpi adaptiveSpi =
    new AdaptiveLoadBalancingSpi();
adaptiveSpi.setLoadProbe(new AdaptiveCpuLoadProbe());

cfg.setLoadBalancingSpi(adaptiveSpi);
The weighted example assigns higher weight to nodes with more memory, so they receive more tasks proportionally. The adaptive example uses CPU load as the probe, meaning tasks are routed to nodes with the lowest current CPU utilization. Both are configured via the SPI mechanism on IgniteConfiguration before starting the node.

Failover Handling


// Ignite automatically handles node failures
IgniteConfiguration cfg = new IgniteConfiguration();

// Configure failover policy
AlwaysFailoverSpi failoverSpi = new AlwaysFailoverSpi();
failoverSpi.setMaximumFailoverAttempts(3);

cfg.setFailoverSpi(failoverSpi);

// Now if a task fails, it will be retried on another node
compute.run(() -> {
    // If this node fails mid-execution,
    // task is automatically resubmitted to another node
    processData();
});

Failover ensures high availability - tasks are never lost!

AlwaysFailoverSpi retries failed tasks on another node up to the configured maximum attempts. This is critical for long-running computations where a node crash would otherwise lose work. Be aware that tasks must be idempotent for failover to work correctly, since a task may have partially completed before the failure.

Async Execution

Non-Blocking Distributed Computing

All the compute methods we have seen so far are synchronous. The async variants return immediately with a future object, letting you continue other work while the task executes remotely. This is essential for high-throughput applications and complex workflows.

Async API Methods


IgniteCompute compute = ignite.compute();

// Async run
IgniteFuture<Void> runFuture = compute.runAsync(() -> {
    // Long-running task
    Thread.sleep(5000);
    System.out.println("Task completed");
});

// Async call
IgniteFuture<String> callFuture = compute.callAsync(() -> {
    Thread.sleep(3000);
    return "Async result";
});

// Continue with other work...
doOtherWork();

// Get results when needed
runFuture.get();  // Wait for completion
String result = callFuture.get();  // Get result
The pattern is simple: append Async to any compute method to get the non-blocking version. The returned IgniteFuture lets you check completion status, get results, or register callbacks. The get() call blocks until the result is available. Submit multiple async tasks to achieve parallelism without managing threads yourself.

Future with Timeout


IgniteFuture<String> future = compute.callAsync(() -> {
    Thread.sleep(10000);  // 10 second task
    return "Result";
});

System.out.println("Task submitted, doing other work...");
Thread.sleep(500);
System.out.println("Still working...");

try {
    // Wait up to 3 seconds for result
    String result = future.get(3, TimeUnit.SECONDS);
    System.out.println("Result: " + result);
} catch (IgniteFutureTimeoutException e) {
    System.out.println("Task taking too long!");
    future.cancel();  // Cancel the task
}
Timeouts prevent your application from blocking indefinitely on slow or stuck tasks. The get() with timeout throws IgniteFutureTimeoutException if the task does not complete in time. Always cancel the future after a timeout to free cluster resources. Consider what timeout values make sense for your use case and set them accordingly.

Async Callback (Listen)


IgniteFuture<String> future = compute.callAsync(() -> {
    return processData();
});

// Add callback for when task completes
future.listen(f -> {
    try {
        String result = f.get();
        System.out.println("Task completed: " + result);

        // Trigger next action
        processResult(result);
    } catch (IgniteException e) {
        System.err.println("Task failed: " + e.getMessage());
        handleError(e);
    }
});

// Continue immediately - callback will be invoked later
System.out.println("Callback registered, continuing...");
The listen method registers a callback that fires when the task completes, either successfully or with an error. This is the event-driven approach that avoids blocking entirely. The callback runs on the Ignite system thread pool, so keep it lightweight. For heavy post-processing, submit another async task from within the callback.

Timeout Configuration


// Set timeout for synchronous operations
try {
    compute.withTimeout(2000).call(() -> {
        System.out.println("Starting long task...");
        Thread.sleep(5000);  // This will timeout
        return "Completed";
    });
} catch (IgniteException e) {
    System.out.println("Task timed out as expected");
}

// Alternative: Use async with explicit timeout
IgniteFuture<String> future = compute.callAsync(() -> {
    Thread.sleep(5000);
    return "Result";
});

// Get with timeout
String result = future.get(2, TimeUnit.SECONDS);
There are two ways to set timeouts. The withTimeout method sets a timeout on the synchronous call itself, so it throws if the remote task exceeds the limit. The async approach with future.get(timeout) gives you more control since you can choose to wait longer or cancel. The withTimeout approach is simpler but less flexible.

Parallel Async Execution


// Submit multiple async tasks
List<IgniteFuture<Long>> futures = new ArrayList<>();

for (int i = 0; i < 10; i++) {
    final int taskId = i;
    IgniteFuture<Long> future = compute.callAsync(() -> {
        // Simulate heavy computation
        long sum = 0;
        for (long j = 0; j < 10_000_000; j++) {
            sum += j;
        }
        return sum;
    });
    futures.add(future);
}

// Collect all results
List<Long> results = new ArrayList<>();
for (IgniteFuture<Long> future : futures) {
    results.add(future.get());
}
System.out.println("All tasks completed: " + results.size());
This pattern submits all tasks first without blocking, then collects results. All 10 tasks run in parallel across the cluster. This is much faster than submitting them synchronously one at a time. The load balancer distributes the tasks across available nodes. For very large numbers of tasks, consider batching to avoid overwhelming the cluster.

Async Best Practices

  • Use async for long-running tasks
  • Always handle timeouts appropriately
  • Use callbacks for event-driven flows
  • Monitor resource usage
  • Consider cancellation scenarios
Recap the key async principles. Always set timeouts to prevent resource leaks from tasks that never complete. Monitor the public thread pool size to avoid exhausting it with too many concurrent tasks. Cancellation is important for user-facing applications where requests may be abandoned. Test your error handling paths thoroughly.

Advanced Compute Patterns

Production-Ready Techniques

This section covers patterns you will use in real production deployments. Targeted execution and cluster group chaining give you precise control over where tasks run, which is essential in multi-tenant or geographically distributed clusters.

Targeted Execution


// Execute on server nodes only
ClusterGroup serverNodes = ignite.cluster().forServers();
ignite.compute(serverNodes).broadcast(() ->
    System.out.println("Running on server: " +
        Ignition.ignite().cluster().localNode().consistentId()));

// Execute on nodes with specific attribute
ClusterGroup highMem = ignite.cluster()
    .forAttribute("memory", "high");

// Execute on oldest node (coordinator)
ClusterGroup oldest = ignite.cluster().forOldest();

// Execute on random node
ClusterGroup random = ignite.cluster().forRandom();
Node attributes are set in IgniteConfiguration and can represent any capability or characteristic. The oldest node is stable because it has been running the longest without crashing. Use forRandom() when you want simple load distribution without round-robin state tracking. These targeting mechanisms can be combined as shown in the next slide.

Cluster Group Chaining


// Complex cluster group selection
ClusterGroup targetNodes = ignite.cluster()
    .forServers()                           // Only servers
    .forAttribute("region", "us-west")      // In US West
    .forPredicate(node ->                   // With enough memory
        node.metrics().getHeapMemoryUsed() <
        node.metrics().getHeapMemoryMaximum() * 0.8
    );

// Execute on these specific nodes
ignite.compute(targetNodes).broadcast(() -> {
    System.out.println("Executing on target node");
});
Chaining cluster group filters creates increasingly specific node selections. This example targets only server nodes in the US West region that have less than 80% heap utilization. The forPredicate method uses real-time node metrics for dynamic filtering. This is powerful for geographic routing, resource-aware scheduling, and avoiding overloaded nodes.

Compute Best Practices Summary

Do

  • Use affinity for data tasks
  • Keep tasks small/focused
  • Handle failures gracefully
  • Use async for long ops
  • Set appropriate timeouts

Avoid

  • Very large task payloads
  • Blocking I/O in tasks
  • Ignoring exceptions
  • Infinite loops in tasks
  • Storing state in tasks
Review each point briefly. Large task payloads slow serialization; keep data in the cache and reference it by key instead. Blocking I/O ties up the compute thread pool. Infinite loops can make a task unfailable. Storing mutable state in task objects causes concurrency bugs since tasks may be reused or serialized. These are the most common mistakes in production compute grid usage.

Module Summary

Time to wrap up the module. Review the key concepts and make sure students understand when to use each compute pattern. The most important takeaway is the shift from moving data to moving computation.

Key Takeaways

Concept Key Points
IgniteCompute Gateway to distributed execution
Runnable/Callable Simple task execution patterns
Broadcast Execute on all cluster nodes
Affinity Colocate compute with data
MapReduce Distributed data processing
Load Balancing Automatic task distribution
Async Non-blocking execution
Go through each row briefly. IgniteCompute is the entry point. Runnable/Callable are the simplest patterns. Broadcast is for cluster-wide operations. Affinity is the performance optimization for data-bound tasks. MapReduce handles complex multi-step aggregations. Load balancing and async are cross-cutting concerns that apply to all patterns.

When to Use Each Pattern

  • run()/call() - Single task execution
  • broadcast() - Execute on all nodes
  • affinityRun()/affinityCall() - Data-intensive tasks
  • MapReduce - Complex aggregations
  • Async - Long-running operations
This is a quick decision guide. If you need to run something once, use run/call. If every node needs to do it, use broadcast. If you are processing specific cached data, use affinity. If you need to split-process-aggregate, use MapReduce. If any of these would block too long, add async. Students should bookmark this slide as a reference.
