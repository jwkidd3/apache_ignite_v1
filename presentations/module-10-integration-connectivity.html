REST API

HTTP-Based Access to Ignite

15 minutes - Language-agnostic access via HTTP endpoints
The REST API is the simplest way to interact with Ignite from any language or tool. It requires the ignite-rest-http module and exposes cache operations, SQL queries, and cluster management via HTTP. This is great for prototyping, monitoring dashboards, and polyglot environments.

REST API Overview

Use Cases

  • Multi-language clients
  • Web applications
  • Monitoring tools
  • Quick prototyping
  • Non-Java systems

Features

  • Cache operations
  • SQL queries
  • Cluster topology
  • Compute tasks
  • Metrics retrieval
The REST API supports all fundamental operations. On the left, note the use cases: it is particularly valuable when you have Python, Node.js, or other non-Java services that need to access Ignite data. On the right, the features cover cache CRUD, SQL execution, topology inspection, and even remote compute task invocation.

Enabling REST API

Add the REST HTTP module dependency:

<dependency>
    <groupId>org.apache.ignite</groupId>
    <artifactId>ignite-rest-http</artifactId>
    <version>2.16.0</version>
</dependency>
This single Maven dependency is all you need to enable REST support. The module bundles an embedded Jetty server that exposes the REST endpoints. Make sure this dependency is on the classpath of the node that will serve REST requests. Not every node needs it -- typically you enable it on one or two nodes behind a load balancer.

REST Configuration

import org.apache.ignite.configuration.ConnectorConfiguration;
import org.apache.ignite.configuration.IgniteConfiguration;

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setIgniteInstanceName("rest-node");

// Enable REST connector
ConnectorConfiguration connectorCfg = new ConnectorConfiguration();
connectorCfg.setPort(8080);
cfg.setConnectorConfiguration(connectorCfg);

// Start node with REST enabled
Ignite ignite = Ignition.start(cfg);

REST endpoint available at: http://localhost:8080/ignite

The ConnectorConfiguration class controls the REST endpoint settings. Port 8080 is a common choice but can be changed. The REST API is available at /ignite on the configured port. In production, you should put this behind a reverse proxy or API gateway for security, rate limiting, and SSL termination.

REST API Endpoints

Command Description Example
version Get Ignite version ?cmd=version
get Get cache value ?cmd=get&cacheName=X&key=Y
put Put cache value ?cmd=put&cacheName=X&key=Y&val=Z
top Cluster topology ?cmd=top
size Cache size ?cmd=size&cacheName=X
These are the most commonly used REST commands. The cmd parameter specifies the operation, and additional parameters provide context like cache name and key. The topology command is useful for monitoring. Note that all operations go through the node hosting the REST endpoint, which then routes to the appropriate data node internally.

REST API Examples

# Get Ignite version
curl http://localhost:8080/ignite?cmd=version

# Put a value in cache
curl "http://localhost:8080/ignite?cmd=put&cacheName=testCache&key=user1&val=John"

# Get a value from cache
curl "http://localhost:8080/ignite?cmd=get&cacheName=testCache&key=user1"

# Get all values
curl "http://localhost:8080/ignite?cmd=getall&cacheName=testCache&k1=user1&k2=user2"

# Get cluster topology
curl http://localhost:8080/ignite?cmd=top

# Execute SQL query
curl "http://localhost:8080/ignite?cmd=qryfldexe&pageSize=10&cacheName=myCache&qry=SELECT+*+FROM+Person"
Walk through each curl example. The put and get commands work with string keys and values by default. The getall command retrieves multiple keys at once. The SQL query command (qryfldexe) allows executing arbitrary SQL. Note that URL encoding is needed for special characters in queries. Students can test these directly in their browser or with curl.

// Successful GET response
{
  "successStatus": 0,

{

Spring Cache Abstraction

import org.springframework.cache.annotation.*;
import org.springframework.stereotype.Service;

@Service
public class UserService {

    @Cacheable(value = "userCache", key = "#userId")
    public User findUser(Long userId) {
        // This method result will be cached
        return userRepository.findById(userId);
    }

    @CachePut(value = "userCache", key = "#user.id")
    public User updateUser(User user) {
        return userRepository.save(user);
    }

    @CacheEvict(value = "userCache", key = "#userId")
    public void deleteUser(Long userId) {
        userRepository.deleteById(userId);
    }
}
This is one of the most powerful integrations. The @Cacheable annotation automatically caches method results in Ignite. On the first call, the method executes and the result is stored. Subsequent calls with the same key return the cached value without executing the method. @CachePut updates the cache, and @CacheEvict removes entries. The application code has no Ignite-specific imports at all.

Enable Caching with Ignite

import org.apache.ignite.cache.spring.SpringCacheManager;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.*;

@Configuration
@EnableCaching
public class CacheConfig {

    @Bean
    public SpringCacheManager cacheManager() {
        SpringCacheManager mgr = new SpringCacheManager();

        // Reference Ignite configuration
        mgr.setConfigurationPath("ignite-config.xml");

        // Or set programmatically
        // mgr.setConfiguration(igniteConfiguration());

        return mgr;
    }
}
The @EnableCaching annotation activates Spring's cache infrastructure. The SpringCacheManager bean connects Spring's caching abstraction to Ignite. You can point it to an XML configuration file or set the IgniteConfiguration programmatically. Once this is configured, all @Cacheable annotations in the application will use Ignite as the cache provider.

Auto-Configuration and Starters

Spring Boot takes the Spring integration further with auto-configuration. The ignite-spring-boot-autoconfigure module automatically sets up Ignite based on application properties, reducing boilerplate even more. This is the recommended approach for new Spring Boot projects.

<dependency>

Three dependencies are needed: the Spring Boot web starter, the Ignite auto-configuration module, and Ignite core. The auto-configure module detects Ignite on the classpath and sets up an Ignite instance automatically. You can override the default configuration with a custom IgniteConfiguration bean or through application properties.

Ignite Configuration Bean

@Configuration
public class IgniteConfig {

    @Bean
    public Ignite igniteInstance() {
        IgniteConfiguration cfg = new IgniteConfiguration();
        cfg.setIgniteInstanceName("springBootNode");
        cfg.setClientMode(false);

        // Configure caches
        CacheConfiguration<Long, User> userCache =
            new CacheConfiguration<>("userCache");
        userCache.setIndexedTypes(Long.class, User.class);

        cfg.setCacheConfiguration(userCache);

        return Ignition.start(cfg);
    }
}
This configuration bean creates and starts an Ignite instance as a Spring-managed bean. The @Bean annotation ensures Spring manages the lifecycle. Setting indexed types enables SQL queries on the cache. Note that setClientMode(false) makes this a server node. In a microservices architecture, you might set this to true for application nodes and have dedicated server nodes for data storage.

Ignite-Powered Service

@Service
public class IgniteUserService {

    @Autowired
    private Ignite ignite;

    @Cacheable(value = "userCache", key = "#userId")
    public String getUserName(int userId) {
        System.out.println("Fetching user " + userId + " from database...");
        // Simulate database call
        simulateDelay(1000);
        return "User-" + userId;
    }

    public void putToCache(String cacheName, Object key, Object value) {
        IgniteCache<Object, Object> cache =
            ignite.getOrCreateCache(cacheName);
        cache.put(key, value);
    }

    public Object getFromCache(String cacheName, Object key) {
        IgniteCache<Object, Object> cache = ignite.cache(cacheName);
        return cache != null ? cache.get(key) : null;
    }
}
This service demonstrates two approaches side by side. The getUserName method uses Spring's @Cacheable annotation for transparent caching. The putToCache and getFromCache methods use the Ignite API directly for more control. The @Autowired Ignite instance gives you full access to the Ignite API when annotations are not sufficient. The first call to getUserName will take 1 second; subsequent calls return instantly from cache.

REST Controller Example

@RestController
@RequestMapping("/api/users")
public class UserController {

    @Autowired
    private IgniteUserService service;

    @GetMapping("/{id}")
    public Map<String, Object> getUser(@PathVariable int id) {
        long start = System.currentTimeMillis();
        String userName = service.getUserName(id);
        long time = System.currentTimeMillis() - start;

        Map<String, Object> response = new HashMap<>();
        response.put("userId", id);
        response.put("userName", userName);
        response.put("responseTime", time + "ms");
        response.put("cached", time < 100);  // Fast = from cache

        return response;
    }
}
This controller shows how the caching is completely transparent to the REST layer. The response includes timing information so you can demonstrate the cache effect: the first request takes about 1 second (simulated DB call), while subsequent requests for the same user ID return in under a millisecond. The "cached" flag in the response makes this visible to the client.

Kafka Connector/Streamer

Real-Time Data Streaming

10 minutes - Stream data from Kafka into Ignite caches
Kafka integration is critical for real-time data pipelines. The Ignite Kafka streamer consumes messages from Kafka topics and loads them directly into Ignite caches using the high-performance DataStreamer. This enables real-time analytics on streaming data with sub-millisecond query latency.

Kafka + Ignite Architecture

+----------------+ +------------------+ +----------------+ | Kafka | | Ignite | | Applications | | Cluster | | Cluster | | | +----------------+ +------------------+ +----------------+ | | | v v v +----------------+ +------------------+ +----------------+ | Topic: | --> | KafkaStreamer | --> | SQL Queries | | events | | (Consumer) | | Cache Ops | | orders | | | | Compute | | metrics | | DataStreamer | | | +----------------+ +------------------+ +----------------+ | | | Real-time | +----> Ingestion -----+
This architecture shows the data flow: Kafka topics on the left produce events, the KafkaStreamer in the middle consumes and transforms them into cache entries, and applications on the right query the data using SQL, cache operations, or compute tasks. The key benefit is that data is queryable in Ignite within milliseconds of being produced to Kafka.

KafkaStreamer Configuration

import org.apache.ignite.stream.kafka.KafkaStreamer;
import org.apache.kafka.clients.consumer.ConsumerConfig;

// Configure Kafka consumer properties
Properties kafkaProps = new Properties();
kafkaProps.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG,
    "localhost:9092");
kafkaProps.put(ConsumerConfig.GROUP_ID_CONFIG,
    "ignite-group");
kafkaProps.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
    StringDeserializer.class.getName());
kafkaProps.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
    StringDeserializer.class.getName());
kafkaProps.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG,
    "earliest");
The Kafka consumer properties are standard Kafka configuration. The bootstrap servers point to your Kafka brokers. The group ID identifies this consumer group for offset management. Setting auto.offset.reset to "earliest" ensures you process all existing messages when starting fresh. In production, you may want "latest" to skip historical data.

Starting the Kafka Streamer

KafkaStreamer<String, String, String> kafkaStreamer = new KafkaStreamer<>();

// Configure streamer
kafkaStreamer.setIgnite(ignite);
kafkaStreamer.setStreamer(ignite.dataStreamer("kafkaCache"));
kafkaStreamer.setTopic("ignite-topic");
kafkaStreamer.setThreads(4);
kafkaStreamer.setConsumerConfig(kafkaProps);

// Set tuple extractor - transforms Kafka messages to cache entries
kafkaStreamer.setSingleTupleExtractor(msg -> {
    // Parse message: "key:value" format
    String[] parts = msg.split(":", 2);
    if (parts.length == 2) {
        return new AbstractMap.SimpleEntry<>(parts[0], parts[1]);
    }
    return null;
});

// Start streaming
kafkaStreamer.start();
System.out.println("Streaming from Kafka topic: ignite-topic");
The KafkaStreamer brings together the Ignite instance, a DataStreamer for the target cache, and the Kafka consumer configuration. The tuple extractor is the transformation function that converts each Kafka message into a cache key-value entry. Setting 4 threads allows parallel consumption. The DataStreamer automatically batches entries for optimal throughput.

Custom Message Transformations

// Complex transformation example
kafkaStreamer.setSingleTupleExtractor(
    new StreamSingleTupleExtractor<String, String, Order>() {

    @Override
    public Map.Entry<String, Order> extract(String message) {
        try {
            // Parse JSON message
            ObjectMapper mapper = new ObjectMapper();
            JsonNode node = mapper.readTree(message);

            String orderId = node.get("orderId").asText();
            Order order = new Order(
                orderId,
                node.get("customer").asText(),
                node.get("amount").asDouble()
            );

            return new AbstractMap.SimpleEntry<>(orderId, order);
        } catch (Exception e) {
            return null; // Skip malformed messages
        }
    }
});
This example shows a more realistic transformation that parses JSON messages from Kafka into domain objects. The ObjectMapper deserializes the JSON, and the extract method creates an Order object from the fields. Returning null skips malformed messages gracefully. In production, you should log skipped messages and monitor the skip rate to detect data quality issues.

CDC Architecture Pattern

Change Data Capture for Cache Synchronization

The Production Pattern: Write to OLTP, Read from Ignite
CDC is an increasingly popular pattern for keeping Ignite caches synchronized with a primary database. Instead of the application writing to both the database and the cache (dual write, which is error-prone), CDC captures changes from the database's write-ahead log and streams them into the cache. This gives you the reliability of an OLTP database with the speed of in-memory reads.

The Canonical Architecture

┌────────────┐ ┌──────────┐ ┌───────┐ ┌──────────┐ ┌────────┐ │ PostgreSQL │───>│ Debezium │───>│ Kafka │───>│ Consumer │───>│ Ignite │ │ (OLTP) │WAL │ (CDC) │ │ │ │ │ │(Cache) │ └────────────┘ └──────────┘ └───────┘ └──────────┘ └────────┘ ^ | | Application Layer | +--- writes to DB ---[ App reads from Ignite (fast!) ]<----+
Pattern: Write to OLTP, read from Ignite. CDC syncs automatically.
Walk through this diagram from left to right. PostgreSQL captures all changes in its WAL (write-ahead log). Debezium reads the WAL and publishes change events to Kafka topics. A consumer application reads from Kafka and updates the Ignite cache. The application writes to the database normally and reads from Ignite for fast access. The cache stays synchronized automatically without any dual-write logic in the application.

Write to OLTP, Read from Ignite

Why This Pattern?

  • OLTP handles write durability
  • Ignite handles read performance
  • Single source of truth (database)
  • Automatic cache synchronization
  • No dual-write complexity

Benefits

  • Sub-millisecond reads
  • ACID writes to database
  • Eventually consistent cache
  • No application code changes
  • Works with existing systems
The key advantage is separation of concerns. The database handles the hard problem of durable, ACID writes. Ignite handles the hard problem of fast, scalable reads. CDC bridges them automatically. "No application code changes" is a major selling point -- existing applications that write to the database continue to work unchanged, and you add Ignite reads where you need performance.

CDC Event Flow

DB Operation CDC Event Cache Action
INSERT CREATE (c) cache.put(key, value)
UPDATE UPDATE (u) cache.put(key, newValue)
DELETE DELETE (d) cache.remove(key)
Snapshot READ (r) cache.put(key, value)
Each database operation generates a corresponding CDC event type. The consumer maps these events to cache operations. INSERT and UPDATE both translate to cache.put, DELETE translates to cache.remove. The Snapshot/READ event occurs during initial snapshot capture when Debezium first connects and reads all existing data. This ensures the cache starts fully populated.

CDC vs Other Patterns

Pattern How It Works Consistency
CDC DB WAL → Kafka → Cache Eventual
Dual Write App writes to both Inconsistent!
Read-Through Load on cache miss Eventual
Write-Through Cache writes to DB Strong
Recommendation: CDC for read-heavy workloads. See Lab 13 (Bonus)!
This comparison is important for students to understand the trade-offs. Dual write is dangerous because if either write fails, you get inconsistency. CDC avoids this by having a single write path. Read-through loads data lazily on cache misses, which can cause latency spikes. Write-through provides strong consistency but makes Ignite the write path, which may not fit all architectures. CDC is best for read-heavy workloads with existing databases.

When to Use CDC

Good Fit

  • Existing OLTP database
  • Read-heavy workloads
  • Multiple consuming systems
  • Need eventual consistency
  • Legacy system integration

Consider Alternatives

  • Strong consistency required
  • Simple application (use write-through)
  • Ignite is primary store
  • Infrastructure overhead too high
CDC adds infrastructure complexity (Debezium, Kafka, consumer service), so it is best justified when you have a clear need. Legacy system integration is a particularly strong use case because you do not need to modify the existing application. If you need strong consistency or have a simple architecture, write-through or read-through may be better fits with less operational overhead.

Hibernate L2 Cache

Distributed ORM Caching

10 minutes - Use Ignite as Hibernate second-level cache
Hibernate's second-level cache is a session-factory-scoped cache that stores entity data across sessions. By default it uses in-process caching, but Ignite makes it distributed. This means entity data cached on one application server is available to all servers, dramatically reducing database load in clustered deployments.

Hibernate Cache Levels

+----------------------------------------------------------+ | Application | +----------------------------------------------------------+ | v +----------------------------------------------------------+ | Hibernate Session (L1 Cache) | | - Per-session scope | | - Automatic, always enabled | +----------------------------------------------------------+ | v +----------------------------------------------------------+ | Second-Level Cache (L2) [IGNITE] | | - SessionFactory scope | | - Shared across sessions | | - Distributed with Ignite | +----------------------------------------------------------+ | v +----------------------------------------------------------+ | Database | +----------------------------------------------------------+
The L1 cache is per-session and always active. The L2 cache sits between the session and the database, shared by all sessions in the SessionFactory. Without Ignite, L2 caching is local to each JVM. With Ignite, the L2 cache is distributed across the cluster, so an entity loaded by one app server is available to all others without hitting the database again.

Hibernate Configuration

<hibernate-configuration>
    <session-factory>
        <!-- Database settings -->
        <property name="connection.driver_class">org.h2.Driver</property>
        <property name="connection.url">jdbc:h2:mem:testdb</property>

        <!-- Enable Ignite L2 cache -->
        <property name="cache.use_second_level_cache">true</property>
        <property name="cache.use_query_cache">true</property>

        <!-- Ignite as cache provider -->
        <property name="cache.region.factory_class">
            org.apache.ignite.cache.hibernate.HibernateRegionFactory
        </property>

        <!-- Ignite instance configuration -->
        <property name="org.apache.ignite.hibernate.ignite_instance_name">
            hibernate-grid
        </property>
        <property name="org.apache.ignite.hibernate.default_access_type">
            READ_WRITE
        </property>
    </session-factory>
</hibernate-configuration>
Three key Hibernate properties enable the integration: use_second_level_cache turns on L2 caching, use_query_cache enables caching of query results, and cache.region.factory_class points to Ignite's implementation. The ignite_instance_name must match a running Ignite instance. The default_access_type sets the concurrency strategy for all entities unless overridden per-entity.

Cacheable Entity

import org.hibernate.annotations.Cache;
import org.hibernate.annotations.CacheConcurrencyStrategy;
import javax.persistence.*;

@Entity
@Table(name = "products")
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private Double price;

    // Constructors, getters, setters...
}
Each entity that should be cached needs two annotations: @Cacheable from JPA and @Cache from Hibernate with the concurrency strategy. READ_WRITE is the most commonly used strategy as it provides a good balance between performance and consistency. Without these annotations, the entity will not participate in L2 caching even though the cache provider is configured.

Cache Concurrency Strategies

Strategy Use Case Consistency
READ_ONLY Reference data, never changes Highest
READ_WRITE Read-mostly data High
NONSTRICT_READ_WRITE Rarely updated, occasional stale OK Medium
TRANSACTIONAL Full ACID requirements Strict
Choose the strategy based on your data's update frequency and staleness tolerance. READ_ONLY is the fastest but only works for immutable data like country codes or product categories. READ_WRITE uses soft locks to maintain consistency during updates. NONSTRICT_READ_WRITE has no locking and may serve stale data briefly after updates. TRANSACTIONAL provides full ACID but requires a JTA transaction manager and has the highest overhead.

Monitoring L2 Cache

// Enable statistics
sessionFactory.getStatistics().setStatisticsEnabled(true);

// First query - hits database
Session session1 = sessionFactory.openSession();
Product p1 = session1.get(Product.class, 1L);
session1.close();

// Second query - hits L2 cache!
Session session2 = sessionFactory.openSession();
Product p2 = session2.get(Product.class, 1L);
session2.close();

// Print statistics
Statistics stats = sessionFactory.getStatistics();
System.out.println("L2 Cache Hits: " + stats.getSecondLevelCacheHitCount());
System.out.println("L2 Cache Misses: " + stats.getSecondLevelCacheMissCount());
System.out.println("L2 Cache Puts: " + stats.getSecondLevelCachePutCount());
Hibernate statistics are essential for verifying that L2 caching is working. The first session.get causes a cache miss and a database query, then puts the result into L2 cache. The second session.get (in a different session) hits the L2 cache and avoids the database entirely. Monitor the hit ratio in production. A healthy L2 cache should have a hit ratio above 80% for read-heavy workloads.

L2 Cache Benefits

  • Reduced database load
  • Better application performance
  • Distributed caching across cluster
  • Automatic cache synchronization
  • Transparent to application code
The transparency is the key advantage. Existing Hibernate code works unchanged -- you just add annotations and configure the cache provider. The distributed nature means cache entries are shared across all application servers, unlike local L2 cache implementations like Ehcache (non-distributed mode). This eliminates redundant database queries from different servers for the same entity.

JDBC/ODBC Drivers

Standard SQL Connectivity

5 minutes - Connect using standard database drivers
Ignite provides standard JDBC and ODBC drivers, making it accessible from any tool or language that supports these protocols. This is particularly valuable for BI tools, reporting systems, and existing database-oriented applications that need to query Ignite data using familiar SQL interfaces.

JDBC Connection

import java.sql.*;

// JDBC connection URL format
String jdbcUrl = "jdbc:ignite:thin://localhost:10800";

// Alternative: specify schema
String jdbcUrlWithSchema = "jdbc:ignite:thin://localhost:10800/PUBLIC";

// Connect
try (Connection conn = DriverManager.getConnection(jdbcUrl)) {
    // Execute SQL
    Statement stmt = conn.createStatement();
    ResultSet rs = stmt.executeQuery(
        "SELECT * FROM Person WHERE age > 25"
    );

    while (rs.next()) {
        System.out.println(rs.getString("name") +
            ": " + rs.getInt("age"));
    }
}
The JDBC thin client connects to Ignite's client connector port (10800 by default). The connection URL format is straightforward. You can optionally specify a schema after the port. Standard JDBC operations like Statement, PreparedStatement, and ResultSet all work as expected. The thin JDBC driver is lightweight and does not require an Ignite node to be started in the client process.

JDBC with Connection Pooling

import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;

// Configure HikariCP
HikariConfig config = new HikariConfig();
config.setJdbcUrl("jdbc:ignite:thin://localhost:10800");
config.setMaximumPoolSize(10);
config.setMinimumIdle(5);
config.setConnectionTimeout(30000);

// Create datasource
HikariDataSource dataSource = new HikariDataSource(config);

// Use in application
try (Connection conn = dataSource.getConnection()) {
    PreparedStatement ps = conn.prepareStatement(
        "INSERT INTO Person (id, name, age) VALUES (?, ?, ?)"
    );
    ps.setLong(1, 1001);
    ps.setString(2, "John Doe");
    ps.setInt(3, 30);
    ps.executeUpdate();
}
In production, always use connection pooling. HikariCP is the recommended pool for Ignite JDBC connections. Each connection maintains a TCP socket to the Ignite cluster, so pooling avoids the overhead of repeatedly opening and closing connections. Set the pool size based on your application's concurrency needs. Ten connections is a good starting point for most applications.

Use ODBC for Excel, Power BI, Tableau, and other BI tools

ODBC allows non-Java tools to connect to Ignite using the standard ODBC interface. On Windows, you configure a DSN through the ODBC Data Source Administrator. On Linux, you edit the odbc.ini file. Once configured, tools like Excel, Power BI, and Tableau can connect to Ignite and query data using SQL, treating it like any other database.

JDBC Driver Types

Driver Connection String Use Case
Thin Client jdbc:ignite:thin://host:10800 Lightweight, remote access
Client Node jdbc:ignite:cfg://config.xml Full cluster participation
Recommendation: Use thin client JDBC for most applications - simpler setup and lower resource usage.
There are two JDBC driver types. The thin client driver connects via TCP and has minimal resource requirements. The client node driver actually starts an Ignite client node in the JVM, giving you full cluster participation including compute capabilities, but at higher resource cost. For most SQL-only use cases, the thin client driver is sufficient and much simpler to set up.

Client vs Server Nodes

Choosing the Right Node Type

5 minutes - Understanding node topology roles
Understanding node types is critical for designing a proper Ignite topology. Server nodes store data and execute compute tasks. Client nodes connect to the cluster without storing data. Thin clients are even lighter, using only a TCP connection. Each has its place depending on performance requirements and resource constraints.

Node Type Comparison

+--------------------+ +--------------------+ | SERVER NODE | | CLIENT NODE | +--------------------+ +--------------------+ | - Stores data | | - No data storage | | - Participates in | | - Lightweight | | compute grid | | - Routes requests | | - Full cluster | | - App integration | | member | | | | - Higher resources | | - Lower overhead | +--------------------+ +--------------------+ | | v v +--------------------+ +--------------------+ | Data Nodes | | Application | | Compute Nodes | | Servers | | Primary/Backup | | Web Tier | +--------------------+ +--------------------+
Server nodes are the backbone of the cluster. They hold data partitions, execute compute tasks, and participate in the discovery protocol. Client nodes are lighter: they do not store data but are full cluster members that can submit compute tasks and use near caches. The choice between them depends on whether your application needs to store data locally and how much memory you can dedicate to Ignite.

Server Node Configuration

IgniteConfiguration cfg = new IgniteConfiguration();

// Server mode (default)
cfg.setClientMode(false);

// Configure as data node
cfg.setDataStorageConfiguration(
    new DataStorageConfiguration()
        .setDefaultDataRegionConfiguration(
            new DataRegionConfiguration()
                .setMaxSize(2L * 1024 * 1024 * 1024) // 2GB
        )
);

// Start server node
Ignite ignite = Ignition.start(cfg);
System.out.println("Server node started: " + ignite.cluster().localNode().id());
Server mode is the default, so setClientMode(false) is optional but explicit. The DataStorageConfiguration sets memory limits. Here we allocate 2GB for the default data region. In production, size this based on your data volume plus overhead for indexes and metadata. Server nodes should run on dedicated machines or containers with sufficient memory and CPU.

Client Node Configuration

IgniteConfiguration cfg = new IgniteConfiguration();

// Enable client mode
cfg.setClientMode(true);

// Client-specific settings
cfg.setNetworkTimeout(10000);
cfg.setClientFailureDetectionTimeout(30000);

// Discovery configuration
TcpDiscoverySpi disco = new TcpDiscoverySpi();
TcpDiscoveryVmIpFinder ipFinder = new TcpDiscoveryVmIpFinder();
ipFinder.setAddresses(Arrays.asList(
    "server1:47500..47509",
    "server2:47500..47509"
));
disco.setIpFinder(ipFinder);
cfg.setDiscoverySpi(disco);

// Start client node
Ignite client = Ignition.start(cfg);
Client mode is enabled with setClientMode(true). The client joins the cluster topology but does not store data partitions. The failure detection timeout controls how long before a disconnected client is removed from the topology. The IP finder must list at least some server nodes for the client to discover the cluster. Client nodes are ideal for application servers that need full Ignite API access without data storage overhead.

Thin Client (Lightweight)

import org.apache.ignite.client.*;

// Thin client - even lighter than client node
ClientConfiguration cfg = new ClientConfiguration()
    .setAddresses("server1:10800", "server2:10800");

// Connect
try (IgniteClient client = Ignition.startClient(cfg)) {

    // Cache operations
    ClientCache<Integer, String> cache =
        client.getOrCreateCache("myCache");

    cache.put(1, "Hello");
    String value = cache.get(1);

    // SQL queries
    SqlFieldsQuery query = new SqlFieldsQuery(
        "SELECT * FROM Person WHERE age > ?"
    ).setArgs(25);

    try (QueryCursor<List<?>> cursor = cache.query(query)) {
        for (List<?> row : cursor) {
            System.out.println(row);
        }
    }
}
Thin clients are the lightest option. They use a simple TCP connection to port 10800 and do not join the cluster topology at all. This means zero discovery overhead and minimal memory usage. The trade-off is reduced functionality: no compute task submission, no continuous queries, and no near cache. For simple CRUD and SQL operations, thin clients are ideal. The try-with-resources pattern ensures proper cleanup.

When to Use Each Type

Node Type Best For Resources
Server Data storage, heavy compute, core cluster High (dedicated)
Client App servers, compute submission, near cache Medium
Thin Client Simple CRUD, SQL queries, low footprint Low (connection only)
This decision table helps students choose the right node type. Server nodes for the data tier, client nodes for application servers that need full API access, and thin clients for lightweight microservices or tools. A common architecture uses 3-5 dedicated server nodes with multiple client or thin client connections from application pods.

Client Node Features

Advantages

  • No data storage overhead
  • Near cache support
  • Full compute capabilities
  • Continuous queries
  • Fast data affinity

Considerations

  • Cluster topology impact
  • Discovery overhead
  • Memory for metadata
  • Connection management
Client nodes provide the richest feature set of all client options. Near cache support is especially valuable: it stores frequently accessed data locally on the client node for even faster reads. However, each client node adds to the cluster topology, and too many client nodes (hundreds) can strain the discovery protocol. For large-scale deployments with many application instances, thin clients may be more appropriate.

Integration Patterns Summary

Cache-Aside

Application manages cache explicitly

Read-Through

Cache loads from database on miss

Write-Through

Writes go to cache and database

Write-Behind

Async writes to database

These four patterns represent the fundamental approaches to integrating a cache with a database. Cache-aside gives the application full control. Read-through and write-through automate the cache-database synchronization. Write-behind adds asynchronous writes for better performance at the cost of durability risk. Understanding these patterns is essential for choosing the right architecture.

Choosing Integration Approach

Requirement Recommended Approach
Multi-language access REST API or Thin Client
Spring application Spring Cache + Spring Data
Streaming data Kafka Streamer
Existing Hibernate app L2 Cache integration
BI tools / SQL JDBC/ODBC drivers
High-performance Java Client or Server node
This is the key decision matrix for the module. Have students identify which row matches their use case. Many production deployments use multiple integration methods simultaneously. For example, a Spring Boot application might use Spring Cache for its own operations, expose data via JDBC for BI tools, and ingest data via Kafka. The approaches are complementary, not mutually exclusive.

Integration Best Practices

Do

  • Use thin clients for simple access
  • Pool JDBC connections
  • Configure proper timeouts
  • Enable SSL for production
  • Monitor integration points

Avoid

  • Too many client nodes
  • Unbounded Kafka consumers
  • Missing error handling
  • Synchronous calls in async code
  • Ignoring connection limits
Review each best practice. Connection pooling is critical for JDBC performance. SSL is mandatory for any production deployment handling sensitive data. Too many client nodes (more than about 100) can overload the discovery protocol. Kafka consumers should have bounded thread pools and backpressure handling. Every integration point should have proper error handling and monitoring dashboards.

Troubleshooting Integration

Issue Cause Solution
REST not responding Connector not configured Enable ConnectorConfiguration
L2 cache not working Missing @Cacheable Add entity annotations
Kafka not streaming Topic/broker issues Verify Kafka connectivity
JDBC timeout Server overload Add connection pooling
Client disconnects Discovery issues Configure IP finder properly
This troubleshooting table covers the most common integration issues students will encounter. REST not responding is usually a missing or misconfigured ConnectorConfiguration. L2 cache issues often come down to missing annotations on entities. Kafka problems typically stem from broker connectivity or topic configuration. JDBC timeouts suggest either connection exhaustion or slow queries. Client disconnects are usually discovery-related -- check firewall rules and IP finder configuration.
