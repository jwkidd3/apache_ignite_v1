Apache Ignite 3.x

Architecture & APIs

Module 13 | Apache Ignite Training
A ground-up rewrite for modern distributed computing

Welcome to Module 13. Ignite 3.x is a complete ground-up rewrite -- not an upgrade. The APIs, configuration, and architecture are fundamentally different from 2.x. Today we'll explore what changed, why, and how to work with the new APIs. Students will need Docker running for the lab exercises.

What's New in Ignite 3.x

A complete rewrite -- not an upgrade from 2.x

  • Schema-first design -- define tables via SQL DDL, not cache configurations
  • RAFT consensus -- consistent replication replaces 2.x's primary-backup
  • SWIM protocol -- lightweight cluster discovery replaces TcpDiscoverySpi
  • Pluggable storage engines -- choose page memory (volatile) or RocksDB (persistent)
  • Distribution Zones -- declarative control over data placement and storage profiles
  • Thin client only -- no embedded node mode; all apps connect as thin clients
  • HOCON configuration -- human-friendly config replaces XML/Spring
  • Strictly serializable transactions -- stronger consistency guarantees
Walk through each bullet point. Emphasize that this is NOT a version bump -- it's a new product. The 3.x codebase shares almost no code with 2.x. Key philosophical shift: 2.x was cache-first (define a cache, optionally query it), 3.x is schema-first (define a table via DDL, access it through multiple views). RAFT provides formally proven consensus vs 2.x's custom primary-backup protocol. SWIM discovery scales to thousands of nodes where 2.x ring topology had O(n) failure detection.

Ignite 3.x Architecture

┌─────────────────────────────────────────────────────────────┐ │ Client Application │ │ IgniteClient (thin client only) │ └──────────────────────────┬──────────────────────────────────┘ │ TCP (port 10800) ┌──────────────────────────▼──────────────────────────────────┐ │ Ignite 3.x Cluster │ │ │ │ ┌──────────┐ SWIM Protocol ┌──────────┐ │ │ │ Node A │◄──────────────────►│ Node B │ │ │ └────┬─────┘ └────┬─────┘ │ │ │ RAFT Consensus │ │ │ │◄─────────────────────────────►│ │ │ │ │ │ │ ┌────▼─────┐ ┌────▼─────┐ │ │ │ Storage │ │ Storage │ │ │ │ Engine │ │ Engine │ │ │ │(PageMem/ │ │(PageMem/ │ │ │ │ RocksDB) │ │ RocksDB) │ │ │ └──────────┘ └──────────┘ │ └─────────────────────────────────────────────────────────────┘
  • SWIM -- scalable failure detection and membership protocol
  • RAFT -- each partition has a RAFT group for leader election and log replication
  • Storage -- pluggable per distribution zone (volatile or persistent)
Walk through the diagram top to bottom. Client connects via TCP 10800 -- always a thin client, never joins the cluster. SWIM handles membership and failure detection using gossip -- each node periodically pings random peers and propagates membership changes. RAFT runs per partition group -- every data partition has a RAFT leader that handles writes and replicates to followers. Storage is pluggable per distribution zone -- aimem for pure in-memory volatile, aipersist for durable page memory, rocksdb for write-heavy persistent workloads. Ask: "Has anyone worked with RAFT before? etcd, CockroachDB, TiKV all use it."

Schema-First Philosophy

2.x Cache-First

// 2.x: define cache, then query
CacheConfiguration<Long, Person> cfg =
    new CacheConfiguration<>("persons");
cfg.setIndexedTypes(Long.class, Person.class);
IgniteCache<Long, Person> cache =
    ignite.getOrCreateCache(cfg);

3.x Schema-First

-- 3.x: define table via SQL DDL
CREATE TABLE persons (
    id   INT PRIMARY KEY,
    name VARCHAR,
    city VARCHAR
);

Then access via Table API, SQL, or KV view

Key shift: Tables are the primary abstraction. No more CacheConfiguration or @QuerySqlField annotations.
Show the side-by-side comparison. In 2.x, you had to create a CacheConfiguration, set indexed types, and configure affinity -- all in Java. In 3.x, a single CREATE TABLE statement handles everything. The schema is the source of truth. This means any client in any language can create tables -- not just Java. Ask students: "Which approach do you think is easier to maintain?" Point out that @QuerySqlField annotations in 2.x meant your domain model was coupled to the cache engine.

Connecting to Ignite 3.x

Builder pattern -- no embedded mode

try (IgniteClient client = IgniteClient.builder()
        .addresses("localhost:10800")
        .retryPolicy(new RetryLimitPolicy().retryLimit(5))
        .build()
) {
    // Use client.tables(), client.sql(), client.transactions(), etc.
}
Maven dependency: 
<dependency>
    <groupId>org.apache.ignite</groupId>
    <artifactId>ignite-client</artifactId>
    <version>3.1.0</version>
</dependency>
  • All applications are thin clients -- server nodes run independently via CLI or ignite3db
  • Automatic reconnect and retry policies built in
Key difference: In 2.x you chose between thick client (Ignition.start() with client mode) and thin client (Ignition.startClient()). In 3.x there's only IgniteClient -- always a thin client. The builder pattern is fluent and familiar. RetryPolicy handles transient connection failures. Note the Maven dependency uses ignite-client artifact (not ignite-core). Port 10800 is the standard client port, same as 2.x thin client.

Table API Overview

Multiple views onto the same table

ViewDescriptionUse Case
RecordView<Tuple> Schema-less tuples, full row access Dynamic schemas, prototyping
RecordView<POJO> Mapped to a Java class Type-safe domain objects
KeyValueView<K,V> Separate key and value types Cache-like get/put semantics 
// Obtain views from a table
Table table = client.tables().table("persons");

RecordView<Tuple>          tupleView = table.recordView();
RecordView<Person>         pojoView  = table.recordView(Person.class);
KeyValueView<Tuple, Tuple> kvTuple   = table.keyValueView();
KeyValueView<Long, Person> kvPojo    = table.keyValueView(Long.class, Person.class);
This is the core API students need to understand. One table, three views. RecordView is the most flexible -- no Java class needed, great for dynamic schemas. RecordView maps directly to a Java class by field name -- no annotations required, just matching field names. KeyValueView separates key and value -- closest to 2.x IgniteCache.get/put semantics. All views see the same data. You can insert via RecordView and read via SQL -- they're just different lenses on the same table.

RecordView with Tuples

Schema-less access -- no POJO needed

RecordView<Tuple> view = client.tables().table("persons").recordView();

// Insert
Tuple record = Tuple.create()
    .set("id", 1)
    .set("name", "Alice")
    .set("city", "New York");
view.upsert(null, record);

// Read
Tuple key = Tuple.create().set("id", 1);
Tuple result = view.get(null, key);
String name = result.stringValue("name");   // "Alice"
String city = result.stringValue("city");   // "New York"

// Delete
view.delete(null, key);
  • First argument is the transaction (null = auto-commit)
  • Tuple columns must match the DDL schema
Walk through the code. Tuple.create().set() is the builder pattern for creating records. The first argument to upsert/get/delete is always the transaction -- null means auto-commit. For reads, you only need to set the key columns in the Tuple. The API returns null if the key doesn't exist (check for null!). Batch operations available via getAll(), upsertAll(), deleteAll(). Compare with 2.x: cache.put(key, value) vs view.upsert(null, tuple) -- conceptually similar but tuple-based rather than key-value.

RecordView with POJOs

Type-safe mapping -- fields match column names

// POJO: field names must match DDL column names (case-insensitive)
public class Person {
    int id;
    String name;
    String city;
}

RecordView<Person> view = client.tables()
    .table("persons")
    .recordView(Person.class);

// Insert
Person alice = new Person();
alice.id = 1;
alice.name = "Alice";
alice.city = "New York";
view.upsert(null, alice);

// Read
Person key = new Person();
key.id = 1;
Person result = view.get(null, key);
System.out.println(result.name);  // "Alice"
  • No annotations required -- mapping is by field name
  • For reads, only the key fields need to be populated in the lookup object
Show how simple POJO mapping is. Field names must match column names (case-insensitive). No @QuerySqlField, no Serializable, no special annotations. Default constructor is required for deserialization. For reads, create a key object with just the PK field set. Compare with 2.x where POJOs needed @QuerySqlField(index=true) for indexed fields and had to implement Serializable. Much cleaner in 3.x.

KeyValueView

Familiar get/put semantics with separate key and value

KeyValueView<Long, Person> kvView = client.tables()
    .table("persons")
    .keyValueView(Long.class, Person.class);

// Put
Person alice = new Person();
alice.name = "Alice";
alice.city = "New York";
kvView.put(null, 1L, alice);

// Get
Person result = kvView.get(null, 1L);

// Contains
boolean exists = kvView.contains(null, 1L);

// Remove
kvView.remove(null, 1L);
When to use: KeyValueView is ideal when you think of data as key-value pairs and want the simplest possible API. RecordView is better when the key is part of the record.
KeyValueView is for teams that think in key-value terms. Separate key type and value type -- closest to 2.x IgniteCache semantics. put/get/contains/remove are the core operations. Note: the value object does NOT include the key fields (unlike RecordView where the record contains everything). When migrating from 2.x, KeyValueView is often the easiest path since the mental model is the same.

SQL in Ignite 3.x

First-class SQL with client.sql()

// DDL
client.sql().executeScript(
    "CREATE TABLE IF NOT EXISTS persons ("
    + "  id INT PRIMARY KEY, name VARCHAR, city VARCHAR"
    + ")"
);

// DML with parameters
client.sql().execute(null,
    "INSERT INTO persons (id, name, city) VALUES (?, ?, ?)",
    1, "Alice", "New York");

// Query
try (ResultSet<SqlRow> rs = client.sql().execute(null,
        "SELECT name, city FROM persons WHERE city = ?", "New York")) {
    while (rs.hasNext()) {
        SqlRow row = rs.next();
        System.out.println(row.stringValue("name"));
    }
}
  • executeScript() for DDL (multi-statement)
  • execute() returns ResultSet<SqlRow> -- implements AutoCloseable
  • First argument is transaction (null = auto-commit)
SQL is a first-class citizen in 3.x, not an overlay on the cache. executeScript() handles DDL and multi-statement batches. execute() is for DML and queries -- returns ResultSet which is AutoCloseable. Always use try-with-resources! Parameters use ? placeholders (positional). The first argument is the transaction. Compare with 2.x: cache.query(new SqlFieldsQuery("...")) returned List>. In 3.x, client.sql().execute() returns typed SqlRow objects with named column access.

Two key differences from 2.x: format and dynamism. HOCON (Human-Optimized Config Notation) replaces Spring XML -- more concise, supports comments, variable substitution. Distribution Zones

Declarative data placement via SQL DDL

-- Create a zone with specific replication and storage settings
CREATE ZONE us_east WITH
    replicas = 3,
    partitions = 100,
    storage_profiles = 'rocksdb';

-- Create a table in that zone
CREATE TABLE orders (
    order_id  INT PRIMARY KEY,
    customer  VARCHAR,
    total     DECIMAL(10,2)
) WITH PRIMARY_ZONE = 'US_EAST';
  • Replicas -- number of copies per partition (RAFT group size)
  • Partitions -- how data is split across nodes
  • Storage profiles -- rocksdb (persistent) or aipersist/aimem (page memory)
  • Tables are assigned to zones; zones control physical placement
2.x equivalent: Replaces CacheConfiguration.setBackups(), setAffinity(), and data region config -- all in one SQL statement.
Distribution Zones are one of the biggest architectural improvements. In 2.x, each cache independently configured its backups, partitions, and affinity function. In 3.x, a zone groups these settings and multiple tables can share a zone. Replicas maps to RAFT group size. Storage profiles let you choose the engine per zone -- rocksdb for write-heavy persistent data, aimem for pure speed. ALTER ZONE lets you change replicas dynamically -- in 2.x this required cache recreation. This is a key concept for the lab exercises.

COLOCATE BY

SQL-based data colocation

-- Parent table
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name        VARCHAR,
    region      VARCHAR
) WITH PRIMARY_ZONE = 'US_EAST';

-- Child table colocated with parent
CREATE TABLE orders (
    order_id    INT,
    customer_id INT,
    total       DECIMAL(10,2),
    PRIMARY KEY (order_id, customer_id)
) COLOCATE BY (customer_id)
  WITH PRIMARY_ZONE = 'US_EAST';
  • Rows with the same customer_id are stored on the same node
  • Enables efficient distributed JOINs without network shuffles
  • 2.x equivalent: Replaces @AffinityKeyMapped annotation and AffinityKey class
COLOCATE BY is the 3.x replacement for @AffinityKeyMapped. It ensures related data is partitioned together so JOINs are local. The colocation column must be part of the primary key. In 2.x, you had to create a custom key class with @AffinityKeyMapped -- Java-only and error-prone. In 3.x, it's a single clause in the DDL -- language-agnostic, any client benefits. Ask: "Why is data colocation important for distributed JOINs?" Answer: without colocation, the query engine must shuffle data across the network to match rows.

Transaction Model

Strictly serializable by default

IgniteTransactions txManager = client.transactions();

Transaction tx = txManager.begin();
try {
    RecordView<Tuple> accounts = client.tables()
        .table("accounts").recordView();

    Tuple from = accounts.get(tx, Tuple.create().set("id", 1));
    Tuple to   = accounts.get(tx, Tuple.create().set("id", 2));

    double amount = 100.0;
    accounts.upsert(tx, Tuple.create()
        .set("id", 1)
        .set("balance", from.doubleValue("balance") - amount));
    accounts.upsert(tx, Tuple.create()
        .set("id", 2)
        .set("balance", to.doubleValue("balance") + amount));

    tx.commit();
} catch (Exception e) {
    tx.rollback();
    throw e;
}
  • Read-write transactions are strictly serializable (strongest isolation)
  • Read-only transactions provide snapshot isolation
Big simplification from 2.x. In 2.x you had to choose PESSIMISTIC or OPTIMISTIC concurrency AND READ_COMMITTED, REPEATABLE_READ, or SERIALIZABLE isolation -- 6 combinations with subtle behavioral differences. In 3.x, all read-write transactions are strictly serializable (the strongest possible isolation). No choices, no confusion. RAFT ensures the ordering. Read-only transactions provide snapshot isolation for better read performance. Walk through the transfer example -- note the explicit tx.commit() and tx.rollback() in the catch block.

runInTransaction

Recommended approach with automatic retry

client.transactions().runInTransaction(tx -> {
    RecordView<Tuple> accounts = client.tables()
        .table("accounts").recordView();

    Tuple from = accounts.get(tx, Tuple.create().set("id", 1));
    Tuple to   = accounts.get(tx, Tuple.create().set("id", 2));

    double amount = 100.0;
    accounts.upsert(tx, Tuple.create()
        .set("id", 1)
        .set("balance", from.doubleValue("balance") - amount));
    accounts.upsert(tx, Tuple.create()
        .set("id", 2)
        .set("balance", to.doubleValue("balance") + amount));
});
Why use runInTransaction?
  • Automatic commit on success, rollback on exception
  • Automatic retry on transient conflicts
  • Cleaner code -- no manual try/catch/rollback
This is the RECOMMENDED pattern -- prefer this over manual begin/commit/rollback. Three advantages: automatic commit on success, automatic rollback on exception, and automatic retry on transient conflicts (like RAFT leader changes or lock timeouts). The lambda receives the Transaction object. No need for try/catch/finally. In the lab, students will use both patterns -- manual for understanding, runInTransaction for production-style code.

Mixed SQL + KV Transactions

New in 3.x -- combine SQL and Table API in one transaction

client.transactions().runInTransaction(tx -> {
    // KV operation: read account balance
    RecordView<Tuple> accounts = client.tables()
        .table("accounts").recordView();
    Tuple acct = accounts.get(tx, Tuple.create().set("id", 1));

    // SQL operation: insert audit log
    client.sql().execute(tx,
        "INSERT INTO audit_log (account_id, action, amount, ts) "
        + "VALUES (?, ?, ?, CURRENT_TIMESTAMP)",
        1, "DEBIT", 100.0);

    // KV operation: update balance
    accounts.upsert(tx, Tuple.create()
        .set("id", 1)
        .set("balance", acct.doubleValue("balance") - 100.0));
});
2.x limitation: In 2.x, SQL DML and cache operations used different transaction mechanisms and could not be mixed safely. Ignite 3.x unifies them.
This is a MAJOR new capability. In 2.x, SQL DML and cache operations used different transaction mechanisms internally, so mixing them could lead to inconsistencies. In 3.x, both go through the same RAFT-based transaction engine. The example shows: KV read, SQL insert, KV update -- all in one atomic transaction. This enables patterns like: update data via KV for speed, log the change via SQL for auditability, all atomically. Ask: "Can you think of use cases where mixing SQL and KV in one transaction would be valuable?"

Compute Grid

JobTarget, JobDescriptor, and Deployment Units

// Submit a compute job to a specific node
JobDescriptor<String, Integer> descriptor = JobDescriptor
    .<String, Integer>builder(WordCountJob.class)
    .units(DeploymentUnit.of("my-jobs", "1.0.0"))
    .build();

CompletableFuture<Integer> result = client.compute().executeAsync(
    JobTarget.anyNode(client.clusterNodes()),
    descriptor,
    "Hello World"
);

// Broadcast to all nodes
Map<ClusterNode, CompletableFuture<Integer>> results =
    client.compute().executeBroadcast(
        client.clusterNodes(),
        descriptor,
        "Hello World"
    );
  • Deployment Units -- versioned JARs deployed to the cluster via CLI
  • JobTarget -- control where jobs execute (specific node, any node, colocated)
  • Jobs implement ComputeJob<I, O> interface
Compute in 3.x works differently from 2.x. No more peer class loading -- jobs must be packaged as JARs and deployed as deployment units via the CLI before execution. This is more operational overhead but prevents class-loader leaks that plagued 2.x. JobTarget controls WHERE the job runs: anyNode (load-balanced), node (specific), or colocated (on the node holding specific data). JobDescriptor specifies WHAT to run (class name + deployment unit). The async API returns CompletableFuture instead of 2.x's custom IgniteFuture. In the lab, students will explore the API but note that actual job execution requires server-side deployment.

Compute: Deployment & Colocation

Server-side code requires explicit deployment

Deployment Workflow

# 1. Package job code as JAR
mvn package -f jobs/pom.xml

# 2. Deploy to cluster
ignite3 cluster unit deploy \
  --path=jobs/target/jobs.jar \
  --version=1.0 --id=my-jobs

# 3. List deployed units
ignite3 cluster unit list

Colocated Compute

// Run job on node holding key
JobTarget target = JobTarget.colocated(
    "orders",
    Tuple.create().set("order_id", 42));

client.compute().execute(
    target, descriptor, args);

Job runs where the data lives -- no data transfer needed

2.x had peer class loading (automatic bytecode transfer). 3.x replaces this with explicit deployment units -- more operational overhead but prevents class-loader leaks and versioning issues.
This slide explains the operational side of compute. In 2.x, you just wrote a Callable and called compute().call() -- peer class loading transferred the bytecode automatically. Convenient but caused class-loader leaks, version conflicts, and was a security concern. In 3.x, you must: 1) package your job classes as a JAR, 2) deploy the JAR to the cluster via CLI, 3) reference the deployment unit in your JobDescriptor. Colocated compute is powerful -- the job runs on the node that owns the data, so no data needs to travel across the network. This is the 3.x way to do what affinityCall() did in 2.x. For the lab, students will explore the API but won't deploy actual units (requires server-side setup). SQL aggregations serve as a practical alternative for many compute patterns.

Direct scraping -- no JMX exporter needed

Available metric groups: jvm (memory, GC, threads), client.handler (connections, requests), sql (queries), compute (jobs), raft (consensus). Enable via: ignite3 node metric source enable <name>
System views are queryable via standard SQL from any client. SYSTEM.TABLES shows all user tables, SYSTEM.ZONES shows distribution zone configuration, SYSTEM.NODES shows cluster membership. No sidecar JMX exporter needed -- Prometheus scrapes directly. Metric sources must be enabled first via CLI. Key groups: jvm for JVM stats, client.handler for connection metrics, sql for query metrics, raft for consensus metrics. In the lab, students will query system views and fetch metrics via HTTP.

Migration Checklist: 2.x to 3.x

  1. Audit feature usage -- identify dependencies on 2.x-only features (Service Grid, Continuous Queries, etc.)
  2. Convert cache configs to DDL -- replace CacheConfiguration with CREATE TABLE / CREATE ZONE
  3. Replace embedded nodes -- move to thin client (IgniteClient.builder())
  4. Replace XML/Spring config -- convert to HOCON configuration files
  5. Update data access code -- migrate from IgniteCache to Table API (RecordView/KeyValueView)
  6. Migrate SQL -- update queries for 3.x SQL engine; use client.sql().execute()
  7. Update transactions -- switch to runInTransaction() pattern
  8. Migrate compute jobs -- rewrite to ComputeJob<I,O> with deployment units
  9. Replace AffinityKey -- use COLOCATE BY in DDL
  10. Update monitoring -- switch from JMX to REST/OpenMetrics
Walk through each item. This is a FULL rewrite -- no incremental migration path. Emphasize item 1: audit feature usage FIRST. If you depend on Service Grid or Continuous Queries, stop and evaluate alternatives before proceeding. The most labor-intensive steps are typically 2 (cache configs to DDL) and 5 (data access code rewrite). Transaction changes (item 7) may surface concurrency bugs that 2.x's weaker isolation hid. Plan for thorough testing. Real-world migrations typically take weeks to months depending on codebase size.

When to Use 2.x vs 3.x

Stay on Ignite 2.x if:

  • You need Service Grid or Continuous Queries
  • You rely on embedded/thick client mode
  • Your app uses IGFS or Messaging APIs
  • You need MapReduce (ComputeTask)
  • Production stability is paramount and migration cost is high
  • You need near cache for latency-sensitive reads

Choose Ignite 3.x if:

  • Starting a new project (greenfield)
  • You want stronger consistency (RAFT)
  • SQL-first or schema-first design fits your needs
  • You need mixed SQL+KV transactions
  • You want modern config (HOCON) and monitoring (REST/Prometheus)
  • You need pluggable persistent storage (RocksDB)
This is the practical takeaway for architects. Left column: reasons to stay on 2.x. Right column: reasons to choose 3.x. For most greenfield projects, 3.x is the right choice. For existing 2.x deployments, the decision depends on feature dependencies. Ask students to think about their own projects and which column applies. Emphasize: 2.x is in maintenance mode but still receives security patches.
