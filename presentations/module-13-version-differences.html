1. The Big Picture

A Complete Rewrite, Not an Upgrade

Apache Ignite 3.0 is a ground-up architectural rewrite - it's not an incremental update from 2.x. Think of it as a new product built on lessons learned from Ignite 2.x.

Philosophy Shift

2.xCache-First

  • Data accessed via Cache API
  • Key-value operations primary
  • SQL layered on top of cache
  • Schema defined via Java annotations
  • Configuration embedded in application

3.xSchema-First

  • Schema defined upfront via SQL DDL
  • SQL is a first-class citizen
  • Multiple data access views
  • Language-agnostic schema definition
  • Cluster managed externally via CLI/REST

Java Version Requirements

2.16

  • Minimum: Java 8
  • Supports Java 8, 11, 17
  • Older codebases compatible
  • Uses older Java APIs and patterns

3.x

  • Minimum: Java 11
  • Designed for Java 11+ features
  • Modern API design (var, records, etc.)
  • Better memory management with newer JVMs

Impact: Projects still on Java 8 must upgrade to Java 11+ before adopting Ignite 3.x.

Timeline and Maturity

2. Architecture Comparison

Core Architectural Differences

Consensus and Replication

2.16

  • Custom replication protocol
  • Baseline topology for persistence
  • Manual partition management
  • Split-brain handling varies by config
  • Eventual consistency possible under failures

3.x

  • RAFT consensus algorithm
  • Automatic leader election per partition
  • Built-in split-brain protection
  • Guaranteed linearizable reads/writes
  • Zone-based replication (3.1+)

Why RAFT? It is an industry-standard consensus protocol (also used by etcd, CockroachDB, TiKV). It provides formally proven consistency guarantees that Ignite 2.x's custom protocol lacked.

Storage Architecture

Ignite 2.16

  • On-heap + Off-heap memory regions
  • Native persistence (optional, all-or-nothing per data region)
  • Single storage engine - page-based B+ tree
  • Write-Ahead Log (WAL) for durability
  • Checkpointing for persistence snapshots

Ignite 3.x

  • Pluggable storage engines per table:
    • aimem - Pure in-memory, volatile, lowest latency
    • aipersist - Memory-first with disk persistence, balanced
    • RocksDB - LSM-tree disk-based, write-optimized, large datasets
  • Choose engine per table via storage profiles

Storage Engine Selection Guide (3.x)

EngineBest ForLatencyDurabilityDataset Size
aimem Caching, sessions, temp data Sub-ms None (volatile) Fits in RAM
aipersist General purpose, OLTP Low ms Full RAM + Disk overflow
RocksDB Write-heavy, large datasets Higher ms Full Disk-bound 
-- Ignite 3.x: different engines for different tables
CREATE ZONE fast_zone WITH storage_profiles='in-memory-profile';
CREATE ZONE durable_zone WITH storage_profiles='persistent-profile';

CREATE TABLE sessions (...) WITH PRIMARY_ZONE='fast_zone';
CREATE TABLE orders (...) WITH PRIMARY_ZONE='durable_zone';

3. Discovery and Networking

How Nodes Find Each Other

Ignite 2.16: TcpDiscoverySpi

// Ignite 2.x - TcpDiscoverySpi with pluggable IP finders
TcpDiscoverySpi discoverySpi = new TcpDiscoverySpi();

// Option 1: Static IP list
TcpDiscoveryVmIpFinder ipFinder = new TcpDiscoveryVmIpFinder();
ipFinder.setAddresses(Arrays.asList(
    "192.168.1.10:47500..47509",
    "192.168.1.11:47500..47509"
));

// Option 2: Multicast (default, local network only)
TcpDiscoveryMulticastIpFinder multicast = new TcpDiscoveryMulticastIpFinder();
multicast.setMulticastGroup("228.10.10.157");

// Option 3: ZooKeeper
TcpDiscoveryZookeeperIpFinder zkFinder = new TcpDiscoveryZookeeperIpFinder();
zkFinder.setZkConnectionString("host1:2181,host2:2181");

// Option 4: Cloud-specific (AWS S3, GCE, Azure)
// Requires additional ignite-aws, ignite-gce modules

discoverySpi.setIpFinder(ipFinder);
discoverySpi.setLocalPort(47500);
discoverySpi.setLocalPortRange(10);
cfg.setDiscoverySpi(discoverySpi);

Ignite 2.16: Discovery Ring Topology

Ignite 2.x uses a RING topology for discovery: Node A ──> Node B ──> Node C ──> Node D ^ | └─────────────────────────────────┘ - Each node knows its "next" neighbor - Messages travel around the ring - Coordinator = first node in ring - Node failure detected by neighbor - Ring must be rebuilt on topology changes - Can be slow with many nodes (O(n) propagation)
  • Ports: Discovery on 47500-47509, Communication on 47100-47199
  • Protocols: Custom TCP protocol for both discovery and data

Ignite 3.x: Built-in Node Finder with SWIM

// Ignite 3.x HOCON configuration
ignite {
  network {
    port: 3344
    nodeFinder {
      // Simple list of seed nodes
      netClusterNodes: [
        "192.168.1.10:3344",
        "192.168.1.11:3344",
        "192.168.1.12:3344"
      ]
    }
  }
  clientConnector {
    port: 10800   // Client connections
  }
  rest {
    port: 10300   // REST API
  }
}

Key Change: Ignite 3.x uses a SWIM-based protocol (Scalable Weakly-consistent Infection-style process group Membership) for failure detection - faster and more scalable than the 2.x ring topology.

4. Cluster Lifecycle

Starting, Managing, and Stopping Clusters

Ignite 2.16: Embedded Lifecycle

// Ignite 2.x - cluster starts when first node starts
Ignite ignite = Ignition.start("ignite-config.xml");

// Cluster state management
ignite.cluster().state(ClusterState.ACTIVE);       // Activate
ignite.cluster().state(ClusterState.ACTIVE_READ_ONLY); // Read-only
ignite.cluster().state(ClusterState.INACTIVE);     // Deactivate

// Baseline topology (persistence only)
ignite.cluster().setBaselineTopology(
    ignite.cluster().forServers().nodes()
);

// Node types decided at startup
IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setClientMode(true);  // or false for server
  • Cluster forms automatically when nodes discover each other
  • Baseline topology must be managed manually when using persistence
  • Activation/deactivation controls data operations

Ignite 3.x: Explicit Cluster Initialization

# Step 1: Start nodes (they are idle until initialized)
ignite3 node start

# Step 2: Initialize cluster (explicit, one-time operation)
ignite3 cluster init \
  --name=myCluster \
  --meta-storage-node=node1 \
  --meta-storage-node=node2 \
  --meta-storage-node=node3

# Step 3: Check status
ignite3 cluster status
# Output: name=myCluster, status=active

# No activation/deactivation - cluster is always active once initialized
# No baseline topology - RAFT handles membership automatically

Key Differences:

  • 3.x requires explicit initialization - nodes don't auto-form a cluster
  • Meta-storage nodes hold cluster metadata (RAFT group)
  • No activation/deactivation states - cluster is always active
  • No baseline topology management

IgniteConfiguration cfg = new IgniteConfiguration();
cfg.setIgniteInstanceName("myCluster");
cfg.setPeerClassLoadingEnabled(true);

// Discovery
TcpDiscoverySpi disco = new TcpDiscoverySpi();

drc.setPersistenceEnabled(true);
dsc.setDefaultDataRegionConfiguration(drc);

// Cache configuration
CacheConfiguration<Integer, Person> cc = new CacheConfiguration<>("persons");
cc.setCacheMode(CacheMode.PARTITIONED);
cc.setBackups(1);
cc.setIndexedTypes(Integer.class, Person.class);
cfg.setCacheConfiguration(cc);

Ignite ignite = Ignition.start(cfg);

HOCON = Human-Optimized Config Object Notation (JSON superset)

Ignite 3.x: Dynamic Configuration via CLI

# View current cluster configuration
ignite3 cluster config show

# View specific section
ignite3 cluster config show --selector=storage

ignite3 cluster config update "gc.lowWatermark=0.3"

ignite3 node config show
ignite3 node config show --selector=network

# Update node configuration
ignite3 node config update "network.port=3345"

Dynamic configuration is a major advantage: most 2.x config changes require cluster restart, while 3.x supports live updates for many settings.

6. API Changes

From Cache API to Table API

Ignite 2.16: Cache API

// Starting Ignite 2.x
Ignite ignite = Ignition.start();

// Creating a cache
IgniteCache<Integer, Person> cache = ignite.getOrCreateCache("persons");

// CRUD operations
cache.put(1, new Person("John", "Doe"));
Person person = cache.get(1);
boolean removed = cache.remove(1);

// Batch operations
Map<Integer, Person> batch = new HashMap<>();
batch.put(1, new Person("John", "Doe"));
batch.put(2, new Person("Jane", "Smith"));
cache.putAll(batch);
Map<Integer, Person> results = cache.getAll(Set.of(1, 2));

// SQL query (layered on cache)
SqlFieldsQuery query = new SqlFieldsQuery(
    "SELECT * FROM Person WHERE lastName = ?");
query.setArgs("Doe");
List<List<?>> results = cache.query(query).getAll();

Ignite 3.x: Table API - RecordView

// Starting Ignite 3.x client
IgniteClient client = IgniteClient.builder()
    .addresses("localhost:10800")
    .build();

// Schema must exist first (created via SQL DDL)
// CREATE TABLE persons (id INT PRIMARY KEY, firstName VARCHAR, lastName VARCHAR)

// Getting a table
Table personTable = client.tables().table("persons");

// RecordView - Tuple-based (flexible, no Java class needed)
RecordView<Tuple> recordView = personTable.recordView();

Tuple record = Tuple.create()
    .set("id", 1)
    .set("firstName", "John")
    .set("lastName", "Doe");

recordView.upsert(null, record);
Tuple result = recordView.get(null, Tuple.create().set("id", 1));
boolean deleted = recordView.delete(null, Tuple.create().set("id", 1));

Ignite 3.x: Table API - KeyValueView

// KeyValueView - closest to Ignite 2.x Cache API
KeyValueView<Integer, Person> kvView =
    personTable.keyValueView(Integer.class, Person.class);

// Familiar put/get operations
kvView.put(null, 1, new Person("John", "Doe"));
Person person = kvView.get(null, 1);
kvView.remove(null, 1);

// Batch operations
kvView.putAll(null, Map.of(
    1, new Person("John", "Doe"),
    2, new Person("Jane", "Smith")
));
Map<Integer, Person> results = kvView.getAll(null, Set.of(1, 2));

Multiple views of the same data: RecordView (tuples), KeyValueView (key-value pairs), and SQL all access the same underlying table. Choose the view that fits your use case.

Ignite 3.x: SQL API

// SQL is a first-class citizen in 3.x
// Direct SQL execution (no need for a cache/table reference)
ResultSet<SqlRow> rs = client.sql().execute(null,
    "SELECT * FROM persons WHERE lastName = ?", "Doe");

while (rs.hasNext()) {
    SqlRow row = rs.next();
    System.out.println(row.stringValue("firstName"));
}

// DDL operations via SQL
client.sql().execute(null,
    "CREATE TABLE orders (id INT PRIMARY KEY, amount DECIMAL, personId INT)");

// DML operations
client.sql().execute(null,
    "INSERT INTO orders VALUES (1, 99.99, 1)");

// SQL is independent of any specific table/cache object
// No need for cache.query() or indexed types

Client Model Changes

2.16

  • Thick Client: Joins cluster, full functionality, peer class loading, runs compute tasks locally
  • Thin Client: Lightweight TCP, limited features (no compute, no continuous queries, no transactions initially)
  • Must choose based on needs
  • Thick client adds cluster overhead

3.x

  • Unified client protocol
  • All features via single client type
  • No thick/thin distinction
  • Consistent API across all languages
  • Clients never join the cluster
  • Reduced cluster overhead

Async API Differences

Ignite 2.16 - IgniteFuture (custom future type)

// Async operations return IgniteFuture
IgniteFuture<Person> future = cache.getAsync(1);
future.listen(f -> System.out.println("Got: " + f.get()));

// Or convert to CompletableFuture
CompletableFuture<Person> cf = future.toCompletableFuture();

Ignite 3.x - CompletableFuture (standard Java)

// Async operations return standard CompletableFuture
CompletableFuture<Tuple> future = recordView.getAsync(null, key);
future.thenAccept(t -> System.out.println("Got: " + t));

// Compose async operations naturally
recordView.getAsync(null, key1)
    .thenCompose(r -> recordView.upsertAsync(null, transform(r)))
    .thenAccept(v -> System.out.println("Done"));

7. SQL Improvements in 3.x

SQL as a First-Class Citizen

SQL Engine Evolution

Ignite 2.16

  • Originally H2-based SQL engine
  • Calcite engine added (newer, optional)
  • SQL queries execute via cache.query()
  • SQL transactions limited (KV transactions more robust)
  • Cannot mix SQL and KV in same transaction easily
  • Distributed joins can be slow without colocation

Ignite 3.x

  • Apache Calcite only - modern, optimized
  • SQL executed directly via client.sql()
  • Full SQL transaction support
  • Strictly serializable isolation
  • Mix SQL and KV operations in same transaction
  • Cost-based query optimization

SQL Transaction Example (3.x)

// Ignite 3.x - Full transactional SQL + KV in same transaction
try (Transaction tx = client.transactions().begin()) {
    // SQL operations
    client.sql().execute(tx,
        "INSERT INTO accounts (id, balance) VALUES (?, ?)", 1, 1000);

    client.sql().execute(tx,
        "UPDATE accounts SET balance = balance - 200 WHERE id = ?", 1);

    // Key-Value operations in SAME transaction
    KeyValueView<Integer, Account> kv =
        accountsTable.keyValueView(Integer.class, Account.class);
    kv.put(tx, 2, new Account(2, 2000));

    // Both SQL and KV committed atomically
    tx.commit();
} catch (Exception e) {
    // Automatic rollback on exception
}

RDBMS migration-friendly: Developers familiar with JDBC transactions will find Ignite 3.x's SQL transaction model natural.

Calcite SQL Engine Benefits

  • Cost-based optimization: Chooses optimal join order, index usage, and scan strategy based on table statistics
  • Better SQL standard compliance: More ANSI SQL features supported
  • Improved distributed joins: Smarter partition pruning and data movement
  • Extensible: Custom functions, type coercions, and optimization rules
  • Query plan caching: Compiled plans reused for repeated queries
-- Ignite 3.x: View query execution plan
EXPLAIN PLAN FOR
SELECT o.id, p.firstName, o.amount
FROM orders o JOIN persons p ON o.personId = p.id
WHERE o.amount > 100;

8. Schema Management

Defining Data Structures

Ignite 2.16: Annotation-Based Schema

// Define schema via Java annotations
public class Person implements Serializable {
    @QuerySqlField(index = true)
    private int id;

    @QuerySqlField
    private String firstName;

    @QuerySqlField(index = true)
    private String lastName;

    @QuerySqlField
    private int age;
}

// Register with cache configuration
CacheConfiguration<Integer, Person> cfg = new CacheConfiguration<>("persons");
cfg.setIndexedTypes(Integer.class, Person.class);
// OR use QueryEntity for more control:
QueryEntity qe = new QueryEntity(Integer.class, Person.class);
qe.setFields(new LinkedHashMap<>(Map.of(
    "id", Integer.class.getName(),
    "firstName", String.class.getName()
)));
cfg.setQueryEntities(Arrays.asList(qe));

Schema is tightly coupled to Java classes

Ignite 3.x: SQL DDL Schema

-- Create table using SQL DDL (language-agnostic)
CREATE TABLE persons (
    id INT PRIMARY KEY,
    firstName VARCHAR(100),
    lastName VARCHAR(100),
    age INT
) WITH PRIMARY_ZONE='default';

-- Create indexes separately
CREATE INDEX idx_lastname ON persons (lastName);
CREATE INDEX idx_age ON persons (age);

-- Alter table schema dynamically
ALTER TABLE persons ADD COLUMN email VARCHAR(200);
ALTER TABLE persons DROP COLUMN age;

-- Composite keys
CREATE TABLE order_items (
    orderId INT,
    itemId INT,
    quantity INT,
    price DECIMAL(10,2),
    PRIMARY KEY (orderId, itemId)
);

Key Change: Schema is defined via SQL DDL, not Java annotations. This makes it language-agnostic, familiar to DBA teams, and allows dynamic schema evolution.

9. Data Colocation and Distribution

Controlling Where Data Lives

Ignite 2.16: Affinity Keys

// Ignite 2.x - Affinity key for colocation
public class OrderKey implements Serializable {
    @AffinityKeyMapped
    private int customerId;  // Colocate with customer
    private int orderId;

    public OrderKey(int customerId, int orderId) {
        this.customerId = customerId;
        this.orderId = orderId;
    }
}

// Orders for same customer are on same node as customer
CacheConfiguration<OrderKey, Order> orderCfg = new CacheConfiguration<>("orders");
orderCfg.setBackups(1);

// Affinity function controls partitioning
RendezvousAffinityFunction af = new RendezvousAffinityFunction();
af.setPartitions(1024);  // Number of partitions
orderCfg.setAffinity(af);

// Affinity-aware operations
ignite.compute().affinityRun("orders", customerId, () -> {
    // Runs on the node that owns customerId's partition
});

Ignite 3.x: Distribution Zones

-- Ignite 3.x - Distribution Zones control data placement

-- Create zones with different replication and storage
CREATE ZONE hot_zone WITH
    replicas=3,
    partitions=256,
    storage_profiles='in-memory-profile';

CREATE ZONE warm_zone WITH
    replicas=2,
    partitions=512,
    storage_profiles='persistent-profile';

CREATE ZONE cold_zone WITH
    replicas=1,
    partitions=128,
    storage_profiles='rocksdb-profile';

-- Assign tables to zones
CREATE TABLE sessions (...) WITH PRIMARY_ZONE='hot_zone';
CREATE TABLE orders (...) WITH PRIMARY_ZONE='warm_zone';
CREATE TABLE audit_log (...) WITH PRIMARY_ZONE='cold_zone';

-- Colocation via colocation key
CREATE TABLE order_items (
    orderId INT,
    itemId INT,
    ...,
    PRIMARY KEY (orderId, itemId)
) COLOCATE BY (orderId)  -- Colocate with orders table
WITH PRIMARY_ZONE='warm_zone';

10. Compute Grid

Distributed Computing Differences

Ignite 2.16: Full-Featured Compute Grid

// IgniteCallable / IgniteRunnable - simple closures
ignite.compute().broadcast(() -> {
    System.out.println("Running on: " + Ignition.localIgnite().name());
});

// ComputeTask - full MapReduce
public class WordCountTask extends ComputeTaskAdapter<String, Map<String, Integer>> {
    @Override
    public Map<? extends ComputeJob, ClusterNode> map(
            List<ClusterNode> nodes, String arg) {
        // Map: distribute jobs to nodes
    }
    @Override
    public Map<String, Integer> reduce(List<ComputeJobResult> results) {
        // Reduce: aggregate results
    }
}
Map<String, Integer> result = ignite.compute().execute(new WordCountTask(), "input");

// Affinity-aware compute
ignite.compute().affinityRun("cache", key, () -> {
    // Runs on node owning the key's partition
});

// Service Grid - deploy long-running services
ignite.services().deployClusterSingleton("mySvc", new MyServiceImpl());

Ignite 2.16: Additional Compute Features

  • ComputeTaskSplitAdapter: Auto-split work across nodes
  • ComputeTaskSession: Share state between map and reduce phases
  • Failover SPI: Automatic job retry on node failure
  • Load Balancing SPI: Round-robin, weighted, adaptive
  • Peer Class Loading: Deploy code dynamically to cluster
  • Continuous Computation: Long-running distributed computations
  • ExecutorService: Standard Java ExecutorService over the grid
// Use cluster as a standard Java ExecutorService
ExecutorService exec = ignite.executorService();
Future<String> future = exec.submit(() -> "computed on grid");
String result = future.get();

Ignite 3.x: Simplified Compute

// Ignite 3.x - Simplified compute API
// Execute on specific nodes
Set<ClusterNode> nodes = client.clusterNodes();

// Run a job on all nodes (broadcast)
Map<ClusterNode, String> results = client.compute()
    .execute(nodes, MyJob.class, "arg");

// Run on a single node
String result = client.compute()
    .execute(Set.of(targetNode), MyJob.class, "arg");

// Colocated compute - run on node owning the key
String result = client.compute()
    .executeColocated("tableName", Tuple.create().set("id", 42),
        MyJob.class, "arg");

Status: Ignite 3.x compute is functional but still evolving. It supports basic job execution and colocated compute. Full MapReduce, Service Grid, peer class loading, and failover SPI are not yet available in 3.x.

11. Serialization

How Data Is Stored and Transferred

Ignite 2.16: Binary Object Marshaller

// Ignite 2.x - BinaryObject for schema-less access
IgniteCache<Integer, BinaryObject> binaryCache =
    cache.withKeepBinary();

// Access fields without deserializing to Java class
BinaryObject bo = binaryCache.get(1);
String name = bo.field("firstName");
int age = bo.field("age");

// Modify without full deserialization
BinaryObject modified = bo.toBuilder()
    .setField("age", 31)
    .build();
binaryCache.put(1, modified);
  • BinaryMarshaller: Default, schema-aware binary format
  • BinaryObject: Access data without deserializing to Java class
  • Java Serializable also supported but slower
  • Objects stored in binary format on-heap and off-heap
  • Schema tracked per type across cluster

Ignite 3.x: Schema-Based Serialization

// Ignite 3.x - Tuple-based access (no serialization concern for users)
RecordView<Tuple> view = table.recordView();

// Tuples are schema-aware - fields validated against table schema
Tuple record = Tuple.create()
    .set("id", 1)
    .set("firstName", "John")
    .set("lastName", "Doe");
view.upsert(null, record);

// Typed (POJO) mapping with automatic marshalling
RecordView<Person> typedView = table.recordView(Person.class);
typedView.upsert(null, new Person(1, "John", "Doe"));
Person p = typedView.get(null, new Person(1));  // Only key fields needed
  • Schema defined by SQL DDL, not by Java class structure
  • Internal serialization format based on table schema
  • Tuples: flexible, no Java class needed
  • POJOs: automatic mapping to/from table columns
  • No BinaryObject concept - data always schema-bound

19. Migration Considerations

From 2.x to 3.x

No Direct Migration Path

There is no in-place upgrade from Ignite 2.x to 3.x. The architectural differences are too significant. Migration requires:

  1. Setting up a new Ignite 3.x cluster
  2. Recreating schema using SQL DDL
  3. Migrating data (export/import or dual-write)
  4. Updating all application code
  5. Replacing integrations (Spring, Kafka, etc.)

Code Migration Examples

// === Connection ===
// 2.x: Embedded node
Ignite ignite = Ignition.start(cfg);
// 3.x: External client
IgniteClient client = IgniteClient.builder().addresses("localhost:10800").build();

// === Data Access ===
// 2.x: Cache API
IgniteCache<Integer, Person> cache = ignite.cache("persons");
cache.put(1, person);
Person p = cache.get(1);
// 3.x: Table API (KeyValueView for similarity)
KeyValueView<Integer, Person> kv =
    client.tables().table("persons").keyValueView(Integer.class, Person.class);
kv.put(null, 1, person);   // null = no transaction
Person p = kv.get(null, 1);

// === SQL ===
// 2.x: Query via cache
cache.query(new SqlFieldsQuery("SELECT * FROM Person")).getAll();
// 3.x: Direct SQL
client.sql().execute(null, "SELECT * FROM persons");

// === Transactions ===
// 2.x: ignite.transactions().txStart(PESSIMISTIC, REPEATABLE_READ)
// 3.x: client.transactions().begin()

Migration Toolkit (3.1+)

Apache Ignite 3.1 includes migration tools:

  • DDL Generator - Convert 2.x schema to 3.x SQL
  • Data Migration - Export from 2.x, import to 3.x
  • Progress Tracking - Monitor migration status
  • Type Conversion - Handle legacy Java types
# Example migration commands
ignite3 migration generate-ddl --source-config=ignite2-config.xml
ignite3 migration export-data --source-config=ignite2-config.xml --output=data.bin
ignite3 migration import-data --input=data.bin

Migration Strategy

  1. Assess Current Usage
    • Which features do you use? Are they available in 3.x?
    • Compute Grid, Continuous Queries, Service Grid = stay on 2.x
  2. Plan Parallel Operation
    • Run both versions during transition
    • Dual-write for gradual cutover
  3. Migrate Incrementally
    • Start with new features on 3.x
    • Move existing workloads gradually
  4. Test Thoroughly
    • Behavior differences exist (e.g., transaction semantics)
    • Performance characteristics differ
    • Error handling and failure modes differ

20. Summary

Key Takeaways

Ignite 2.16 - Choose When

  • You need production-proven stability
  • You require full Compute Grid (MapReduce, services)
  • You need Continuous Queries or Near Caches
  • You need Spring Data, Hibernate L2, or Kafka integration
  • You have existing 2.x deployment
  • You need ML/Streaming features
  • You are on Java 8

Ignite 3.x - Choose When

  • Starting a new project with SQL as primary interface
  • You need strong consistency (RAFT)
  • You're migrating from an RDBMS
  • You want modern tooling (CLI, REST, dynamic config)
  • You want pluggable storage engines
  • You need built-in security (auth/authz)
  • Multi-language team needs feature parity
  • Dynamic schema evolution is important

The Bottom Line

Ignite 2.16 is mature, feature-complete, and production-proven. It's the safe choice for existing workloads and applications needing advanced features like compute grid, continuous queries, or rich integrations.

Ignite 3.x is the future, with a cleaner architecture, RAFT consensus, SQL-first design, and better operational tooling. Choose it for new SQL-heavy projects and teams prioritizing consistency and modern ops.

Both versions will coexist - Ignite 2.x continues receiving maintenance releases.
