What's New in Ignite 3.x

A complete rewrite -- not an upgrade from 2.x

  • Schema-first design -- define tables via SQL DDL, not cache configurations
  • RAFT consensus -- consistent replication replaces 2.x's primary-backup
  • SWIM protocol -- lightweight cluster discovery replaces TcpDiscoverySpi
  • Pluggable storage engines -- choose page memory (volatile) or RocksDB (persistent)
  • Distribution Zones -- declarative control over data placement and storage profiles
  • Thin client only -- no embedded node mode; all apps connect as thin clients
  • HOCON configuration -- human-friendly config replaces XML/Spring
  • Strictly serializable transactions -- stronger consistency guarantees

  • RAFT -- each partition has a RAFT group for leader election and log replication
  • Storage -- pluggable per distribution zone (volatile or persistent)

Schema-First Philosophy

2.x Cache-First

// 2.x: define cache, then query
CacheConfiguration<Long, Person> cfg =
    new CacheConfiguration<>("persons");
cfg.setIndexedTypes(Long.class, Person.class);
IgniteCache<Long, Person> cache =
    ignite.getOrCreateCache(cfg);

3.x Schema-First

-- 3.x: define table via SQL DDL
CREATE TABLE persons (
    id   INT PRIMARY KEY,
    name VARCHAR,
    city VARCHAR
);

Then access via Table API, SQL, or KV view

Key shift: Tables are the primary abstraction. No more CacheConfiguration or @QuerySqlField annotations.

Table API Overview

Multiple views onto the same table

ViewDescriptionUse Case
RecordView<Tuple> Schema-less tuples, full row access Dynamic schemas, prototyping
RecordView<POJO> Mapped to a Java class Type-safe domain objects
KeyValueView<K,V> Separate key and value types Cache-like get/put semantics 
// Obtain views from a table
Table table = client.tables().table("persons");

RecordView<Tuple>          tupleView = table.recordView();
RecordView<Person>         pojoView  = table.recordView(Person.class);
KeyValueView<Tuple, Tuple> kvTuple   = table.keyValueView();
KeyValueView<Long, Person> kvPojo    = table.keyValueView(Long.class, Person.class);

RecordView with Tuples

Schema-less access -- no POJO needed

RecordView<Tuple> view = client.tables().table("persons").recordView();

// Insert
Tuple record = Tuple.create()
    .set("id", 1)
    .set("name", "Alice")
    .set("city", "New York");
view.upsert(null, record);

// Read
Tuple key = Tuple.create().set("id", 1);
Tuple result = view.get(null, key);
String name = result.stringValue("name");   // "Alice"
String city = result.stringValue("city");   // "New York"

// Delete
view.delete(null, key);
  • First argument is the transaction (null = auto-commit)
  • Tuple columns must match the DDL schema

RecordView with POJOs

Type-safe mapping -- fields match column names

// POJO: field names must match DDL column names (case-insensitive)
public class Person {
    int id;
    String name;
    String city;
}

RecordView<Person> view = client.tables()
    .table("persons")
    .recordView(Person.class);

// Insert
Person alice = new Person();
alice.id = 1;
alice.name = "Alice";
alice.city = "New York";
view.upsert(null, alice);

// Read
Person key = new Person();
key.id = 1;
Person result = view.get(null, key);
System.out.println(result.name);  // "Alice"
  • No annotations required -- mapping is by field name
  • For reads, only the key fields need to be populated in the lookup object

KeyValueView

Familiar get/put semantics with separate key and value

KeyValueView<Long, Person> kvView = client.tables()
    .table("persons")
    .keyValueView(Long.class, Person.class);

// Put
Person alice = new Person();
alice.name = "Alice";
alice.city = "New York";
kvView.put(null, 1L, alice);

// Get
Person result = kvView.get(null, 1L);

// Contains
boolean exists = kvView.contains(null, 1L);

// Remove
kvView.remove(null, 1L);
When to use: KeyValueView is ideal when you think of data as key-value pairs and want the simplest possible API. RecordView is better when the key is part of the record.

SQL in Ignite 3.x

First-class SQL with client.sql()

// DDL
client.sql().executeScript(
    "CREATE TABLE IF NOT EXISTS persons ("
    + "  id INT PRIMARY KEY, name VARCHAR, city VARCHAR"
    + ")"
);

// DML with parameters
client.sql().execute(null,
    "INSERT INTO persons (id, name, city) VALUES (?, ?, ?)",
    1, "Alice", "New York");

// Query
try (ResultSet<SqlRow> rs = client.sql().execute(null,
        "SELECT name, city FROM persons WHERE city = ?", "New York")) {
    while (rs.hasNext()) {
        SqlRow row = rs.next();
        System.out.println(row.stringValue("name"));
    }
}
  • executeScript() for DDL (multi-statement)
  • execute() returns ResultSet<SqlRow> -- implements AutoCloseable
  • First argument is transaction (null = auto-commit)

Distribution Zones

Declarative data placement via SQL DDL

-- Create a zone with specific replication and storage settings
CREATE ZONE us_east WITH
    replicas = 3,
    partitions = 100,
    storage_profiles = 'rocksdb';

-- Create a table in that zone
CREATE TABLE orders (
    order_id  INT PRIMARY KEY,
    customer  VARCHAR,
    total     DECIMAL(10,2)
) WITH PRIMARY_ZONE = 'US_EAST';
  • Replicas -- number of copies per partition (RAFT group size)
  • Partitions -- how data is split across nodes
  • Storage profiles -- rocksdb (persistent) or aipersist/aimem (page memory)
  • Tables are assigned to zones; zones control physical placement
2.x equivalent: Replaces CacheConfiguration.setBackups(), setAffinity(), and data region config -- all in one SQL statement.

COLOCATE BY

SQL-based data colocation

-- Parent table
CREATE TABLE customers (
    customer_id INT PRIMARY KEY,
    name        VARCHAR,
    region      VARCHAR
) WITH PRIMARY_ZONE = 'US_EAST';

-- Child table colocated with parent
CREATE TABLE orders (
    order_id    INT,
    customer_id INT,
    total       DECIMAL(10,2),
    PRIMARY KEY (order_id, customer_id)
) COLOCATE BY (customer_id)
  WITH PRIMARY_ZONE = 'US_EAST';
  • Rows with the same customer_id are stored on the same node
  • Enables efficient distributed JOINs without network shuffles
  • 2.x equivalent: Replaces @AffinityKeyMapped annotation and AffinityKey class

Transaction Model

Strictly serializable by default

IgniteTransactions txManager = client.transactions();

Transaction tx = txManager.begin();
try {
    RecordView<Tuple> accounts = client.tables()
        .table("accounts").recordView();

    Tuple from = accounts.get(tx, Tuple.create().set("id", 1));
    Tuple to   = accounts.get(tx, Tuple.create().set("id", 2));

    double amount = 100.0;
    accounts.upsert(tx, Tuple.create()
        .set("id", 1)
        .set("balance", from.doubleValue("balance") - amount));
    accounts.upsert(tx, Tuple.create()
        .set("id", 2)
        .set("balance", to.doubleValue("balance") + amount));

    tx.commit();
} catch (Exception e) {
    tx.rollback();
    throw e;
}
  • Read-write transactions are strictly serializable (strongest isolation)
  • Read-only transactions provide snapshot isolation

runInTransaction

Recommended approach with automatic retry

client.transactions().runInTransaction(tx -> {
    RecordView<Tuple> accounts = client.tables()
        .table("accounts").recordView();

    Tuple from = accounts.get(tx, Tuple.create().set("id", 1));
    Tuple to   = accounts.get(tx, Tuple.create().set("id", 2));

    double amount = 100.0;
    accounts.upsert(tx, Tuple.create()
        .set("id", 1)
        .set("balance", from.doubleValue("balance") - amount));
    accounts.upsert(tx, Tuple.create()
        .set("id", 2)
        .set("balance", to.doubleValue("balance") + amount));
});
Why use runInTransaction?
  • Automatic commit on success, rollback on exception
  • Automatic retry on transient conflicts
  • Cleaner code -- no manual try/catch/rollback

Mixed SQL + KV Transactions

New in 3.x -- combine SQL and Table API in one transaction

client.transactions().runInTransaction(tx -> {
    // KV operation: read account balance
    RecordView<Tuple> accounts = client.tables()
        .table("accounts").recordView();
    Tuple acct = accounts.get(tx, Tuple.create().set("id", 1));

    // SQL operation: insert audit log
    client.sql().execute(tx,
        "INSERT INTO audit_log (account_id, action, amount, ts) "
        + "VALUES (?, ?, ?, CURRENT_TIMESTAMP)",
        1, "DEBIT", 100.0);

    // KV operation: update balance
    accounts.upsert(tx, Tuple.create()
        .set("id", 1)
        .set("balance", acct.doubleValue("balance") - 100.0));
});
2.x limitation: In 2.x, SQL DML and cache operations used different transaction mechanisms and could not be mixed safely. Ignite 3.x unifies them.

Compute Grid

JobTarget, JobDescriptor, and Deployment Units

// Submit a compute job to a specific node
JobDescriptor<String, Integer> descriptor = JobDescriptor
    .<String, Integer>builder(WordCountJob.class)
    .units(DeploymentUnit.of("my-jobs", "1.0.0"))
    .build();

CompletableFuture<Integer> result = client.compute().executeAsync(
    JobTarget.anyNode(client.clusterNodes()),
    descriptor,
    "Hello World"
);

// Broadcast to all nodes
Map<ClusterNode, CompletableFuture<Integer>> results =
    client.compute().executeBroadcast(
        client.clusterNodes(),
        descriptor,
        "Hello World"
    );
  • Deployment Units -- versioned JARs deployed to the cluster via CLI
  • JobTarget -- control where jobs execute (specific node, any node, colocated)
  • Jobs implement ComputeJob<I, O> interface

Migration Checklist: 2.x to 3.x

  1. Audit feature usage -- identify dependencies on 2.x-only features (Service Grid, Continuous Queries, etc.)
  2. Convert cache configs to DDL -- replace CacheConfiguration with CREATE TABLE / CREATE ZONE
  3. Replace embedded nodes -- move to thin client (IgniteClient.builder())
  4. Replace XML/Spring config -- convert to HOCON configuration files
  5. Update data access code -- migrate from IgniteCache to Table API (RecordView/KeyValueView)
  6. Migrate SQL -- update queries for 3.x SQL engine; use client.sql().execute()
  7. Update transactions -- switch to runInTransaction() pattern
  8. Migrate compute jobs -- rewrite to ComputeJob<I,O> with deployment units
  9. Replace AffinityKey -- use COLOCATE BY in DDL
  10. Update monitoring -- switch from JMX to REST/OpenMetrics

When to Use 2.x vs 3.x

Stay on Ignite 2.x if:

  • You need Service Grid or Continuous Queries
  • You rely on embedded/thick client mode
  • Your app uses IGFS or Messaging APIs
  • You need MapReduce (ComputeTask)
  • Production stability is paramount and migration cost is high
  • You need near cache for latency-sensitive reads

Choose Ignite 3.x if:

  • Starting a new project (greenfield)
  • You want stronger consistency (RAFT)
  • SQL-first or schema-first design fits your needs
  • You need mixed SQL+KV transactions
  • You want modern config (HOCON) and monitoring (REST/Prometheus)
  • You need pluggable persistent storage (RocksDB)

Summary

  • Schema-first: SQL DDL is the primary way to define data structures
  • RAFT + SWIM: Stronger consistency and scalable discovery
  • Table API: RecordView, KeyValueView -- multiple views on the same table
  • Distribution Zones: Declarative data placement and storage profiles
  • Unified Transactions: Mix SQL and KV in one strictly serializable transaction
  • Modern Tooling: HOCON config, CLI management, REST/Prometheus monitoring
